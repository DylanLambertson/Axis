# Own shell: ticket plan to the first demo and the Phase 1 slice

- **Status:** Proposed, with ADR 0011 (`docs/adr/0011-own-shell-ide-as-optional-feature.md`). Ticket ids start with `OS-` (shell, main and UI) and `DC-` (new daemon contracts) so they do not collide with `PV-`, `S`, `A` or `C` ids.
- **Goal:** the owner can click through a first own-shell demo as soon as possible. Then the Phase 1 slice (1a, 1b, 1c) is reached on the own shell, with the gate text re-stated in OS-23.
- **Sizes** (working days, building plus an ordinary review): S is 1 day; M is 2 to 4 days; L is 5 to 7 days. A ticket marked **Security review** touches a trust boundary and gets an independent security review, which adds 1 to 3 days (two to four rounds). Other tickets get an independent review. Every ticket goes through the usual loop: build, independent review, fixes, PR, merge. The estimates in §4 are sums of these sizes along the critical path.

## 0. Wave A start list (hand-out on the owner's go)

These four **start** together on day 1 once the owner approves the build. None of them needs another to start. OS-2 starts on day 1 with its first PR (pure modules, no scaffold needed), but it **completes** only with its second PR, which wires those modules into OS-1's `main/`; that PR waits for OS-1. The Depends column and the edge list in §3 use the same split: start versus completion. "Builder" names a role, not a person; master-master assigns the session.

## 1. Layout in the repository

```text
apps/desktop/
  main/        Electron main: window registry, app scheme, session hardening, preload, the adapters
               over packages/daemon-host/src/main/* (replaces code-oss/overlay/.../code/electron-main)
  preload/     the one fixed preload (connect, projectAction, terminalPort, openExternal)
  renderer/    the React app: core shell + built-in modules, one esbuild bundle with lazy chunks
packages/shell-sdk/    module manifest, activation context, intents (types and a tiny runtime)
packages/shell-core/   renderer-safe logic ported from the overlay (daemon client, reconnect, events, models)
packages/ui/           tokens (the single colour source), brand constants, primitives, icons
packages/ui-editor/    the Monaco editor kit (lazy), theme bridge, Trusted Types policy names
scripts/lint/          the import scanner and web/egress rules moved from scripts/code-oss/
```

The renderer packages import only `@axis/protocol`, each other and their pinned UI dependencies, never `node:*`. ADR 0005's package rules apply. New `docs/packages.md` rows and tsconfig references are added in alphabetical order.

## 6. What two later screens need from the daemon

### 6.1 Tasks Start (PV-T2; from the PV-T1 slice 3 note, `docs/design/tasks-slice3.md` §6, merged)

**Already served:**
- `axis.tasks/1.list`, `get` and `revisions`. Titles and bodies are untrusted text, shown as text only, with `untrusted`, `hop` and each revision's author.
- The worker picker from `axis.agents/1.list` for the project: the kind (composer or CLI) and the name, with archived workers hidden.
- `startPreview { taskId, worker }`: the whole prompt, its digest, the worker's kind, and the task's source, `untrusted` and `hop`, shown before anything starts.
- `start { taskId, worker, seq, promptDigest }` with an idempotency key. The first call answers `E_APPROVAL_REQUIRED` with a tier-4 challenge (id, digest, method, tier, target summary, expiry, `nativeConfirmationRequired: true`). **Main's native dialog opens when the challenge is issued**, not when the user answers the card.
- **The card is the shell's own**, built from the whole `startPreview` answer the shell kept (the prompt, the worker, the task's source, `untrusted` and `hop`) together with the pending challenge. It is bound to what it shows, because `start` names that preview's `seq` and `promptDigest`, which are part of the request the challenge covers. The shell **never** calls `axis.approvals/1.detail` for a task Start: `detail` serves plugin challenges only and answers `not_found` here, and no task endpoint for it is planned.
- The user answers the card (`axis.approvals/1.resolve`). For this tier-4 challenge the answer is `approved, nativeRequired: true`, which is **not a grant**: the challenge still waits for main's dialog.
- The shell retries `start` with `approval` and the same idempotency key. A retry before main's dialog has confirmed is refused `E_CONFLICT` and spends nothing, so the shell retries after the dialog closes. **No daemon event** says that the dialog confirmed. A confirmed challenge must be used within its short window; after that it expires and Start begins again from the first call. On `stale_version` the shell previews again and asks again. Other refusals are the contract's closed reasons.
- The result. A composer worker returns `{ runId, workspaceId }`, followed with `axis.runs/1` events. A CLI worker returns `{ text }` for the user to copy (RR-95); the shell offers a copy button and opens the worker's terminal through the existing worker start.

**Daemon tickets:**
- DC-8, **built** (#675): a composer Start links its run to the task and sets `in_progress`, in the same transaction as its `task.start` row. A task already holding its 32 links gets no link.
- DC-9, **built** (#676, follow-up #682): the `tasks` topic of `axis.events/1`, a per-project invalidation hint `{ topic, projectId }` with no text. The shell then calls `list`.
- DC-10, open, not needed for v0: an optional `taskId` on the preview of a worker's pending task-tool card. Until then the shell knows which task a pending card is for only from the card's content.

**What the shell shows (decided):**
- A task stays `in_progress` after its run ends or fails: no rule moves it. The shell shows the linked run's state from `axis.runs/1`.
- A Start whose run is not in the task's `links` (the task held its 32 links) is said in words; there is no replace-oldest.
- A worker's `update_task` over a revision the user wrote asks at tier network, and every task write of a tainted run asks. Both arrive as ordinary OS-11 run cards showing the change whole; no task-specific card.
- `limit_reached` gets fixed words. For a worker it appears in the run's events (past 25 creates in one run, or inside the share kept for the user: the last 100 of a project's 1,000 tasks and a tenth of its text, `tasks-store.md` §4.1). For the user's own create it means the project's 1,000 tasks.

### 6.2 The plugin approval card (PV-K1e-a2's renderer half, `docs/design/plugin-run-start.md` §2)

**What the own shell renders for a plugin challenge:**
- In `axis.approvals/1.pending`, a challenge a plugin caused carries the optional closed `requester { kind: "plugin", pluginId }`. A window holds at most 4 such challenges (`MAX_PLUGIN_CHALLENGES_PER_WINDOW`), and the reader is strict and accepts the field only in that shape.
- `axis.approvals/1.detail { challengeId }` (tier 0, user rows only, never a plugin view or a web client) returns `runs.start` detail: the requester, the **full escaped prompt** (up to 64 Ki UTF-16 units; a longer one is refused at issue, never cut), the project and workspace display names, the mode, the provider and the model. The card shows all of it as text before Approve is offered. It offers no Approve when `detail` fails, the challenge is gone or its binding broke.
- **Tier:** a plugin run start is **tier 3**, resolved in the renderer by the user principal. There is no native dialog (plugin challenges are refused tier 4 today; the open question PV-K1e-T4 may change that), and no copy may call it native. Its protection is the taint, the full prompt on the card and an approval for each side effect of the run.

**Ordering: OS-30 is a hard precondition of PV-K2** (the plugin grant contract; `plugin-run-start.md` §3.1 and `plugin-grant-contract.md` §1, both merged). It is one of six conditions, all of which must hold before PV-K2's grant calls are enabled (K2-enable merges). PV-K2's slices with the grants switched off may merge earlier (`plugin-grant-contract.md` §8.5):
1. The own shell's card exists (OS-30).
2. The Code OSS shell is retired, or every supported pending-approvals reader accepts the optional `requester` and `detail`.
3. A test through the real host composition covers the plugin run-start wiring.
4. A source or test pin shows that every production path granting `runs.start` goes through PV-K2's main-owned tier-4 flow with native confirmation.
5. The open question PV-K1e-T4 (tier 4 for plugin run starts) is decided.
6. The requesting plugin's connection, and its host window, are checked live after the approval is spent and again right before the run is recorded. A race test closes the connection during an awaited step after the spend and proves that no run is created.

**PV-K1e-b merges first, by waiver** (owner delegation, 2026-11-26): it is inert, because no plugin can hold `runs.start` until PV-K2, so OS-30 does not gate it. The Code OSS renderer half (a2-2) stays on hold, and OS-30 replaces it.
