# Axis pty process (ticket B9)

Status: built as `@axis/pty-process`, without a native dependency. Sources: threat model PTY-3, PTY-5, PTY-6, PTY-7, gate G-2 and G-14; `docs/design/daemon-host-plan.md` question 18; runs review 2 (N4). The fake `LocalPty` of the headless slice stays until the shipped entry exists.

## What runs where

- The **pty process** is a separate utility process that main forks. It holds no secrets and no privileged port. `createPtyService` is its logic. The only thing it needs from outside is a `SpawnFn`: a synchronous function that starts a child in its **own session or job** and returns a `PtyChild`. In the shipped entry that function is the native pty binding.
- The **daemon host** talks to it with `createPtyProcessPort` (a `PtyPort`, the shape `@axis/runs` uses) over one **control channel**. `composeDaemonHost` already takes `pty: PtyPort`, so the only wiring is passing this port instead of `LocalPty`; no composition code changes in this ticket.
- The **renderer** reaches terminals over **data channels** that main brokers after the ADR 0003 window-identity checks. A data channel is named (`conn`) by whoever brokers it. It can only `attach` (to a terminal the control channel `grant`ed to that name), `write` and `resize`. A `spawn`, a `kill` or any other message on it is refused and never acted on (`refused unsupported`).
- The package imports no `node:child_process` (ADR 0005: only the listed packages may), so the spawn function is injected. `testing/helpers.ts` holds a pipe-based POSIX reference (`pipeSpawn`) that the conformance tests run against.

It is a state machine over the transitions of the xterm.js parser Code OSS uses: ESC and the 8-bit introducer 0x9d start an OSC from every state (inside another OSC, after ESC plus controls, inside DCS), BEL, 0x9c, ESC, CAN, SUB and the other C1 controls end or abort one, the id is read as an integer (`0633` is 633, controls inside it are skipped), a partial sequence is carried across chunks, and only the id is ever held (64 characters, then the sequence is dropped). ## Limits and platform notes

- A child that calls `setsid` or double-forks leaves the group and is invisible. A pgid can be reused after its group empties: `groupAlive` then reports alive (fails closed); the probe-before-kill narrows but cannot close the window for a signal.
- After a daemon restart the host has no handles, so `discardInterrupted` must not lift a blocked row without its own group check (plan Q18).
- Terminal output produced before the first `attach` is dropped (nothing is buffered): the entry must grant and attach before it releases a run's first input, or accept losing a banner.
- Tests that need real processes run on Linux and macOS (`node:test` skip reasons name the missing capability). `child-fds.test.ts` needs `/proc`. The Windows job-object path is exercised only against a fake child; it is unverified on Windows.
- If the leader is gone the host reports an unknown exit (`null`, `null`) when the channel closes; the supervisor treats that as a failed run with an unknown exit, and the group probe still blocks finalisation while members live.

## Decisions

1. **Native pty dependency: reuse Code OSS's own `node-pty` from the overlay entry, through the injected `SpawnFn`.** No new dependency for `packages/*` and no ADR 0005 change: D4 governs package runtime dependencies, and native modules are reached only from overlay entries through injected functions. Conditions for the ticket that builds the entry:
   - call `node-pty`'s `spawn` **directly**, not upstream's `PtyService`/`TerminalProcess`, which add `VSCODE_*` variables and the nonce after this service's PTY-5 check (PTY-6); node-pty adds `PWD` (the cwd) and, only when missing, `TERM`;
   - run `child-fds.test.ts` and the group tests against the node-pty `SpawnFn` when wiring (on Linux node-pty forks with `setsid`, so pgid equals pid; fd inheritance must be shown, not assumed);
   - Windows: ConPTY via node-pty gives no job object, so the `job` group path has no source. Either a job-object helper (new native piece, needs an ADR) or Windows CLI runs are unsupported for 1a;
   - the ADR 0005 D3.4 overlay lint that stops renderer code importing this package is not built. Ticket row: **X1-lint**, land it (or a staged-graph check) with the entry.
2. **Id binding: `grant`.** Main (through the control channel) names which brokered data port may attach; first-attach-wins is gone.
3. **Channel transport.** `Channel` is a minimal interface; the entry adapts `MessagePort` (built in the addendum below). A utility process's `parentPort` has no `close` event; the control channel is a brokered port, which has one, and `adaptMessagePort` takes `closeOn` for any channel that lacks it.

## Open questions

1. **Git in the pty context.** The `pty` git runner (`commit-tree`, `push`, hooks) is a separate control message family and stays with H9-hooks; the fake runner remains.
2. **`@axis/daemon-host`'s `PtyPort`** (which requires `groupAlive`) is not compared by a type test here, because nothing may import the host; the entry that wires the port adds that check.
3. **Differential OSC test in the overlay suite.** The oracle in `testing/osc-oracle.ts` is a model written from the xterm.js transition table; the real parser is only checked by a manual run. Move that run into the overlay tests (they may import `@xterm/headless`).

## Addendum: the MessagePort adapter and the utility process entry (ticket pty-adapter)

| Piece | File | Runs in |
|---|---|---|
| `adaptMessagePort(port, { shape, closeOn? })`: a `MessagePortMain` (`shape: "electron"`, events `{ data, ports }`) or a Node port (`"node"`) as a `Channel`; close synthesised once from the port or `closeOn`; listeners removed; a message that carries ports is dropped and the ports closed | `packages/pty-process/src/port-adapter.ts` | pty process, daemon host |
| `createNodePtySpawn(spawn, platform)`: node-pty's `spawn` called directly as the `SpawnFn` (`handleFlowControl: false`, environment copied, `pgid = pid`, signal numbers named; Windows throws, so `spawn_failed`) | `src/node-pty.ts` | pty process |
| `runPtyEntry(deps)`: refuses (exit 78) without a parent port, with debugger flags, any `execArgv` or `NODE_OPTIONS`; serves what main hands over; kills every terminal on SIGTERM, SIGINT, process exit or `dispose` | `src/entry.ts` | pty process |
| Overlay hand-over of the real `process`, `parentPort` and Code OSS's `node-pty` | `code-oss/overlay/src/vs/axis/pty/node/axisPtyMain.ts` | pty process |

**Hand-over from main.** Only main writes `parentPort`. A message is exactly `{ type: "pty-control" }` or `{ type: "pty-data", conn }` (`conn` 1 to 128 characters) and carries exactly one port; anything else, or any extra key, is dropped and every port in it closed. The daemon's end of the control port goes to the daemon host (`createPtyProcessPort({ channel: adaptMessagePort(port, { shape: "electron" }) })`); for each renderer connection main makes one port pair per terminal view, sends one end here with the `conn` name, the other to the renderer, and the daemon sends `grant { term, conn }`. G-2 is unchanged: the name is main's, the binding is the daemon's, a data port can attach only to a terminal granted to its name, and the grant dies with the port.

**Backpressure and bounds, hop by hop.** Child to pty process: node-pty `pause()` and `resume()` (a paused child blocks on the kernel pty buffer). Pty process to viewer: credit flow control (`src/flow.ts`). Output sent and not yet acknowledged by the viewer (`ack { term, chars }` on the data channel, owner only) pauses the child above 1 MiB, resumes it under 256 KiB, and past 4 MiB is dropped and counted; the viewer is told once (`overflow`) how much was lost. A child with no `pause` is bounded by the drop alone. When the viewer leaves or is replaced nothing is outstanding: the child is resumed and its output is dropped, as before the first attach. Control and data messages are bounded by the schemas (`writeChars` 65536, ids 128). Renderer to child: not bounded by the adapter. node-pty gives no write-completion signal, so a hostile renderer can queue input faster than the child reads it; the pty process holds no secrets and is killed with its group when the control channel closes. Recorded as a residual risk; a per-terminal input budget is a follow-up.

**Channel close.** The control port closing (daemon exit, or main closing it) kills and discards every terminal through the existing service path; so do SIGTERM, SIGINT and process exit. If the pty process is killed outright its groups survive and the host's `kill(-pgid)` fallback applies (unchanged).

**Child-fd and group conformance against node-pty.** Run by hand against Code OSS's own copy (a packaged `node-pty` 1.2.0-beta.18, Linux): a shell started through `createNodePtySpawn` and the service lists `/proc/$$/fd`: only the pty (`/dev/pts/N` three times), none of the parent's descriptors; `groupAlive()` is true while it runs and false after the control channel closes. The automated suite cannot import node-pty (packages import only `node:*`, zod and `@axis/*`), so it runs the same flows against the `node:child_process` reference and fakes of the node-pty surface; the overlay suite on a Code OSS tree must repeat the manual run.

**Not built here.** Main's side: the `utilityProcess.fork` of the pty entry, the `pty-control`/`pty-data` hand-over, the `grant` call and the daemon entry's `pty` port (the daemon entry still passes no ports, `pty_required`). Registering `vs/axis/pty/node/axisPtyMain` as a build entry needs two more lines in the entry lists of `build/next/index.ts` (patch 0200); that is a Code OSS patch, so it is left to the master. The overlay file has not been compiled against Code OSS's typings (no tree on this host). The renderer-import lint (X1-lint) is a separate branch; this adapter adds nothing the renderer may import.
