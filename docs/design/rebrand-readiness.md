# Rebrand readiness inventory

This is a source inventory at `origin/main` `ce154372` (2026-11-26), not a rename proposal. The product identity is spread across presentation, build inputs, APIs and persisted state. A future name can change the first group cheaply; changing the latter groups needs explicit compatibility work.

## Counting method and limits

Counts below use Git-tracked files (`git ls-files`), so generated Code OSS and vendor trees are excluded. A *file* is counted once per row if it matches that row's stated search, even when it contains many matches. Rows overlap: for example an SVG contributes to both assets and visible brand text. Do not add row counts. The baseline is repeatable with `git ls-files`, `rg -l`, `rg -o`, and the named source tables; documentation and patches are called out separately. Search counts are indicators of work, not a complete rename manifest: tests, examples, comments, localization keys, and similarly named non-brand symbols occur in broad matches.

## Staged change plan

1. **Brand strings and colour tokens.** Define the product display name and shared UI copy at their existing localization/product configuration seams; consolidate theme palette values against `docs/UX.md` tokens. Replace visible copy in overlay UI and docs. Check menus, dialogs, settings labels, accessibility labels, and light/dark contrast. Keep identifier values unchanged in this stage.
2. **Assets.** Replace the six source assets, regenerate platform icons through the existing icon script, and verify extension theme labels, OS icon mapping and package outputs. Keep theme IDs stable until a preference migration is specified.
3. **Internal identifiers.** Produce an explicit old-to-new map for package names/imports, `axis.<area>/<n>` contracts, `axis.*` settings and commands, journal schema/data paths, Git refs, URI schemes and `AXIS_*` handoffs. For each persisted or externally callable ID, state who writes it, who reads it, the old-data discovery path, migration/alias window, rollback behavior and version tests. Move protocol versions and handlers with their policy rows; migrate existing journal/data before switching the default. Do not treat a text replacement as a migration.

## Rules until the change

- Put new user-visible brand text through localization or the existing product/theme sources; use design tokens for colours. Keep assets in `assets/brand/` and generated outputs generated.
- Reuse existing contract constants, setting/command constants and package imports. Do not invent another branded namespace or inline a second copy of an ID.
- Keep wire, stored and OS-facing identifiers stable even when display text changes. A proposed rename of one of these needs a compatibility note and a test with old state or old clients before implementation.
- Label documentation examples as examples; verify implementation claims in the registry, manifests, storage code and product patch. This avoids counting a design proposal as a shipped surface.
