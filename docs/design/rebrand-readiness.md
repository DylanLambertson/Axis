# Rebrand readiness inventory

This is a source inventory at `origin/main` `ce154372` (2026-11-26), not a rename proposal. Its overlay, theme extension, product patch and icon generator rows describe the **legacy Code OSS shell**. On 2026-11-26 the owner directed an own shell with the IDE as an optional feature. ADR 0011 on `docs/adr-own-shell` records that direction but is **Proposed**, not Accepted; its new-shell adapters are not yet an inventory of shipped code. The product identity is spread across presentation, build inputs, APIs and persisted state. A future name can change visible copy and colours cheaply; stored and externally callable identities need compatibility work.

## Counting method and limits

Counts below use Git-tracked files (`git ls-files`), so generated Code OSS and vendor trees are excluded. A *file* is counted once per row if it matches that row's stated search, even when it contains many matches. Rows overlap: for example an SVG contributes to both assets and visible brand text. Do not add row counts. The baseline is repeatable with `git ls-files`, `rg -l`, `rg -o`, and the named source tables; documentation and patches are called out separately. Search counts are indicators of work, not a complete rename manifest: tests, examples, comments, localization keys, and similarly named non-brand symbols occur in broad matches.

## Staged change plan

1. **Brand strings and colour tokens.** Establish one shared product/display-name source for every shell and package adapter, and one semantic palette definition per supported theme with derived consumers. Change visible copy and colours in the active shell and docs; check menus, dialogs, settings labels, accessibility labels, and light/dark contrast. Preserve wire IDs, stored names, the old `safeStorage`/OS encryption identity, secret frames and the original audit anchor. Updating Code OSS localization, `product.json` patches or `theme-axis` is a legacy-only step, not the new shell's brand source.
2. **Assets.** Replace source artwork, then derive platform icons through packaging and icon adapters for the new shell. Verify installed app icons and both themes. The current `scripts/code-oss/gen-icons.sh`, theme extension labels and product patch outputs are legacy-only consumers; their new-shell replacements depend on the own-shell design. Keep persisted theme preferences compatible until their migration is specified.
3. **Internal identifiers and stored data.** Produce an old-to-new map for package names/imports, `axis.<area>/<n>` contracts, `axis.*` settings and commands, journal schema/data paths, Git refs, URI schemes, `AXIS_*` handoffs, secret frames and the anchor tag. For each externally callable or stored ID, state the writer, reader, old-data discovery path, alias window and rollback behavior. Discover and migrate the daemon database, worktrees, `<base>/secrets` and `<base>/anchor/audit-anchor.v1` as sibling stores together; keep old encryption access until old-secret reads and the original audit head are verified through upgrade, crash recovery and rollback. Preserve historical audit payload bytes and hashes: never rewrite them, re-anchor a chain or silently start with empty state. Require old-state, old-secret-read and audit tail-truncation tests before implementing any such rename. Move protocol versions and handlers with their policy rows. Do not treat a text replacement as a migration.

## Rules until the change

- Put new user-visible brand text through the shared display-name source and theme colours through semantic palette definitions; derive shell, packaging and icon consumers. Code OSS overlay, theme extension, product patch and icon-generator changes are legacy-only. Keep assets in `assets/brand/` and generated outputs generated.
- Reuse existing contract constants, setting/command constants and package imports. Do not invent another branded namespace or inline a second copy of an ID.
- Keep wire, stored and OS-facing identifiers stable even when display text changes. A proposed rename of one of these needs a compatibility note and a test with old state or old clients before implementation.
- Label documentation examples as examples; verify implementation claims in the registry, manifests, storage code and product patch. This avoids counting a design proposal as a shipped surface.
