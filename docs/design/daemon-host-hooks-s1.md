## Departures from the design text

1. **Filter drivers are pinned off on every exec (finding).** §4.1 says no allowed form can start a filter, but git compares a racily clean index entry with the work tree through the clean or process filter when it writes the index, and `write-tree` does that. With `filter.<name>.process` set and a matching attribute, a pinned `write-tree` started the driver (git 2.53). The service now reads the configured driver names (`config --null --name-only --get-regexp ^filter\.`, which starts nothing) with the same prefix and environment just before each non-`config` call and adds `-c filter.<name>.{clean,smudge,process}=` and `filter.<name>.required=false`, as git-ops already does daemon-side. A driver name a `-c` pair cannot carry exactly (`=`, newline) refuses the call. The design's mechanism is strengthened, not changed; the design doc should say so in S3.
2. **Verification hashes in-process.** §5 step 8 says `hash-object --no-filters --stdin` over bytes the service read. The service computes git's blob id itself (`blob <size>\0` plus the bytes, SHA-1 or SHA-256 by the id length): the same value, no process, no `--stdin-paths` possible.
3. **`bind` carries the attempt id** (`{ attempt, gitDir, index }`); the design's `{ gitDir, index }` cannot name the registration it must equal.
4. **Both scratch indexes are filled and checked.** `staged` reports whichever differs from the reviewed tree, so a hook bound to `index2` cannot stage unseen.
5. **Hook refusals use `spawn-failed`** with the new codes `hook_changed` and `bad_bind` (a realpath outside both roots is `bad_bind`). Scratch replies are `scratch-ready`, `scratch-verified`, `scratch-ended` and `scratch-failed` (`bad_bind`, `bad_tree`, `capacity`, `timeout`, `spawn_failed`); the design names none.
6. **A path that is not UTF-8 refuses the fill** (`bad_tree`): fail closed rather than write byte names.
7. **Capacity counts requests at entry**, before their version and filter reads, and a request whose control channel closed while it awaited a read never starts its git and sends no reply (a reply would reach the next control channel).
8. **`GIT_ALLOW_PROTOCOL=/` and `-c help.autocorrect=0` on every exec (review findings).** §4.1 said `protocol.allow=never` stops a lazy fetch on git before 2.44, which has no `GIT_NO_LAZY_FETCH`. It does not: a repository `protocol.file.allow=always` (or the same for another transport or a `<helper>::` remote) overrides it, and the promisor remote's `uploadpack` or a `git-remote-<x>` helper runs. `GIT_ALLOW_PROTOCOL` overrides every `protocol.*` setting on every git since 2.12, but its value is a list of transport NAMES, so whatever it names is admitted: `none` is a helper a repository can supply (`remote.<r>.vcs=none` with `alias.remote-none`, a `none::` URL, `git-remote-none` on PATH), and an empty value matches an empty `vcs`. `/` is admitted too, but its helper `git remote-/` cannot run: it is no builtin, no program (`git-remote-/` can only be a directory) and no alias (`alias.remote-/` is not a valid key). Git then falls through to autocorrect, which with a repository `help.autocorrect` would run the closest alias (`alias.remote-a`), so the service pins `help.autocorrect=0` (suggest only on every version; `never` exists only from 2.37). Tested with an old-git stand-in (the real git with `GIT_NO_LAZY_FETCH` removed) for `protocol.file.allow=always`, `vcs=none` with an alias, an empty `vcs` with a helper on PATH, and `vcs=/` with `help.autocorrect=-1` and a near alias, each in every form a lazy fetch can take, each with a control showing the setting does start a program without the service's value or pin.
9. **Plain `repo.gitDir` is shape-checked only** (absolute, no NUL), not checked on disk like `bind.gitDir`; it is trusted from the daemon (R-H3). The design text now says so.
10. **A close also stops scratch steps.** `scratch-begin` and `scratch-verify` record the service generation; after a close no further git starts for the attempt and no reply for it is sent.
11. **`-c core.fsmonitor=` (empty), not `false`.** Git 2.24 to 2.35 read `core.fsmonitor` as a hook path, so `false` names a program looked up on PATH; empty disables it there and reads as false from 2.36. git-ops' own daemon prefix still uses `false` (its ticket).
12. **Stricter than listed:** `var` takes only `GIT_AUTHOR_IDENT` or `GIT_COMMITTER_IDENT`; `read-tree` takes exactly one object id; `rev-parse --git-path` only `hooks/<name>`; `rev-list` also allows `--objects` (the design's own marker case uses it).

## Old git: pins or a version floor (evaluated, not decided)

Three review rounds found three ways a repository could start a program through a lazy fetch on git before 2.44 (a per-protocol allow, a helper named by the allow-list value, autocorrect onto a near alias). Each is closed by a pin and tested with an old-git stand-in. Only git 2.44 and later honour `GIT_NO_LAZY_FETCH`, which stops the fetch before any transport, helper or alias is looked up, so on 2.44+ the whole class is closed by one switch; below it the service depends on the pins being complete.

- **Switch.** `MIN_GIT_VERSION` in `src/exec-argv.ts` (default `undefined`: pins only), overridable per service as `minGitVersion`. Set to `[2, 44, 0]`, every `exec` and `scratch-begin` on older or unknown git is refused (`spawn_failed`) before any git but the version probe runs, so no hook runs either. Tested both ways (`exec-version.test.ts`).
- **Cost of a 2.44 floor** (distribution defaults as known when written; re-check before deciding): Ubuntu 22.04 ships 2.34 and Ubuntu 24.04 2.43, Debian 12 2.39, RHEL 9 2.43 or older by minor release, and the git in Apple's command line tools has long been 2.39. Users there would need a newer git (a PPA, backports, Homebrew) or `axis.git.runHooks` off. Git for Windows, Homebrew, Fedora and Debian 13 are past 2.44.
- **Recommendation.** Keep the pins as the default (they are tested and each failure mode found so far was a missing pin, not a design flaw), and decide the floor with the owner together with D1, since a floor turns old git into `hooks_unavailable`. Not decided here.

## Residuals (to enter the register with S3)

- **Filter-read window.** The driver-name read and the call it protects are two processes. A filter added to the config or `info/attributes` between them (a CLI run in another terminal, a surviving hook child, R-H2) is started by the pty process. Impact: a program runs as the user; the decision is unchanged (the racy check does not change the tree written). Narrowing on git 2.40+ with an attribute source for bound calls is possible; `info/attributes` would stay.
- **Parent checks are lstat-then-use.** The writer checks each parent with `lstat` before the create; a same-user racer could swap a parent for a symlink in the window. Node has no `openat`. The check is defence in depth: the planner already refuses every tree that would need it, and symlinks are written last.
- **Windows.** The NTFS trailing-dot and trailing-space fold is applied to collisions on every platform (so a tree holding both `a` and `a.` is `bad_tree` on Linux too, fail closed), and `GIT_ALLOW_PROTOCOL=/` is unverified there, but the Windows path as a whole (modes, the hooks-off directory) is unverified.

## Left for the rest of S1 and later slices

- Host-side hook orchestration (§4.2: grant and attach before the spawn, timeout and cancel, `groupAlive` after exit) and the daemon's use of `judgeHooksPathRead` (S2), with `Snapshot` v3 storing the raw value (git-snapshot).
- The shipped entry must supply the `ExecFn` (a process-group launcher), the startup git path, git-ops' `hooksOffPath()` and the scratch parent. Windows is unverified (the hooks-off directory and modes).
- Open decisions D1 to D3 are unchanged; part 1 implements the D3 default (raw tree, any new file refuses).
