# `axis.git/1` handlers and the `GitOpsDeps` assembly (ticket H9)

- **Where.** `src/handlers/git*.ts` (`pushPlan`, `commit`, `push`, `compareUrl`, registered with `registerGitHandlers(registrar, deps)`, never the daemon) and `src/bindings/git.ts` (the only file that calls git-ops' operations, with `@axis/secret-scan` for the scanner type; `bindings/review.ts` and the port files import it as before). `createGitPort` builds `GitOpsDeps`: one runner that routes `daemon` to the node runner over the host's single `gitPath` and `pty` to the injected pty runner (absent, or an unknown context: `E_UNAVAILABLE`; the composition injects `createPtyGitRunner` over the pty port's `exec` when it has one, `docs/design/daemon-host-hooks-s1.md` part 2); the scanner is required and `scanner` and `scanMode` both come from it. `createGitOperations` refuses a port without a function scanner and a `refuse` or `warn` mode (the scan runs inside git-ops with that port, and git-ops finds nothing without a scanner), exposes the mode as `GitOperations.scanMode`, and `registerGitHandlers` refuses to register without it.
- **Derived, never sent.** Branch, base (what Axis last pushed to THAT remote, else the recorded base), worktree and remote URL come from the journal, the locator and the repository; the request names a workspace and a remote.
- **Commit.** Under the one project mutex: `expectedBranch` must equal the journal's branch, the reviewed tree must be one a `diff` of that workspace produced with the same parent and branch, then `prepareCommit` (the brand check; the handle is read by nothing before it), `handoff`, and `executeCommit` with `assertReviewFresh`. A refusal after `prepare` returned puts the person's index back, only while HEAD is still the reviewed commit and the index still holds what Axis staged (staging the person did since is kept). A refusal `prepareCommit` raises after its own `read-tree` leaves the reviewed tree staged (upstream: nothing to restore from). **Decision B2 (OPEN, ticket H9-hooks):** a bound commit runs no repository hook and nothing records "made without hooks". The design for the hook runner, the reply fields and the slices is `docs/design/daemon-host-hooks.md`.
- **Push.** The content hook asks the anchor first (a stalled anchor does no scan and issues no challenge), then plans under the mutex and uses the plan digest as the content digest; a plan that is not the request's `confirmedPlan` is `plan_changed` before a challenge exists. The handler pushes only the confirmed tip and records it as the last pushed sha; if that write fails the push still happened and the reply is the success.
- **Scan base per destination (S1).** The journal's `lastPushedSha` is per workspace but the destination is per request, so it is recorded (informational) and never used as a scan base. `PushedBases` is a bounded table (persisted, see H9-base-ssh below) keyed by (workspace, SHA-256 of the sorted `git remote get-url --push --all` output) to the last pushed tip, so `pushurl` and `pushInsteadOf` count, a remote re-pointed after a push misses, two names for one URL share an entry, and no URL (userinfo) is ever stored. A destination with no entry (never pushed, evicted, or after a restart) is scanned from the workspace's recorded base, which is only ever a larger range. `allowedBinaryPaths` is per request, so a waiver never carries to another destination. **Destination resolved (H9-base, RR-11).** The key is the hash of the sorted canonical destinations, not of the raw URLs (`src/bindings/push-target.ts`): a path remote (plain, relative or `file://`) is its `realpath`, so a symlink or relative form shares an entry and a directory swapped behind the same name misses; an ssh remote (`ssh://` or scp-like `host:path`) is (user, host, port, path) after the injected `resolveSshHost` (`GitOperationsDeps`) has turned the host or alias into where it connects, so an alias edited to another host misses and two names for one host share; other URL forms are keyed as written. **Fail closed:** a path that does not resolve, or a resolver that throws or answers something that is not a host and a port, makes `pushPlan` and `push` answer `E_INVALID_ARGUMENT` before any scan. The URL's own user and port win over the resolver's (as in ssh); a host that starts with `-` or holds whitespace or control characters, and a bad URL port, are refused before the resolver is called, and the resolver is given the user name only, never a password. A trailing slash, a `.git` suffix and the case of an https host are not folded (only extra misses, never a shared base). Without a resolver (a test) an ssh host is keyed as written. **Resolver and persistence (H9-base-ssh).** The composition wires `createSshResolver` (`src/bindings/ssh-resolver.ts`) when the embedder passes `ComposeOptions.sshSpawn`; this package starts no process itself (the staging allowlist keeps `node:child_process` out of it), so the embedder supplies a spawn that takes the options the resolver passes (`shell: false`, stdio `ignore, pipe, ignore`, `windowsHide`, `detached: true`, exactly the given environment) and whose `kill()` ends the process GROUP (`process.kill(-pid)`). Without one, every ssh destination refuses its scan base (`unavailableSshResolver`, fail closed) and path remotes are unaffected. **The embedder that supplies it is not written yet** (`axisDaemonMain.ts` does not even pass `pty` yet), so RR-11 closes only when it passes a spawn. The resolver runs `ssh -G [-l user] [-p port] -- host`, never connecting; the program is `ssh` found on the filtered `PATH` (or an absolute `file`), no `-F`, so ssh reads the person's own configuration as it would for the push. The environment is only `PATH`, `HOME`, `USER`, `LOGNAME` and `LC_ALL=C`; `PATH` keeps its plain absolute entries only, minus every entry inside the registered worktrees, the data directory and the daemon's working directory (`excludeDirs`), judged by spelling and by real path on both sides, compared by path component (a `PATH` entry that is a symlink into a worktree, and a worktree configured through a symlink, are both caught; the same rule as git's resolver), and with none left nothing starts. The program is found once per resolution and its absolute REAL path is what is spawned, after a last check that it is an executable file outside every excluded directory, so the spawn looks nothing up and nothing falls back to a bare `ssh`. `HOME` does not select the ssh configuration (ssh reads `~/.ssh/config` through the account database). Before any process starts the host must match `[A-Za-z0-9._:-]{1,255}` (an ipv6 literal loses its brackets): no `@`, no control character of any range (C1 included), no non-ASCII, no leading `-`; a user must be ASCII `[A-Za-z0-9._+-]` without a leading `-`. Stdin is closed, stderr dropped, output is at most 64 KiB and the run at most 5 s (the process is killed), one resolution at a time, at most 16 running or waiting in all (one more is refused; the timeout starts when a run starts, so the last in the queue can wait about 80 s). Only `hostname`, `port` and `user` are read; a missing hostname or port, a value outside the strict set, two different values for one key, a non-zero exit, a start error or invalid UTF-8 throws, which refuses the scan base. The answer is not cached, so an alias edited between two pushes is seen. **Trust decision:** `ssh -G` evaluates `Match exec` of the person's own configuration, as the push itself would; Axis does not disable it, and does not read any other configuration. **Residual:** a `Match exec` command that outlives a timeout is ended only if the embedder's `kill()` ends the process group as the contract says; a plain `kill` of ssh leaves it running. **Another ssh command:** when `GIT_SSH` or `GIT_SSH_COMMAND` is set in the daemon or push environment, or `core.sshCommand` is set in any config git reads (or `git config` gives anything but a clean "not set"), the configuration `ssh -G` reads is not the one the push uses, so an ssh destination refuses its scan base; path remotes are unaffected. `core.sshCommand` is read by the daemon's git, with the daemon's `HOME` and `XDG_CONFIG_HOME`, while the push runs with the push environment's: "any config git reads" means the daemon's view (the same assumption `env.ts` documents for `XDG_CONFIG_HOME`), so a global `core.sshCommand` that only a different push `HOME` would load is not seen. **Which ssh:** the resolver's `ssh` comes from the daemon's filtered `PATH`, the push's from the push environment's `PATH`; when they name different binaries (for example `/usr/local/bin/ssh` with another system configuration path), the key can describe a destination the push's ssh would not choose (residual, RR-11). A non-ASCII (IDN) host is refused, not guessed at. **Persistence:** `PushedBases` is loaded from and saved to `push-bases.v1.json` in the data directory (`src/storage/pushed-bases-file.ts`): a hash and an object id per workspace and destination, never a URL. A save writes a new `0600` temporary file in the same directory, `fsync`, `rename`, then `fsync` of the directory; saves run one at a time in call order; a save that fails after the push went out is reported as bookkeeping and the push still succeeds (the in-memory base stays). A load never throws and trusts nothing: a missing file, a symlink, a file over 1 MiB, bad JSON, another version or any malformed entry gives an empty table (a larger scan, never a smaller one), and only the newest 1024 entries are kept. A destination base that is no longer a commit or an ancestor of the branch (history rewritten after the push, for example a rebase and a force-push from a terminal) is dropped when it is next used and that push scans from the workspace's recorded base instead (a larger range, `scanBase` in `handlers/git-common.ts`); only the recorded base can conflict. Still not covered: the gap between this read and the push (a drift item, see above).
- **Idempotency (decided).** A handler that throws frees the key; that is accepted. Commit and push are retry-safe (commit is pinned to the reviewed parent and a retry of one that landed is refused `head_moved` or `stale`; a push that went out and then failed is retried as a fresh tier 4 request and is a no-op push: same tip, no force), and both return normally once their side effect is known.
- **A blocked plan (ticket P1e).** The scan can block a push for one closed reason, `GIT_PUSH_BLOCKS`, the first that applies: `message_unscannable` (a commit message nothing can read, both modes), then in `refuse` mode `secrets_found`, `scan_incomplete` (too large to scan, or the scanner reported it could not cover the text: a `SecretScanError` other than `internal` becomes git-ops' `ScanIncomplete`) and `binary_unscanned` (a binary path not in `allowedBinaryPaths`). `pushPlan` asks git-ops for `reportBlocked` and RETURNS the plan with `blocked: { reason, binaryPaths, binaryPathsTruncated }`: the findings it already lists (rule, display path, line, commit), the unlisted binary paths through `toDisplayPath` (at most 50, the size of `allowedBinaryPaths`, so each can be allowed), `requiresConfirmation: false` and no reasons (a blocked plan cannot be confirmed; the contract refuses one that says otherwise). The client renders its own text from the closed reason. `push` refuses with `E_CONFLICT` and the same `details.reason` from the content hook, BEFORE a challenge exists and before the `plan_changed` comparison; `executePush` refuses a blocked plan again (git-ops throws `E_POLICY_DENIED` with the reason, which the host serves as `E_CONFLICT`, like `detached_head`). No matched text, label or raw path reaches the wire: only rule names, display paths and the closed reason. Warn mode is unchanged apart from `message_unscannable`, which blocks in both modes (it already refused in both) and now carries its reason. The listed paths are DISPLAY text: a path is copyable into `allowedBinaryPaths` only when it is not shortened (over 256 units) and holds no backslash, ellipsis, control or format character (all are escaped or cut), and more than 50 unlisted binary paths cannot all be allowed in one request (recorded, refuse mode only; a UI that must recover every path needs an opaque identity, not display text). **A name containing U+FFFD stays blocked even when it is in `allowedBinaryPaths`:** git-ops decodes names lossily, so distinct files (invalid bytes `0xff`, `0xfe`, or a real U+FFFD) share one string; no allow-list entry can name one of them, so none can waive them (the scanner is not told it is allowed either). Keep `message_unscannable` a blocked, never confirmable plan in warn mode too (native confirmation cannot establish what an unreadable message says). The block does not say which commits have an unreadable message (git-ops' text names them; the host forwards no text).
- **Drift (ticket P1e).** `createGitPort` wraps `assertNoDrift`: only a `DaemonError` whose `details.reason` is `git_drift` becomes `GitOpsError("E_CONFLICT", ..., { reason: "git_drift" })`, so `pushPlan` and `push` answer `E_CONFLICT` `git_drift` (listed in `GIT_PUSH_REFUSALS`; the client sends the user to the drift acknowledgement). Any other failure of the check stays `E_UNAVAILABLE`. `commit` runs the same check (git-ops `executeCommit`) before it commits, so `git_drift` is also in `GIT_COMMIT_REFUSALS.E_CONFLICT` (simplest truthful and fail-closed: the shared gate stays enforced and the closed set names what the wire can carry). When the scanner gives up, scanning stops at once (no later read, scan or message check), so a later failure cannot replace `scan_incomplete`; an unreadable message in a commit not yet read is then not reported, the plan is blocked either way.
- **Limitations (recorded).** (1) closed by P1e (above). (2) closed by P1e (above). (3) `detached_head` and `no_head` reach the wire under `E_CONFLICT` because a handler cannot raise `E_POLICY_DENIED`, while `GIT_COMMIT_REFUSALS` lists them under `E_POLICY_DENIED`; a client must accept the reason under either code. (4) `push` and `commit` serve READY workspaces only (kept). (5) An approved push scans three times under the mutex (hook at issue, hook at spend, `executePush`): kept, because each is an independent check of the confirmed plan; the cost is bounded.
- **Attribute reads (ticket REV2-FIX, REV-2 / G-27; HALF built: the git-ops primitive only).** `attributeReadGit(worktree, deps, { userAttributesFile?, indexFile? })` returns a daemon-hardened `git` over a PRIVATE, empty git directory (a temp directory with `HEAD`, `refs/`, and `objects/info/alternates` naming the real object store; for a linked worktree the store and `info/` of its `commondir`), so no repository config, driver or `info/attributes` of the real git directory is read. `info/attributes` is read ONCE as bytes through one open file (bounded to 1 MiB, a larger or non-file source is refused) and those exact bytes are both returned (`infoAttributesBytes`, with a UTF-8 view `infoAttributes` so the caller can refuse on any line) and copied into the private directory, which is what git reads: a write to the real file after the call, such as a swap that is later restored, changes nothing. `core.attributesFile` is pinned to a private copy of the file the caller names (empty when none: the user's XDG and configured files are not read), and `GIT_ATTR_NOSYSTEM=1` drops the system file. `HOME`, `XDG_CONFIG_HOME` (and `USERPROFILE` on Windows) point at an empty private directory, so the user's GLOBAL config (`diff.external`, `diff.<x>.textconv`, filters) is not found; the runner refuses `GIT_CONFIG_*`, so the SYSTEM config is still read and callers must pass `--no-ext-diff --no-textconv` on any diff. No `GIT_DIR`, `GIT_OBJECT_DIRECTORY` or other location variable is set (the runner refuses them): the location is `--git-dir`, the objects come through alternates. `dispose()` removes the directory; a failed setup removes it itself. Tests plant clean, smudge, textconv, `diff.external` and global-config filters with marker files, prove they run unprotected and not through this read, and fail on mutation (real git dir, no `GIT_ATTR_NOSYSTEM`, no `core.attributesFile` pin, no copy, `commondir` ignored, leaked directory).
  - **Not done / limits.** (1) `@axis/review` still calls `check-attr` on the real git directory; switching it (and reading refs there as object ids, since the private directory has none) is the remaining half, so RR-13 stays open. (2) The repository config is not read, so settings the reads depended on (`core.ignorecase`, sparse checkout) do not apply; a caller that needs one must pin it. (3) **The work tree's tracked `.gitattributes` files (nested, macros, `-diff`, `working-tree-encoding`, eol) are still read LIVE from the work tree** (or the `indexFile` the caller passes), so a write there between two calls changes the answer: only `info/attributes` and the user file are snapshotted, and the ticket's "cannot change what the scan and review see" does not yet hold for tracked files. The review-side switch must read them from a tree or index object or record the race. (4) A shallow or grafted repository has no `shallow` file in the private directory, so a walk past the boundary fails closed.
