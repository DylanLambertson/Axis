# `axis.git/1` handlers and the `GitOpsDeps` assembly (ticket H9)

- **Where.** `src/handlers/git*.ts` (`pushPlan`, `commit`, `push`, `compareUrl`, registered with `registerGitHandlers(registrar, deps)`, never the daemon) and `src/bindings/git.ts` (the only file that calls git-ops' operations, with `@axis/secret-scan` for the scanner type; `bindings/review.ts` and the port files import it as before). `createGitPort` builds `GitOpsDeps`: one runner that routes `daemon` to the node runner over the host's single `gitPath` and `pty` to the injected pty runner (absent, or an unknown context: `E_UNAVAILABLE`); the scanner is required and `scanner` and `scanMode` both come from it. `createGitOperations` refuses a port without a function scanner and a `refuse` or `warn` mode (the scan runs inside git-ops with that port, and git-ops finds nothing without a scanner), exposes the mode as `GitOperations.scanMode`, and `registerGitHandlers` refuses to register without it.
- **Derived, never sent.** Branch, base (what Axis last pushed to THAT remote, else the recorded base), worktree and remote URL come from the journal, the locator and the repository; the request names a workspace and a remote.
- **Commit.** Under the one project mutex: `expectedBranch` must equal the journal's branch, the reviewed tree must be one a `diff` of that workspace produced with the same parent and branch, then `prepareCommit` (the brand check; the handle is read by nothing before it), `handoff`, and `executeCommit` with `assertReviewFresh`. A refusal after `prepare` returned puts the person's index back, only while HEAD is still the reviewed commit and the index still holds what Axis staged (staging the person did since is kept). A refusal `prepareCommit` raises after its own `read-tree` leaves the reviewed tree staged (upstream: nothing to restore from). **Decision B2 (OPEN, ticket H9-hooks):** a bound commit runs no repository hook and nothing records "made without hooks". The design for the hook runner, the reply fields and the slices is `docs/design/daemon-host-hooks.md`.
- **Push.** The content hook asks the anchor first (a stalled anchor does no scan and issues no challenge), then plans under the mutex and uses the plan digest as the content digest; a plan that is not the request's `confirmedPlan` is `plan_changed` before a challenge exists. The handler pushes only the confirmed tip and records it as the last pushed sha; if that write fails the push still happened and the reply is the success.
- **Scan base per destination (S1).** The journal's `lastPushedSha` is per workspace but the destination is per request, so it is recorded (informational) and never used as a scan base. `PushedBases` is an in-memory, bounded table keyed by (workspace, SHA-256 of the sorted `git remote get-url --push --all` output) to the last pushed tip, so `pushurl` and `pushInsteadOf` count, a remote re-pointed after a push misses, two names for one URL share an entry, and no URL (userinfo) is ever stored. A destination with no entry (never pushed, evicted, or after a restart) is scanned from the workspace's recorded base, which is only ever a larger range. `allowedBinaryPaths` is per request, so a waiver never carries to another destination. Not covered: a path or ssh alias whose target changes behind an unchanged URL.
- **Idempotency (decided).** A handler that throws frees the key; that is accepted. Commit and push are retry-safe (commit is pinned to the reviewed parent and a retry of one that landed is refused `head_moved` or `stale`; a push that went out and then failed is retried as a fresh tier 4 request and is a no-op push: same tip, no force), and both return normally once their side effect is known.
- **A blocked plan (ticket P1e).** The scan can block a push for one closed reason, `GIT_PUSH_BLOCKS`, the first that applies: `message_unscannable` (a commit message nothing can read, both modes), then in `refuse` mode `secrets_found`, `scan_incomplete` (too large to scan, or the scanner reported it could not cover the text: a `SecretScanError` other than `internal` becomes git-ops' `ScanIncomplete`) and `binary_unscanned` (a binary path not in `allowedBinaryPaths`). `pushPlan` asks git-ops for `reportBlocked` and RETURNS the plan with `blocked: { reason, binaryPaths, binaryPathsTruncated }`: the findings it already lists (rule, display path, line, commit), the unlisted binary paths through `toDisplayPath` (at most 50, the size of `allowedBinaryPaths`, so each can be allowed), `requiresConfirmation: false` and no reasons (a blocked plan cannot be confirmed; the contract refuses one that says otherwise). The client renders its own text from the closed reason. `push` refuses with `E_CONFLICT` and the same `details.reason` from the content hook, BEFORE a challenge exists and before the `plan_changed` comparison; `executePush` refuses a blocked plan again (git-ops throws `E_POLICY_DENIED` with the reason, which the host serves as `E_CONFLICT`, like `detached_head`). No matched text, label or raw path reaches the wire: only rule names, display paths and the closed reason. Warn mode is unchanged apart from `message_unscannable`, which blocks in both modes (it already refused in both) and now carries its reason. The listed paths are DISPLAY text: a path is copyable into `allowedBinaryPaths` only when it is not shortened (over 256 units) and holds no backslash, ellipsis, control or format character (all are escaped or cut), and more than 50 unlisted binary paths cannot all be allowed in one request (recorded, refuse mode only; a UI that must recover every path needs an opaque identity, not display text). **A name containing U+FFFD stays blocked even when it is in `allowedBinaryPaths`:** git-ops decodes names lossily, so distinct files (invalid bytes `0xff`, `0xfe`, or a real U+FFFD) share one string; no allow-list entry can name one of them, so none can waive them (the scanner is not told it is allowed either). Keep `message_unscannable` a blocked, never confirmable plan in warn mode too (native confirmation cannot establish what an unreadable message says). The block does not say which commits have an unreadable message (git-ops' text names them; the host forwards no text).
- **Drift (ticket P1e).** `createGitPort` wraps `assertNoDrift`: only a `DaemonError` whose `details.reason` is `git_drift` becomes `GitOpsError("E_CONFLICT", ..., { reason: "git_drift" })`, so `pushPlan` and `push` answer `E_CONFLICT` `git_drift` (listed in `GIT_PUSH_REFUSALS`; the client sends the user to the drift acknowledgement). Any other failure of the check stays `E_UNAVAILABLE`. `commit` runs the same check (git-ops `executeCommit`) before it commits, so `git_drift` is also in `GIT_COMMIT_REFUSALS.E_CONFLICT` (simplest truthful and fail-closed: the shared gate stays enforced and the closed set names what the wire can carry). When the scanner gives up, scanning stops at once (no later read, scan or message check), so a later failure cannot replace `scan_incomplete`; an unreadable message in a commit not yet read is then not reported, the plan is blocked either way.
- **Limitations (recorded).** (1) closed by P1e (above). (2) closed by P1e (above). (3) `detached_head` and `no_head` reach the wire under `E_CONFLICT` because a handler cannot raise `E_POLICY_DENIED`, while `GIT_COMMIT_REFUSALS` lists them under `E_POLICY_DENIED`; a client must accept the reason under either code. (4) `push` and `commit` serve READY workspaces only (kept). (5) An approved push scans three times under the mutex (hook at issue, hook at spend, `executePush`): kept, because each is an independent check of the confirmed plan; the cost is bounded.
- **Attribute reads (ticket REV2-FIX, REV-2 / G-27; git-ops half).** `attributeReadGit(worktree, deps, { userAttributesFile?, indexFile? })` returns a daemon-hardened `git` over a PRIVATE, empty git directory (a temp directory with `HEAD`, `refs/`, and `objects/info/alternates` naming the real object store; for a linked worktree the store and `info/` of its `commondir`), so no repository config, driver or `info/attributes` of the real git directory is read. `info/attributes` is read ONCE (bounded to 1 MiB, a larger or non-file source is refused) and that text is both returned (`infoAttributes`, so the caller can refuse on any line) and copied into the private directory, which is what git reads: a write to the real file after the call, such as a swap that is later restored, changes nothing. `core.attributesFile` is pinned to a private copy of the file the caller names (empty when none: the user's XDG and configured files are not read), and `GIT_ATTR_NOSYSTEM=1` drops the system file. No `GIT_DIR`, `GIT_OBJECT_DIRECTORY` or other location variable is set (the runner refuses them): the location is `--git-dir`, the objects come through alternates. `dispose()` removes the directory; a failed setup removes it itself. Tests plant clean, smudge, textconv, `diff.external` and global-config filters with marker files, prove they run unprotected and not through this read, and fail on mutation (real git dir, no `GIT_ATTR_NOSYSTEM`, no `core.attributesFile` pin, no copy, `commondir` ignored, leaked directory).
  - **Not done / limits.** (1) `@axis/review` still calls `check-attr` on the real git directory; switching it (and reading refs there as object ids, since the private directory has none) is the remaining half, so RR-13 stays open. (2) The repository config is not read, so settings the reads depended on (`core.ignorecase`, sparse checkout) do not apply; a caller that needs one must pin it. (3) The work tree's tracked `.gitattributes` files are still read from the work tree (or the `indexFile` the caller passes); that source is the user's own file-system state, as for WT-2. (4) A shallow or grafted repository has no `shallow` file in the private directory, so a walk past the boundary fails closed.
