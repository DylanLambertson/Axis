# Tool broker core (`@axis/broker`)

- **Status:** Draft for the Phase 1b prerequisites of ROADMAP ticket 10. Pure TypeScript, `node:*`, `zod`, `@axis/protocol`, `@axis/audit`, `@axis/git-ops` and `@axis/pty-policy` only. No Electron, no worktree manager, no challenge manager, no provider or UI code.
- **Scope:** what a composer tool call may touch (paths, environment, processes, git) and the policy that decides whether it runs. Wiring to the daemon, `@axis/challenge` and `@axis/worktrees` comes later and goes through the injection points below.
- **Threat mapping:** WT-1, WT-2 (broker side), WT-3, GIT-ENV-1, PTY-2, PTY-4, ANT-2, DMN-2, DMN-3, DMN-5, DMN-6 (threat model Phase 1, controls file §Phase 1b gate lines 1b/L2 to 1b/L8).

## 1. Injection points

Everything outside pure computation is a port, so tests run without a worktree manager or Electron.

| Port | Provided by (later) | Used for |
|---|---|---|
| `WorktreeRegistry.get(id)` / `repositoryRoots()` | worktree manager (DMN-2) | The only source of roots. A request names a registered id, never a root. |
| `BrokerFs` | `nodeBrokerFs` here; tests wrap it to inject races | Realpath, lstat, open with `O_NOFOLLOW`, fstat, write. |
| `ApprovalHook.request(req)` | daemon adapter over `@axis/challenge` | Returns a grant bound to the call digest. |
| `AuditSink` (from `@axis/audit`) and `Redactor` | `AuditLog` and the vault-aware redactor | Every decision and run record. |
| `GitRunner` (from `@axis/git-ops`) and `assertNoDrift` | `createNodeRunner`, GIT-SNAP-1 | Broker-run git. |
| `EnvGrantSource.grantsFor(tool, worktreeId)` | vault (PRV-2, later) | Scoped secret grants for a child environment. |
| `Clock`, `SpawnPort` | tests | Expiry and process control. |

## 2. Modules

- `contain` (WT-1, DMN-2): `resolveInWorktree`, `readContained`, `writeContained`.
- `protectedPaths` (WT-3): `matchProtected` over folded path segments.
- `env` (PTY-2): `buildToolEnv`.
- `runner` (PTY-4): `createCommandRunner().run` and `killAll`.
- `git` (WT-2, GIT-ENV-1): `createBrokerGit`.
- `policy` (WT-3, DMN-3, ANT-2): `ToolPolicy.decide`, tiers, approval verification.
- `broker`: `ToolBroker.invoke` ties validation, containment, policy, approval and audit together.
- `audit`: `BrokerAudit` (redaction, fail-closed append) and `BROKER_PAYLOAD_ALLOWLIST` for `AuditLog` options.
- `errors`: `BrokerError` carrying only a closed `@axis/protocol` code, a fixed message and scalar details. It never carries `cause`, a path from the model, or a value.

## 3. Containment (WT-1)

1. **Lexical stage (pure, platform-parameterised).** The input is a bounded string with no NUL or control characters. Refused on every platform: any `..` segment, a backslash (except as a separator on win32), a drive prefix on non-win32, and on win32 UNC, device (`\\?\`, `\\.\`), drive-relative, `:` (alternate data streams), reserved device names, trailing dots or spaces and `~N` short names. An absolute path is accepted only when, after normalisation, it lies under the registered root (case-folded on win32 and darwin).
2. **Registry stage.** The root is looked up by id. At every use `realpath(root)` must equal the root recorded at registration (a worktree that is, or sits under, a symlink is refused, including a symlink into the local checkout), and must not be inside any `repositoryRoots()` entry.
3. **Real-path stage.** The real path of the target's parent (or the target itself for read) must be inside the real root, compared segment-wise, never by string prefix.
4. **Open stage.** Node has no `openat`, so the broker opens `<real parent>/<name>` with `O_NOFOLLOW` (final component), `O_NONBLOCK` (no FIFO hang), and without `O_TRUNC`. After the open it `fstat`s the descriptor and refuses anything but a regular file; compares dev and ino with an `lstat` taken before the open and with a second `lstat` and `realpath` of the parent after it; on Linux also reads `/proc/self/fd/N`. Any mismatch closes the descriptor and refuses before a byte is read or written. A write truncates (`ftruncate`) only after verification. Writes also refuse files with more than one link (a hard link planted from outside). Where `O_NOFOLLOW` does not exist (win32), the lstat and realpath re-verification is the only guard.
5. **Protected paths.** Root-anchored: `.github/` (all of it, since a local composite action runs in CI like a workflow), `.vscode/`, `.husky/`, `.githooks/`, `lefthook.yml|yaml`, `.pre-commit-config.yaml`, `.devcontainer/`, `.devcontainer.json`, `.gitmodules`. As a file name at any depth (the last path component only; a directory with that name is not it): `package.json`, `.npmrc`, `.envrc`, `.gitattributes`, `Makefile`, `GNUmakefile`, `justfile`, `.yarnrc*`, `.pnpmfile.cjs` and `*.code-workspace` (its `tasks` and `settings` sections equal `.vscode/`). `.git` matches at any segment. 8.3 short-name aliases are matched on win32 only. Other CI files (`.gitlab-ci.yml`, `.circleci/`, `Taskfile.yml`) are left to the host through `extraProtected`. This covers every file the threat model's WT-3 row names. The host adds more through `extraProtected`. Matching is on both the lexical and the real relative path (a symlink inside the tree to `.github/workflows` does not hide it).
6. **Use-time enforcement (WT-3).** The policy decision is made on the paths a call declares, resolved at that moment (`access`, lexical path, real path). The same call is then bound to them: every `readFile` or `writeFile` the tool makes must name a declared path (`undeclared-path` otherwise) and must still resolve to the same real path (`path-changed` otherwise), checked before anything is opened. After the open the descriptor must be that same real path (Linux: `/proc/self/fd`; elsewhere: the parent's real path, then the name's identity). The approval digest covers the access and real path of every target as well as the arguments, and the approval request shows them with a redacted, bounded preview of the arguments, so what the user approves is what runs. A directory swapped for a symlink to `.github/workflows` after the decision is therefore refused, not written.

Residual risks (documented, not closed): a create race can leave an *empty* file outside the tree if the parent is swapped between the check and an `O_CREAT`, but no bytes are written; reads through a hard link to an outside file are allowed (pnpm stores need them); a same-UID attacker with a process outside the broker can still race any user-space check on win32 and on darwin. On darwin `/proc/self/fd` does not exist, so only the parent's real path and the name's identity are checked after the open (in that order, so a swap undone between the two is still seen); a racer that swaps and restores faster than those two calls can still get one write outside the tree, or into a protected path inside it by hard-linking the created file back (the link count is read again after the last check, which narrows this). Neither platform has a descriptor path to compare. Node offers no `openat`, so this is the limit of user space; the OS sandbox (P3) is the real answer.

## 4. Environment (PTY-2)

Allow-list: `PATH`, `HOME`, `LANG`, `TERM`, plus names the tool declares (`envAdditions`) and fixed values it declares (`envFixed`). `PATH` is rewritten to absolute entries outside the worktree and any registered repository. Denied even when declared: `VSCODE_*`, `ELECTRON_*`, `AXIS_*`, `GIT_ASKPASS`, `SSH_ASKPASS*`, `SSH_AUTH_SOCK`, `GIT_EDITOR`, git redirectors and config injectors, loader and interpreter injection (`LD_*`, `DYLD_*`, `NODE_OPTIONS`, `BASH_ENV`, `ENV`, `PYTHONSTARTUP`, ...), and any secret-looking name (`*_TOKEN`, `*_KEY`, `*SECRET*`, `*PASSWORD*`). A scoped grant (`tool`, `worktreeId`, `name`, `value`, `expiresAt`) is the only way such a name appears; its value comes from the grant, never from the parent environment, and loader or interpreter injection and `VSCODE_*`/`ELECTRON_*`/`AXIS_*` names stay refused even with a grant.

## 5. Commands (PTY-4)

Argv only, `shell: false`, no option to turn a shell on. `argv[0]` is an absolute path or a bare name resolved by `resolveExecutable` (PATH only, never the cwd or worktree). Own process group on POSIX. Timeout and a combined stdout and stderr cap, both kill the group (SIGTERM, then SIGKILL after a grace). The run record states why it ended (`exit`, `signal`, `timeout`, `output-cap`, `aborted`, `spawn-error`). A concurrency slot is released only after the child's streams closed or were destroyed after the kill, never while work may still run. The runner installs no process-wide hook; the host calls `killAll()` at shutdown. Lingering group members after the main process exits are killed and counted. **A descendant that leaves the group (`setsid`, a daemon double-fork) is not killed and not counted:** user space cannot close that, the P3 OS sandbox does. Consequently a tool that starts a command cannot be registered below the approval floor (`register` refuses it), so a human has approved every command that could do this. **The launcher list in the policy is a deny-list, a convenience and not a boundary.** A match (`sh`, `env`, `python*`, `node`, `perl`, `find`, `make`, `git`, `npx`, `tar`, `vim`, `rsync`, `taskset`, `setarch`, the dynamic loader `ld.so` and `ld-linux*` ...) adds the `launcher` reason and raises the call to `privileged`. A wrapper, editor or toolchain program that is not on the list runs at the tool's own tier, and the list can never be complete: the approval, and the tier, are the gate.

**Binding to the decision.** `ctx.run` and `ctx.git` exist for every tool but work only for what the tool declared and the policy judged. What is guaranteed:
- **One snapshot.** The tool definition is copied and frozen at `register`, and every declared target, argv and git call is read once and copied at the decision. `ctx.run` and `ctx.git` read the tool's call object once, at the call, before anything else happens. The check and the execution use that copy, so a tool that changes its object (or a getter that answers differently) afterwards cannot start something else.
- **The program is pinned by file, not by name.** `ctx.run` needs `command` (or `argv`, the whole command line, which the approval shows and which must match exactly). The program is found when the policy decides (a bare name on the tool's PATH outside the worktree and every repository; an absolute path by its real path, which is also what is started) and the approval and the digest name its real path. What is recorded is its identity: `dev:ino`, size, modification time and change time. At the time of use the program is resolved again and must have the same path and the same identity, or the call is refused with `program-changed`: a file renamed over it, a copy put in its place, an edit in place and a retargeted symlink all change it. A script is judged by its `#!` interpreter: the interpreter's real path is judged as a launcher (a script run by a shell is `privileged`) and is pinned the same way. One level is followed. A script whose `#!` line cannot be read (mode 0111 hides it from us, and the kernel still runs it), a script whose interpreter is itself a script, and a file that neither starts with `#!` nor with a header the loader accepts on this platform (a checked ELF header on Linux, Mach-O or fat on macOS, PE on Windows; a text file with a magic prefix is refused by the kernel and `/bin/sh` runs it, and so is a `#!` line whose path the kernel cuts at 256 bytes), cannot be judged here: they are treated as launchers (`privileged`, reason `opaque-program`). **Coarse-timestamp residual:** kernel timestamps advance in ticks of a few milliseconds and a deleted file's inode number can be reused at once, so two different files that have the same inode number, the same size and were written within the same tick are indistinguishable by identity. A file deleted and recreated at the same size within one tick is therefore not seen (the same holds for the identity compare in section 3). The tests never rely on this: they keep the old file linked, or wait past a tick, before they create its replacement. A bare name is started by the path that was found, not by its real path, because a multi-call binary reads its own name. The identity is compared just before the spawn; Node offers no `fexecve`, so a same-user process that swaps the file between that comparison and the exec can still win (the OS sandbox, P3, closes this).
- **What the approval shows.** With `argv`, the whole command line as a JSON array (so `["echo","a b","c"]` and `["echo","a","b c"]` differ), with every control character, U+2028/2029, bidirectional control and invisible format character (zero-width space, joiners, the BOM, tag characters) written as a `\uXXXX` escape, and the program and interpreter paths quoted; git calls are shown the same way. With only `command`, the program and its resolved path, and the reason `args-at-run-time`: the arguments are chosen when it runs and the approval cannot show them. Prefer `argv`.
- **Git.** `ctx.git` needs `git: (args) => GitCall[]`; the call must be one of them (compared by a key over command, flags, revisions and paths), its own tier raises the decision (a worktree-rewriting `restore` is destructive and always asks, whatever the floor), and its paths are shown and protected-path checked. `git add` of the whole tree (`.`) always asks; a named directory is checked lexically only, because staging is not a write to the tree and the commit stays with the reviewed tree.

What is not guaranteed:
- What a started command does to files: the approval is the only gate, and P3 is the answer.
- The arguments of a `command`-only tool, and any launcher that is not on the list.
- The working directory and the standard input of a run: they are not part of the approved line.
- The timeout and the output cap of a run: the tool chooses them, they are not part of the approved line.
- Code the program loads from outside the tree (libraries, plug-ins, user configuration in the home directory).
- Repeated runs: one approval allows `ctx.run` to start the approved line any number of times during that call.
- Anything the program reads from the tree: a started program reads its own configuration (a `.npmrc`, a `Makefile`, a `pyproject.toml`), and the protected set covers only the files named in section 4.
- A shebang interpreter that is neither a launcher nor changed: it runs as approved, and its own behaviour is not judged. Only one level of `#!` is followed (see above).

A tool that declared neither a command nor git gets neither.

## 6. Git (WT-2 broker side, GIT-ENV-1)

Subcommands come from a fixed table (`status`, `diff`, `log`, `show`, `ls-files`, `add`, `restore`), each with an exact flag allow-list. The argv is `prefix()` from `@axis/git-ops` in the daemon context (explicit `--git-dir` and `--work-tree`, `core.hooksPath` off, `core.fsmonitor=false`, filters neutralised, no transport), plus `--literal-pathspecs`, `--no-ext-diff` and `--no-textconv` where they apply, then the subcommand and flags, then revisions after `--end-of-options`, then paths after `--`. Environment is `daemonGitEnv` (GIT-ENV-1). `assertNoDrift` runs before every call and after every writing call; drift fails closed (`E_CONFLICT`). Commit and push are not broker tools: they stay with `@axis/git-ops` (daemon-orchestrated, reviewed tree).

## 7. Policy and approvals (WT-3, DMN-3, ANT-2)

Tiers: `read` < `write` < `network` < `destructive` < `privileged`. A tool declares one tier. Unknown tool names, tiers that are not one of the five strings (including numbers, `NaN`, `undefined`), invalid arguments and a tier raised by the injected override to something invalid all **deny**. Default approval floor is `network`; the floor itself is validated the same way. Protected paths force approval for any write and for any access to a Git directory path, whatever the floor. An absolute `argv[0]` is judged by its real path and refused inside the worktree or a repository. A shell or launcher in `argv[0]` (`sh`, `bash`, `env`, `xargs`, `sudo`, `cmd`, `powershell`, ...) raises a command to `privileged`.

The approval hook receives the tool, tier, reasons, the real paths with their access, a redacted preview of the arguments (bounded, with a truncation flag) and a digest of the canonical call. A call is read once into locals at entry; its abort signal is checked before the decision is recorded, raced against the approval (a hook that ignores it cannot start a cancelled call) and checked before every file, command and git operation. Its answer is validated with a strict schema: approved, `approvedBy: "user"` (an `agent:*` approver is refused), the same digest, an `approvalId`, an expiry in the future and within a bound. A rejected, malformed, expired, mismatched, replayed (`approvalId` seen before) or timed-out answer, or a throwing hook, denies. The model never receives a way to resolve its own approval.

## 8. Audit (DMN-5, DMN-6)

Each call writes `broker.decision` before it runs (a failed append stops the call) and `broker.result` after (a failed append is reported with `executed: true`). Payloads and targets pass through the injected `Redactor` first; the sink may redact again. Paths appear only as worktree-relative text, output only as length and hash. Payload keys are listed in `BROKER_PAYLOAD_ALLOWLIST`, to be merged into the `AuditLog` options.

## 9. Not in this package

Composer, provider calls, UI, daemon/challenge/worktrees integration, vault, network egress policy, `mkdir -p`, rename and delete tools, commit and push.
