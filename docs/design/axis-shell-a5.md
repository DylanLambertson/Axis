# Shell A5: the Changes view

Task A5 of `axis-agent-shell.md` §8.1 (design in §4.3 and the reveal routing in §3.4). The workspace view gets a Changes list under its Files tree. It lists the focused worktree's conflicts, staged, not staged and untracked files from the workbench `IGitService` state, and opens a file's diff, or every listed file in one multi-diff, in IDE view through `IAxisViewService.reveal`. Axis adds no write action to it, no upstream patch and no git process path, and changes no daemon contract (what the upstream editors it opens can do is under Limits).

## What it reads, and how

- **Reads only.** `AxisChangesSource` (`services/changes/common/axisChangesSource.ts`) reads `IGitService.repositories`, calls `IGitService.openRepository` under the rules below, and follows the repository's observable `state`. It calls nothing else on the service or the repository: no `commitFiles`, no `diffBetweenWithStats`, no `getRefs`, no `updateState`. The git extension, which is the service's delegate, runs git as it does for the SCM view; Axis starts no process.
- **It opens as little as it can.** The git extension's public `openRepository` (`extensions/git/src/api/api1.ts`) opens with `openIfClosed` and `openIfParent` on: it would silently open a parent repository (whatever `git.openRepositoryInParentFolders` says), reopen a repository the user closed in the SCM view, and each call replaces the repository object other readers of `IGitService` follow. So:
  1. A repository `IGitService.repositories` already has for exactly this root (compared as upstream does, case-insensitively where the file system usually is) is followed and never reopened.
  2. Otherwise the root is opened only if it is inside the window's folders (so the git extension never asks to trust a folder outside the window) and is a repository root git will not walk up from (`isRepositoryRoot`, checked with `IFileService`): its `.git` is a file (a linked worktree's pointer) or a directory with what git's `is_git_directory` needs: a `HEAD` file and the `objects` and `refs` directories. An empty or half-deleted `.git` directory (even one with `HEAD` left) does not count, because `git rev-parse --show-toplevel` would resolve a parent repository and the git extension would open it. A `.git` file that points nowhere makes git fail rather than walk up. This is a check of the folder's shape, not of a working repository: git itself decides the rest.
  3. If the user has closed repositories in the git extension (its `git.closedRepositoryCount` context key is above 0), or that is not known yet (the key is unset until the git extension has activated and scanned, for example while a restored window starts), a root the service does not have is not opened automatically: the list says so and offers "Show changes". When the key changes, the list looks again, and opens the root by itself once the key says no repository is closed. Opening a closed repository through the public API also deletes it from the git extension's persisted closed list (`model.ts`, `closedRepositories` in workspace state), so the user's "Close Repository" would be undone for later sessions too; the user decides. `IGitService.repositories` holds only repositories opened through it, so while any repository is closed, every worktree asks once per window session, including ones the user never closed; and if the git extension is off, the key is never set and the list always asks.
  4. A root is opened at most once: one found unavailable stays so on every later workspace list update and revisit (no "Reading…" flash, no `git rev-parse` per update), until the window's folders change or the user presses "Try again".
  - Residual: when no repository is closed, the first look at a root the git extension has not opened (beyond its scan depth, for example) opens it, which the extension would do itself for a root at the top of the window. `IGitService` gives no list of closed repositories, so the closed count is the signal.
- **A replaced repository is found again.** The service never drops a repository, but another `openRepository` for the same root replaces the object Axis follows. On the next `setRoot` for the same root the source checks the object is still listed and, if not, follows the new one. A repository the user closes in SCM stays listed by the service (there is no close path in `IGitService`), so the list keeps showing its last state until the folders change; that is a stated limit.
- **Phase 0 folders.** The window's folder does not follow the focused workspace yet (task A2's folder manager), so for other worktrees the list says "Changes show for the folder this window has open"; it looks again when the window's folders change.
- **The repository must be the worktree.** A repository rooted anywhere else is not shown: the list says "Git has no repository for this worktree" and lists nothing.
- **A late answer is dropped.** Every open has a generation; a reply for a worktree the user has already left is ignored, so one workspace's changes never show under another's name. Switching worktrees stops listening to the old repository.

## The model

`readChanges(state, root)` in `services/changes/common/axisChanges.ts` turns the state into groups in the order the user needs them: Conflicts (`mergeChanges`), Staged (`indexChanges`), Not staged (`workingTreeChanges`), Untracked (`untrackedChanges`). A file staged and changed again is in both Staged and Not staged. Each group is in path order, sorted before it is cut to 500 rows; the rest are counted and the note sends the user to the SCM view. The kind of a staged or not-staged change comes from which sides it has (no original: added; no modified: deleted; two different paths: renamed; otherwise modified), as the delegate maps them (`extHostGitExtensionService.ts` `toGitChangeDto`).

A change is dropped, and counted in a note, if any of its URIs is not a `file:` URI strictly inside the worktree root (after `.` and `..` are resolved). So no diff is built for a file the view was not asked about.

### Diff sides

The diff sides are the ones the SCM view uses (`extensions/git/src/repository.ts` `getLeftResource` and `getRightResource`), as `git:` URIs in the git extension's own shape (`toGitUri`: the path, and a JSON query with `path` and `ref`), which its existing content provider serves:

| Group | Left | Right |
|---|---|---|
| Staged | `HEAD` (none for an added file) | the index (`ref` `''`; none for a deleted file) |
| Not staged | the index (`ref` `~`) | the file itself (none for a deleted file) |
| Untracked, Conflicts | none | the file itself |

## Opening, through `reveal`

`IAxisRevealTarget` (now in `services/view/common/axisRevealInput.ts`) is a file, a diff or a multi-diff, and `editorInputForReveal` builds the untyped editor input; `reveal` then applies the view mode as before (§3.4: switch to IDE view per workspace or globally, or open in the IDE half in split mode) and opens it.

- **A row** opens its diff (`diffTargetOf`). With two sides it is a diff editor with no selection, so `TextDiffEditor` reveals the first change ("at the change"). With one side (added, untracked, deleted, conflict) it opens that side at line 1. The tab title is `diffLabelOf`: the cleaned name and the fixed group text, for example `app.ts (Staged)`, never a path.
- **Review all** opens every listed row in one multi-diff editor (`reviewAllTargetOf`, "Changes in ws-a" with the workspace name cleaned). Each item's "open file" goes to the worktree file. It is transient, so a reload does not restore a stale list.
- The editors are pinned and reuse an open one (`revealIfOpened`). The view never calls `IEditorService` itself.

## Accessibility and text

- The list is a `listbox` with one `group` per state (named by its heading, "Staged · 2") holding `option` rows, with a roving tab stop: Up, Down, Home, End, Page Up and Page Down move; Enter, Space or a click opens. The focused row is kept by id across updates, so a refresh from git does not move focus to another file.
- **State is never colour alone.** Each row shows a letter in a box and a word (`M Modified`, `A Added`, `D Deleted`, `R Renamed`, `U Untracked`, `! Conflict`) before the name; colour (the theme's git decoration colours) only supports them, and a deleted name is also struck through. A rename shows "from <old path>" after the folder.
- **The accessible name puts fixed text first:** "Modified, Staged: app.ts, in src", or "…, at the worktree root", plus ", renamed from <path>". The state and group come from the group and the URI sides, never from the name, so a file called `Staged, Modified: spoof.ts` reads "Untracked, Untracked: Staged, Modified: spoof.ts, at the worktree root".
- **Hostile names.** Every name, folder and previous path passes `cleanDisplayText` (control characters including newline, format and bidi controls, zero-width characters, line and paragraph separators, private-use and unassigned code points, and letters that draw nothing (Hangul fillers, the blank Braille pattern) become U+FFFD; runs of combining marks are cut to two) and is clamped on code points (120 for a name, 240 for a folder) with an ellipsis. The view sets every text with `textContent` and has no HTML sink; the name and folder cells also use `unicode-bidi: isolate`, so right-to-left text in a name cannot reorder the state cell. The row's hover title is the cleaned folder and name. The file the editor opens is the real URI from git, not the cleaned text.
- **Focus.** Updates are keyed and in place (`placeInOrder`): a row keeps its element while its file stays listed, an unchanged row is not redrawn, rows and groups that left are removed before anything is inserted, and nodes move only when the order changes, so a git update that removes or adds files around the focused row neither blurs nor re-announces it (a reorder that moves the focused row itself does), and the element the view service remembers when a diff opens is still there on the way back. The workspace view returns focus to the Changes list when it held focus last. After an update (`focusAfterUpdate`): focus outside the view is never taken; focus on another control ("Review all", "Try again") stays there and is never moved onto a row; a focused row stays on its file (`nextActiveIndex`), else on the row now in its place; and focus that would be lost (the list emptied, the focused control hidden or disabled, the worktree gone) goes to the "Changes" heading (`tabindex=-1`, always shown), never to the page body.
- **Contrast.** "Review all" and "Try again" use `.axis-button`, whose border is `input.border` (3:1 or more on every pane in both Axis themes, checked in `test/theme-axis/contrast.test.mjs`, which also checks the CSS uses that token). The git decoration colours are mapped to the status tokens and checked at 4.5:1 on every pane and on a hovered or selected row. A focused list shows the active selection colour and a 2 px ring; in forced colours the selected row has a `Highlight` outline and buttons a `ButtonBorder` edge.
- The summary line ("2 files: Staged 1, Untracked 2"; a file in two groups counts once) and the notes (loading, not mounted, unavailable, rows not listed, changes outside the worktree) are plain text.

## Limits (Phase 0)

- **What the upstream editors do.** The diff and multi-diff editors are upstream: the diff editor carries the git extension's own title actions (Stage, Unstage, Revert Selected Ranges), and its description, hover and breadcrumbs show the raw path (Axis cleans only its own surfaces). An untracked symlink row opens the link's target. Escaping paths in the upstream editors, refusing symlinks that leave the worktree and validating `reveal` targets are Phase 1b items (threat model).
- The git extension waits for a repository's `HEAD` before answering, with no time limit, so a stuck repository shows "Reading…" until "Try again" or a folder change.

- Changes "since base" (`diffBetweenWithStats(baseSha, 'HEAD')`) and the dashboard's Changes column are Phase 1 (§4.3, §4.2): this view reads only the working state.
- No accept, reject, stage or commit: those are daemon actions (§5.4, `axis.git/1`), never the renderer.
- Only the worktree the window has open is listed (see above).

## Manual test on a fixture repository

1. `scripts/code-oss/changes-fixture.sh <dir>` (a path without spaces, on Linux or macOS). It makes `<dir>/changes-repo` with every kind of change and the hostile names above, and `<dir>/conflict`, a worktree with a merge conflict.
2. Build and start Axis as in `axis-shell-runbook.md`, with `<dir>/changes-repo` as the window's folder. Trust the folder (the git extension does not run in Restricted Mode).
3. In Agent view, focus the local checkout. The Changes list shows Staged (`docs/new.md` A, `lib/renamed.ts` R "from src/old.ts", `src/app.ts` M, `src/gone.ts` D), Not staged (`README.md` M, `src/app.ts` M, `test/a.test.ts` D) and Untracked (eight files). The hostile names show U+FFFD where the newline, override, zero-width and escape characters were; no row is split or reordered; the long name ends with an ellipsis; `Staged, Modified: spoof.ts` is a `U Untracked` row.
4. Keyboard: Tab into the list, move with the arrow keys, Home, End, Page Up and Page Down; a screen reader reads "Untracked, Untracked: …" for each row, and the group names.
5. Enter on `README.md` (Not staged): IDE view opens a diff of the index against the file, scrolled to the first change. Back in Agent view, Enter on `src/app.ts` under Staged: `HEAD` against the index. `docs/new.md` and the untracked files open as files; `src/gone.ts` opens its `HEAD` version.
6. Review all: one multi-diff "Changes in changes-repo" with every listed file.
7. Edit a file in a terminal: the list updates without moving focus off the selected row.
8. Open `<dir>/conflict` as the window's folder: `src/shared.ts` is listed under Conflicts. Focus a workspace whose folder is not open: the list says changes show for the folder the window has open, and the SCM view does not gain a repository. Delete `.git` from a copy of a worktree inside the window and focus it: the list says Git has no repository for it and no parent repository appears in SCM.
9. In split mode, a row opens the diff in the IDE half without switching view.
