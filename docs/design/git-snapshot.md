# Git snapshot (`@axis/git-snapshot`)

> Phase 1a · design for GIT-SNAP-1, WT-2 (CLI side) and WT-3 highlighting. WT-4 (one branch and worktree per workspace, base SHA recorded) is the worktree manager's; nothing here addresses it. Source of the requirements: `docs/ROADMAP.md` (Phase 1a gate), `docs/design/axis-agent-shell-policies.md` §6.4, threat model rows WT-2, WT-3, GIT-SNAP-1, GIT-4 and gaps G-3 to G-6.

## 1. Scope

A package of pure logic over two directory paths: a worktree and its `$GIT_COMMON_DIR`. It reads files, never writes, and does not depend on the worktree manager. It runs `git` only for read-only questions (`config --list --show-origin -z`, `rev-parse`), with the GIT-ENV-1 environment from `@axis/pty-policy` (no caller `GIT_*`, no system or user config, discovery capped at the worktree). `git` is started by absolute path only, found by `@axis/pty-policy`'s `resolveExecutable` (absolute `PATH` entries only: no empty, relative, UNC or root-relative entry; `.exe` and `.com` on Windows), never inside a worktree (the ones the caller names and every checkout the repository lists under `worktrees/*/gitdir`), with a neutral working directory and `-C <worktree>`. The host should resolve it once at start, with every registered worktree excluded, and pass `gitPath`; without it the package resolves once per distinct `PATH` for the process, and again only when the cached `git` has vanished (ENOENT) or has come to sit inside a worktree, so a `git` dropped into an earlier `PATH` directory later is not picked up. `safe.directory` is passed, for exactly the worktree, common dir and git dir (never `*`), on the read-only calls, so a repository git calls "dubious ownership" is still read; nothing is read from the user's config, and these calls run no code from the repository. The time budget and the abort signal reach the process, its output is bounded by `Limits`, and a config file over the size limit is not handed to git to list (the snapshot is blocking-incomplete). Only settings git read from a file are listed: values git reports from `-c` (the snapshot's own `core.fsmonitor=false`) are not the repository's. The daemon decides **when** to take a snapshot (worktree creation, before and after a CLI run, before commit and push, on status refresh) and **where** to keep it (the journal). This package supplies:

1. `takeSnapshot` / `takeStableSnapshot`: the GIT-SNAP-1 set, with bounded memory and time.
2. `diffSnapshots`: a structured before/after diff for display, redacted.
3. `judgeDrift` / `acknowledgeDrift`: the verdict that Axis commit and push consult.
4. `classifyPath` / `classifyPathResolved`: the WT-3 protected-path matcher.

Not in this package: snapshot refs (`refs/axis/runbase|backup|archive`), their retention (policies §7) and the push-side refusal. The snapshot only **observes** `refs/axis/*`; creating, expiring and never pushing them belongs to the snapshot-refs ticket and to `@axis/git-ops`.

## 2. What is read

| Group | Items | Blocks commit and push |
|---|---|---|
| config | `$GIT_COMMON_DIR/config`, `config.worktree` (main and `worktrees/*`), and every file reached by `include.path` / `includeIf.*.path` (all conditions assumed true) | yes |
| hooks | every file under `$GIT_COMMON_DIR/hooks`, subdirectories included (a dispatcher such as `pre-commit.d/*`): type, mode, SHA-256, text | yes |
| in-tree hooks | the target of every `core.hooksPath` value (relative values resolve against the worktree, so an in-worktree directory is hashed, recursively and bounded), plus `.husky/`, `.githooks/`, `lefthook*.y(a)ml` and `.pre-commit-config.yaml` of the worktree | yes |
| attributes | `info/attributes`, `info/exclude`, and the targets of `core.attributesFile` / `core.excludesFile` | yes |
| link | the worktree `.git` file, `worktrees/*/gitdir`, `worktrees/*/commondir`, and, when the caller passes the journal's git dir, a mismatch check | yes; a mismatch is **refused**, not acknowledgeable |
| settings | parsed from the config files above: `core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `url.*.insteadOf`, `remote.*.url`/`pushurl`, `credential.*`, `filter.*`, `diff.*`, `merge.*`, `alias.*`, `protocol.*`, `include*`, `gpg.*`, `http.*` and others (see `settings.ts`). Derived from the file contents, so they add no digest input of their own | via the files |
| refs | `refs/axis/*` from loose refs and `packed-refs` | no (notice only: Axis itself writes them) |

Global and system config, the home directory and submodule git dirs (`modules/*`) are not read (ADR 0004 states the first two; the third is an open question).

**What decides what is hashed comes from git, not from this package's parser.** Git reports every config entry with its origin file (includes followed), the hook directory it will use (`rev-parse --git-path hooks`) and where the worktree really points: discovery from inside it (git dir, common dir and top level, with no `--work-tree`), compared with the journal's git dir, the common dir and the worktree path. A top level that is not the worktree (`core.worktree` in `config.worktree`) means hooks run elsewhere and is refused. Relative hook paths are resolved against git's top level. The package's own git-config parser is a second opinion, run over the bytes (latin1 view) of every file git read: if it rejects a line, or disagrees with git on any file, the snapshot is blocking-incomplete and can never read as clean. The parser also finds include files git did not read (missing, or an `includeIf` that is false today); they are hashed so their appearance shows. Settings and hook targets come from git's list only, so a `core.hooksPath` inside an `includeIf` that is false today is not walked until the condition becomes true (the next snapshot then sees the change); the files themselves are hashed either way. Paths that are not valid UTF-8 (a config value, a directory name) are reported unread and block; they are never decoded lossily.

## 3. Snapshot

Plain JSON (layout version 2; an older stored snapshot is refused): `{ version, takenAtMs, worktreePath, commonDir, entries[], settings[], incomplete[] }`. An entry holds `state` (`file`, `dir`, `symlink`, `missing`, `other`, `unreadable`, `oversize`, `unstable`), mode, size, SHA-256, symlink target, and the **redacted** text (first 16 KiB, text only). Raw text is never kept: URLs with credentials, authorization headers, token shapes and secret-named assignments are replaced using the `@axis/audit` redactor plus config-aware rules (credentials also hide in `url.<base>.insteadOf` subsections). The hash is of the raw bytes, so a rotated secret still shows as "changed" without showing either value.

The digest covers the blocking entries only (id, state, mode, size, hash, link target), never timestamps or text.

**Bounds** (`Limits`, all overridable): 4096 entries, 4 MiB parsed per config file, 16 MiB hashed per file, 128 MiB read in total, 16 KiB text per entry, 10 s wall clock, include depth 10 and 64 include files, and an `AbortSignal`. Exceeding a bound (including more recognised settings than the list holds, which is decided after path settings are resolved by key), an unreadable item, or a file that changes while read (size, mtime and ctime are compared around the read; two retries) makes the snapshot **incomplete**: it names the item, and no verdict over it can be acknowledged. Nothing is silently skipped.

`takeStableSnapshot` takes two snapshots and returns the first only if the digests agree (three attempts), so a re-take before commit or push is not a mix of two states. It does not remove the race with a writer that is still running: the daemon refuses commit and push while a CLI run is active (policies §6.1).

## 4. Diff

`diffSnapshots(before, after)` returns `changes[]` (added, removed, modified, mode or type change, became incomplete) with a flag label, a blocking bit, redacted before and after views and a bounded line delta, `settingChanges[]` (key-level, for the flags such as "core.hooksPath set to a path inside the worktree"), and `flags[]` for the dashboard row. Flags for the settings that decide what git runs (hooks path, fsmonitor, ssh command, includes, credentials, URL rewrites, remotes, filters, and any link mismatch or unread item) have their own slots: a flood of lesser changes cannot push them out. Control characters and bidirectional or invisible format characters are escaped; counts and sizes are capped. Output is checked in tests for planted secrets.

## 5. Verdict

`judgeDrift({ baseline, current, acknowledgement })` returns one of:

- `clean`: digests equal. No flag.
- `acknowledged`: differs, but the user acknowledged exactly this digest. Allowed.
- `unacknowledged`: differs. Not allowed; carries the diff.
- `refused`: incomplete snapshot (either side) or a worktree-link mismatch. Not allowed, and `acknowledgeDrift` throws `E_POLICY_DENIED` for it. `assertDriftAllowed` throws a fixed message with counts; names and paths stay in the structured verdict.

An acknowledgement binds the digest of the state the user reviewed, so any further change invalidates it. Because legitimate git use also edits `config` (for example setting an upstream), the daemon re-baselines after its own operations; any other config churn needs one acknowledgement. Persisted snapshots are re-validated with `parseSnapshot` (zod) before use.

## 6. Protected paths (WT-3)

`classifyPath(relPath)` is lexical and `classifyPathResolved(root, relPath)` also follows symlinks (hop-limited, dangling links included) and reports a path whose resolution lands in a protected path, or outside the root. Matching is case-insensitive on every platform (a false highlight is harmless; a miss on a case-insensitive volume is not), compares after Unicode NFKC normalisation and an upper-then-lower case fold (dotless i, Kelvin sign), ignores HFS+ ignorable code points, NTFS trailing dots and spaces, alternate data streams and `NAME~1` short names (including a dash, as in `PRE-CO~1.YAM`), and accepts `\` as a separator. The list is data (and a caller can add paths with `extraPaths`; product-specific tool directories belong in the caller's configuration, not in this list): `.github/workflows/` and `.github/actions/`, `.vscode/`, `.devcontainer*`, `.husky/`, `.githooks/`, `lefthook*`, `.pre-commit-config.yaml`, CI configs (GitLab, CircleCI, Azure, Jenkins, Travis, Buildkite, Drone, Bitbucket, AppVeyor), Dockerfile-likes and compose files, `package.json`, `conftest.py`, `build.rs`, `pyproject.toml`, `.npmrc` and the other package-manager rc files, `.envrc`, `.env` and `.env.*`, `Makefile`, `.gitmodules`, `.gitattributes`, and any `.git` component at any depth. Hard links are not detectable by path.

## 7. Open questions

- Submodule git dirs (`$GIT_COMMON_DIR/modules/*`) carry their own hooks and config; they are not in the ADR 0004 set and are left out.
- **Decided: no product or tool name is built in.** The owner's rule keeps tool names out of tracked files, and no tracked file names such a path. The gap is closed by generic rules, judged after the specific categories above (so those keep their own category), at any depth, with the same case, normalisation, NTFS and 8.3 handling. `hidden-config` (high) is any path with a component that starts with a dot (a dot-directory and everything under it, or a hidden file) and any component that looks like a generated short name (`ALPHA~1`, which may stand for a dot name). Ignore and style files are reviewable, not exempt: `.gitignore`, `.dockerignore`, `.prettierignore` and `.eslintignore` are `ignore-rules` and `.editorconfig` is `hidden-config`, both of medium severity, and only when the exact final name is that file (`.gitignore/x` is high). A run that adds a config file and an ignore rule for it therefore still shows a change; the host must list changes with ignored files included (for example `git status --ignored`) for any path this classifier marks, because the classifier itself never reads ignore rules. Version-manager files (`.nvmrc`, `.node-version`) are hidden-config like any other dot name. `instruction-file` (high) is a `.md` file whose first segment is upper-case (`NAME.md`, `NAME.local.md`, `NAME.override.md`) at any depth, except common project documents (README, LICENSE, LICENCE, COPYING, NOTICE, CHANGELOG, CONTRIBUTING, SECURITY, CODE_OF_CONDUCT, AUTHORS, MAINTAINERS, CODEOWNERS, SUPPORT, GOVERNANCE, TODO, HISTORY, RELEASE and a few more); and, at the root only, any plain `*.md` name in any case, since a lower-case spelling is the same file on a case-insensitive volume. Below the root lower-case documents (`docs/design.md`, `a.b.md`) are not marked, which leaves a lower-case spelling of an upper-case instruction file below the root unmarked on a case-insensitive volume. The names a particular product reads (its own folders and files) are the host's: it reads them from the user's own settings (application or machine scope, never from the repository, never a tracked file) and passes them as `extraPaths`, which adds the category `caller-defined` with the same matching rules. `.env` and `.env.*` are `shell-env` (they carry secrets) and `.npmrc` stays `package-config` (registries and tokens).
- Known limit: the time a snapshot takes grows faster than the number of worktrees (sibling scan: about 5.6 s at 100 worktrees, 10 to 14 s at 200, 35 s at 300, as measured by the review), so roughly 200 or more registered worktrees in one repository are refused for time. This fails closed. Follow-up: make the sibling scan incremental (read only entries whose directory changed since the last snapshot).
- A repository with more config entries than the snapshot lists (16,384 by default, mostly thousands of tracked branches) is refused with the reason stated, until the limit is raised.
- `credential.helper` values that carry a secret inside a file path are not redacted (the value is a command line).
- Another worktree's creation changes `worktrees/*` and so counts as drift for every workspace in the repository until the daemon re-baselines; the worktree manager should re-baseline all workspaces of a repository after `worktree add`.
- With a very large config line (hundreds of MB), the `rev-parse` calls read the config too, so a snapshot can use its whole time budget before it fails closed. The size check stops only the listing. Not fixed: the result is a blocking-incomplete snapshot, never a clean one.
- A host must resolve `git` once, with every managed worktree excluded, and pass the same absolute `gitPath` to this package and to the Axis commit and push code. Without it each package resolves on its own and their defaults can differ (one may accept a `git` in a sibling worktree the other refuses).
- Content of the repository's own files (a `gitdir` file that names `/.git`, a path that is not text) never makes `takeSnapshot` throw: the snapshot comes back refused or blocking-incomplete. Argument mistakes by the caller still throw (`E_INVALID_ARGUMENT`); a host must treat any rejection as "not clean" in every case.
- The number of entries in `worktrees/` is capped by the `maxWorktrees` limit (1024), and the reason says so.
- **Index flags (decided: detected).** `git update-index --skip-worktree` and `--assume-unchanged` make git stop looking at a tracked file, so an edit to it appears in neither `git status` nor `git diff`; the flags live in the index, which is not hashed. The snapshot reads them from `git ls-files -v -z` as a stream (bounded by `maxIndexBytes` (512 MiB), the time budget and a record length, so a large repository is not held in memory). EVERY flagged path is hashed into the entry `index/flags`, with its flag and the file's identity in the worktree (size, mtime, mode, or absent), so setting a flag, moving it to another file, or editing a flagged file changes the digest and reads as drift, even when the count does not change. The entry's text shows only the first flagged paths within the text bound (and the total), so a saved snapshot always loads. A flagged path that the protected-path matcher marks is also a setting of its own (label `index flag hides changes`, high severity, a critical flag in the diff); the others, which sparse checkouts set legitimately, are counted in one medium setting. git prints a file with both flags as assume-unchanged. If git cannot list them, or the listing is over the byte limit or the time budget, the snapshot is blocking-incomplete. Known limit: each flagged path costs a path classification and a `lstat` (about 25 µs and a few µs); about a million flagged files do not fit the 10 s default budget, and the snapshot then fails closed. Limits that stay: git's own status uses a timestamp cache (a change that keeps size and mtime, or a repository with `core.trustctime=false`, may be missed by `git status`), which this package does not replace.
- A host that lists a run's changes should use `git status --porcelain=v2 --untracked-files=all --ignored=matching` so that untracked and ignored files are shown, and read the flagged files from the `index/flags` entry, since status cannot show them.
- The broker package keeps its own protected-path list; this package's matcher and that list are separate and are not kept in step by code.
