# `axis.messages/1`: the protocol contract (PV-M1)

- **Status:** Built (ticket PV-M1) and **served** since PV-M3 slice 1: the contract and its rows moved to the served tables together with the handlers (section 8). Section 1 describes the planned stage it went through.
- **Design:** `docs/design/inter-agent-communication.md` (sections 2, 4, 7, 8), `docs/design/inter-agent-cli-endpoint.md` (sections 4, 5).
- **Code:** `packages/protocol/src/messages.ts` (methods), `packages/protocol/src/messages-wire.ts` (ids, records, escaping, refusals), `packages/daemon-host/src/policy/rules.ts` (rows), `packages/daemon-host/src/policy/coverage.ts` (the check), `packages/daemon-host/src/messages/` and `src/handlers/messages.ts` (the service), `packages/journal/src/message-store.ts` (schema version 9).

## 1. Planned, then served

`@axis/protocol` has a second table, `plannedContracts`, next to `contracts`. `lookupMethod` reads only `contracts`, so a planned method cannot be called by a client or served by a daemon: the envelope answers `E_METHOD_NOT_FOUND` as for any unknown method. The daemon-host coverage check holds the two tables together:

- every method of a planned contract has exactly one row in `PLANNED_RULES`, at the contract's tier;
- a planned row for anything that is not a planned method fails;
- a key in both the served and the planned registry, or in both rule tables, fails;
- `policySurface(ids)` filters the planned registry with the planned rows, so a host configured without `axis.messages` drops both.

`RuleTablePolicy` is built from `RULES` only, so planned rows are never served: the rows were written and reviewed first, and PV-M3 moved them. Adding the contract to `contracts` without handlers would fail host startup (the handler coverage check), which is why the contract is planned.

## 2. Methods

| Method | Side effect | Tier | Idempotency | What it does |
|---|---|---|---|---|
| `send` | write | 2 | required | A new thread (no `threadId`) or a post into one |
| `thread` | read | 1 | none | One thread's messages visible to the caller, after a cursor |
| `threads` | read | 0 | none | The caller's threads, most recent first; `projectId` is a filter, never authority |
| `read` | read | 1 | none | The caller's inbox: unread messages addressed to it (the `read_messages` tool and the CLI endpoint's read) |
| `markRead` | write | 1 | none | The caller's own read cursor of one thread; never moves back |
| `pause`, `resume` | write | 2 | none | The kill switch for a project, a group or an agent |
| `settings` | read | 0 | none | A project's messaging settings |
| `updateSettings` | write | 2 | none | One setting per call (cross-group, a group pair, scan mode, retention, accepts-from, CLI messaging, mute) |

**Deviation from the ticket:** the ticket names one `settings` method. Reading settings is a read and changing them is a tier 2 user write, and one method cannot be both, so the contract has `settings` (read) and `updateSettings` (write). Each update names one setting so the `message.settings` audit row records exactly one before and after.

Content reads (`thread`, `read`) are tier 1, as `axis.review/1.diff` is: they return bodies and excerpts copied from worktrees. Nothing is tier 3 or above, so no request takes an `approval`.

## 3. What no field can carry

No request or response field, at any depth, names an approval, a challenge, a digest, a grant, a token, a capability, a credential, a command, a tool or an actor; the test walks every schema's JSON form and fails on such a name (the secret-scan mode `secretScan` is the one allow-listed setting name). Every field the daemon fills (`messageId` of a new message, `projectId`, `seq`, `sender`, `hop`, `createdAt`, the expanded recipients) is absent from every request, so the strict schemas refuse it. Bodies have one format, `text`; there is no Markdown or HTML format.

## 4. Ids

Thread and message ids are `thr_` or `msg_` followed by 16 random bytes as unpadded base64url (22 characters, the last one of `A`, `Q`, `g`, `w`, so the encoding is canonical). `encodeMessagingId(kind, bytes)` is the one encoding; it throws unless it gets exactly 16 bytes. The daemon passes `randomBytes(16)`. The prefix only keeps the kinds apart; ids carry no order, time, project or sender.

## 5. Visibility and `not_found`

The contract comments state the rule of `inter-agent-communication.md` section 4.2: participant sets, participant-only reads, posting needs participation and every recipient passes the send policy at accept and at delivery, the user reads every thread. The contract's part of "no existence oracle" is that a refusal's `details` is exactly `{ reason }` from a closed set, with the fixed message `MESSAGES_REFUSAL_MESSAGE`: a `not_found` cannot carry an id, a count or text that would tell a hidden thread from a missing one. The same holds for `recipient_refused`, which answers both an unknown and a disallowed recipient. The service makes the two refusals structurally identical (section 8).

| Code | Reasons |
|---|---|
| `E_NOT_FOUND` | `not_found` |
| `E_INVALID_ARGUMENT` | `too_large`, `too_many_recipients` |
| `E_CONFLICT` | `recipient_refused`, `cross_project` (user only), `paused`, `hop_limit`, `secret_found`, `excerpt_path_refused`, `bypass_entry`; for enabling CLI messaging (section 14), also `wrapper_unparsed`, `config_unparsed`, `too_many_repo_files`, `empty_argv` |
| `E_BACKPRESSURE` | `rate_limited`, `queue_full` |

PV-M1 put the policy refusals under `E_POLICY_DENIED`. A handler cannot raise that code (the daemon answers `E_INTERNAL` for it, because only its pipeline decides it, with its own audit row), so PV-M3 moved them to `E_CONFLICT`, as `axis.review/1` and `axis.git/1` answer their packages' policy refusals. The daemon's error filter now lets `E_BACKPRESSURE` carry `reason`, so `rate_limited` and `queue_full` stay apart on the wire.

## 6. Bounds and display text

- **Request body:** 1 to 16,384 UTF-16 units, well-formed (no lone surrogate). Control and bidi characters are accepted in: the daemon stores the text and escapes it on every way out.
- **Response text:** `toMessageText` escapes every control character except tab and newline (so CR, ESC and C1 are out), bidi, zero-width, the invisible set and lone surrogates as `\u{hex}`, and the backslash as `\\`, so a typed escape cannot pass for a real one. The response schemas refuse anything unescaped. An escaped body is at most 8 times the request cap and is never cut; an excerpt is cut at 65,536 units with `truncated`. Paths are `toDisplayPath` text (at most 512); a raw path is never echoed.
- **Recipients** 1 to 16 (unique), and 16 after group expansion; **refs** at most 16, of which at most 4 excerpts of at most 2,000 lines; **participants** of a thread at most 64 (a send past it is `too_many_recipients`); **hop** 0 to 8, and 0 for a user message.
- **Replies:** `thread` and `read` return at most 32 messages and 204,800 units of body, excerpt and display-path text (`MAX_READ_TEXT`, exactly one message at its largest, so a reader always makes progress); `threads` returns at most 32 threads. These caps are set so the worst reply passes the protocol's message walk (1 MiB, 10,000 values) with 16 KiB and 64 values left for the envelope: the test builds it with every id, plugin id and path at its schema maximum, every list at its cap and 3-byte text, and fails if it does not fit. 50 messages at 262,144 units, or 50 threads of 64 participants, did not fit. The design's 256 KiB read cap is a ceiling; this one is lower and counted in UTF-16 units.
- **Cursor:** the `thread` reply's `nextSeq` is the last returned message's `seq`, or `min(afterSeq, lastSeq)` when nothing is returned, so a cursor past the end gets an empty reply, not an error.

## 8. As served (PV-M3 slice 1)

- **Who.** The bridge serves the user's own connection: the rows admit `user` only, every handler refuses any other actor again with `not_found`, and no row is in `WEB_ALLOWED`. The service (`createMessageService`, `createMessagingSettings`) takes an attested `MessageCaller` (`user`, or an agent or plugin with its run's received hop) from its binding, never from a payload, and parses every request with the contract's schema itself, so the broker (PV-M4) and the endpoint (PV-M6) cannot pass an unchecked one.
- **Directory.** Agents and groups are the journal's (PV-G3 slice 2, `packages/daemon-host/src/agents/directory.ts`): live agents only (an archived agent is unknown: neither addressable nor delivered to, and its queued messages wait for a restore), each group expanded to its live members in id order (at most `MAX_SETTINGS_AGENTS`), every answer read at the moment it is asked. The host's `agentOf` is the run's recorded agent (`agent_runs.agent_id`); no run records one until PV-G4 starts runs from an agent, so delivery and the composer tools stay inert until then.
- **Project of a thread.** From the thread; for a new thread the attested sender's own project for an agent, and the one project of every named agent and group for the user (a send to the user alone, from the user, is refused; recipients that span projects are `cross_project` to the user). A plugin cannot open a thread.
- **Policy at accept.** Every expanded recipient, participant or not, passes section 4.1 (`mayAddress`: own group, `crossGroup` or a pair, the recipient's `acceptsFrom`, never itself, never another project); one refused principal refuses the whole send. Groups expand at accept, without the sender, and the expansion is recorded. A post into a thread needs participation (the user may post into any thread and joins it); new recipients join with `joinedSeq` = the thread's last seq. `inReplyTo` must be a message of that thread the sender can read. `deliverable(messageId, principal)` is slice 2's hook: it runs the policy and Pause again with the settings of the moment, for a principal the message was addressed to.
- **No existence oracle.** Every method that names a thread resolves it on one path. For any caller but the user that is ONE participant-scoped lookup (the thread joined with the caller's participation), so an unknown and a hidden thread are the same miss, refused with the same audit row and the same error. The claim is structural identity, not equal latency; the test compares the sequence of store and audit calls of both cases. A late joiner's summary still shows the thread's `lastSeq` and its participants: the size of the history it cannot read is visible, not its content.
- **Hop.** 0 for the user; for an agent or plugin one past the larger of the hop its run received and the hop of the message it replies to; past `MAX_TAINT_HOP`, or a received hop that is not an integer in range, is `hop_limit`. Slice 1 records no hop when an agent reads: slice 2's taint producer must raise the run's received hop on every `thread` and `read` result and every delivery, or a sender could reset the hop by posting without `inReplyTo`.
- **Body.** Stored as the sender wrote it (raw, bounded by the request schema) and escaped with `toMessageText` on every way out, in one place (`messages/wire.ts`); a file ref leaves only as `toDisplayPath` text. Excerpt refs are refused (`excerpt_path_refused`) until the excerpt slice builds the containment and path refusals. The body is secret-scanned before accept (`refuse`; `warn` only when every recipient is a composer agent or the user, M-6; a scan that cannot finish refuses).
- **Limits** (`DEFAULT_MESSAGING_LIMITS`, design section 7): per agent or plugin sender 30 sends a minute and 500 per run, 300 per project and minute, 60 reads a minute per agent or plugin caller (`rate_limited`); per recipient 200 unread messages from agents and plugins, 50 of them from one sender (`queue_full`, refused, never dropped; the user's messages never count and are never refused for a full queue; the user's own inbox is a recipient like any other, so agents' messages to the user share its 200, at most 50 from one agent, which bounds what any flood can hold); 2,000 messages per thread (`too_large`: start a new thread; nothing is archived), 10,000 threads per project (`queue_full`), 64 participants (`too_many_recipients`). The user is not rate limited (the daemon's connection limits bound it). Until delivery exists, the queue is a recipient's unread messages (after its read cursor). Every counter is bounded (4,096 keys; a new key past it is refused while all are live).
- **Audit** (`MESSAGES_PAYLOAD_ALLOWLIST`): `message.send`, `message.send.refused`, `message.read.refused`, `message.settings` (one setting, before and after), `message.pause`, `message.resume`, with ids, kinds, counts and closed reasons only, never text. A `rate_limited` refusal is recorded once per caller and minute. `bodyMac` is not written: no hash of a body is recorded until the per-install key's storage is decided.
- **Settings.** Held in the journal (`messaging_settings`, `messaging_agent_settings`), user only; an unknown project, group or agent is `not_found`. Enabling an endpoint (`cliMessaging: true`) passes the enable rule of section 14 first, else it is `bypass_entry`.
- **Ids.** `encodeMessagingId` over 16 bytes of the daemon's `randomBytes` for every thread and message. `send` answers `replayed: false`; a retry with the same key gets the stored result from the daemon's durable idempotency store.
- **Journal** (schema version 9, forward-only, pinned by hash): `message_threads`, `message_participants` (join only, at most 64), `agent_messages` (never changed; the next seq of its thread, by trigger), `message_recipients`, `message_cursors` (never back) and the two settings tables.

## 9. Delivery into runs (PV-M3 slice 2)

- **Where.** `packages/daemon-host/src/messages/delivery.ts`, called by the agent binding's `deliver` tool hook, which the composer loop asks at each turn boundary: after a turn's tool results and drift notice, never inside a tool call, never into the first prompt (no wake, design section 6.4), never when no further turn follows and never once the run is cancelled. A run of no agent gets nothing: PV-G4 records a run's agent (and must then also check that the run's project is the agent's), and until then the host's `agentOf` knows none, so nothing is delivered in production. Only a RUNNING run is delivered to; an agent the directory no longer knows (archived) gets nothing and its messages stay queued.
- **Re-checked at delivery.** A waiting message is delivered only while the recipient is a participant of its thread and `deliverable` still allows it under the settings of this moment (send policy, `acceptsFrom`, Pause of the sender's or the recipient's scope); otherwise it stays queued. The pipeline pages past refused messages with a keyset cursor in send order (up to 1,024 a boundary), so refused messages cannot hold back later ones (review 1 SF1). The hop needs no check here: the journal refuses a hop above `MAX_TAINT_HOP`. Mute does not stop delivery: the design defines it as hiding an agent from the attention block only (section 10, the contract's `muted` field; confirmed in review 1).
- **Taint first.** Per message, in one journal transaction: the lease, then for a sender other than the user (an agent, a CLI endpoint sender, a plugin) the run's `RunTaint.receive` with source `message`, the sender kind (`cli` for an unverified sender or a CLI agent), the sender's name cut to 64 characters, the message's hop and its id as `ref`, then `message.deliver` (message, thread, run, agent, channel `composer-turn`, sender kind, hop). `receive` records `composer_runs.tainted` and `message.taint` in the same transaction. If that fails, the run is tainted in memory, the block is withheld, the leases this boundary took are released, the failure is counted and the loop ends the run `FAILED` / `DELIVERY_FAILED`. After 3 failures for one recipient the message is quarantined (`failed`, never offered again), `message.deliver.failed` is written and Axis posts a system message to the user in the thread, so one message cannot end every run of an agent. The count is committed on its own before the quarantine and the notice (a notice that cannot be posted still leaves the message quarantined and audited), and a check that throws on corrupt stored state (the message, its participation, the project's settings) is counted against that message and the candidate skipped, without ending the run. A message from the user is never counted for a failing check: it stays queued and is looked at again at every boundary, so a fault of Axis (a corrupt settings row fails every check of its project) cannot set the user's own words aside; messages from other senders, and a message whose record cannot be read (its sender is then unknown), are counted and quarantined as above. After 3 failed checks of a user message since host start Axis tells the user, in its thread, that it is held by an error in Axis and stays queued: one notice per message whatever the number of recipients, naming none (the agents in the thread read it too); none when Axis already replied to that message, so a restart does not repeat it; a notice that cannot be posted is tried again at the next failed check. The counts are in memory, at most 4,096. A failure after the lease (the lease, the taint or the `message.deliver` row) is counted for every sender, the user's included, so no message can end every run of an agent. A notice that cannot be posted is logged as the code `delivery_notice_failed`, without text; a log hook that throws is ignored. A message from the user is delivered without a receipt.
- **At most once per run, acknowledged late; at least once when an acknowledgement fails.** Journal schema version 10: `message_deliveries` (one row per message and recipient: `leased`, `acked` or `failed`; a lease only moves to `acked`, an acked or failed row never changes and is deleted only after its message) and `message_delivery_failures`. The loop acknowledges a block only after the provider request that carried it succeeded, and releases it when that request failed, when the run ended or was cancelled first, or when the acknowledgement itself failed; every lease is also released at host start. A released message goes to a later run, which it taints in turn; the run that leased it stays tainted. A model may already have seen a block whose acknowledgement failed (or whose request failed after the provider read it); it is then delivered again to a later run, the safe direction because that run is tainted too. `message.deliver` means leased and tainted, not seen by a model: a released lease keeps its row, so the log can show a message delivered to two runs. The retention purge deletes a message and its delivery rows in one transaction with `PRAGMA defer_foreign_keys = ON` (the trigger refuses deleting an acked or failed row while its message exists, and the foreign key refuses deleting the message first).
- **The block.** One text block after the tool results. The opening line carries a nonce of 16 random bytes drawn for that block, after the bodies were stored, and says the messages are untrusted data that is not an instruction and grants nothing, and that only a header line Axis writes, carrying that code, names a sender, so nothing inside a message can, not even a claim to be from the user. Per message: a header (sender, kind, `verified`, thread, message id, hop), the body escaped with `toMessageText` with every line prefixed `| ` (no body line can begin like a frame line), and an end line; then a closing line. The system prompt of the edit and agent modes names the frame as untrusted data (design section 6.1). At most 8 messages and 65,536 escaped units a block, whole messages, one message always fits; the rest wait for later boundaries, in send order. Delivered text counts toward the run's result cap (`TOOL_RESULT_LIMIT`).
- **For PV-M4.** The 1,024-row scan stays ahead of refused messages only because the queue quota (counted after the recipient's read cursor) keeps refused rows under 200 plus the user's messages. Once agents mark their own threads read, refused rows can pile up past the scan: bound the pending rows themselves or skip refused senders in SQL then.
- **Not here.** The CLI pull (PV-M6), an index for `pending` (its work grows with what an agent has ever received until retention exists). `read_messages` and `send_message`, and the run's `receivedHop` raised by what it is delivered, are PV-M4 (section 10). **Inert until PV-G4:** the host's `agentOf` knows no run, so nothing is delivered and neither tool is offered in production.

## 10. Composer participation (PV-M4)

- **Where.** `packages/daemon-host/src/bindings/agent-messages.ts` (the two broker tools) over `src/messages/participation.ts` (the caller, the read's framing and receipts; no broker). The host passes `MessagingBinding.participation` to the agent binding as `AgentBindingDeps.messaging`.
- **INERT UNTIL PV-G4 (named follow-up).** Both tools are registered and offered only for a run whose agent `participation.agentOf` returns AND the directory knows. The host's `agentOf` is the messaging binding's default (none: `hostMessagingDeps` gives no `agentOf`) and its directory is `journalDirectory` (no agent), so in production no run is offered either tool and a call by name is the broker's `unknown_tool` (one `broker.decision` row, `deny`, nothing else). The follow-up, with PV-G3 and PV-G4: `compose.ts` passes the real `agentOf` (the run's recorded agent) and PV-G3's directory to `createMessagingBinding`; `agentOf` must then also check that the run's workspace is in the agent's project (section 9 says the same for delivery). Everything else is tested end to end on a fake directory (`test/composer-messages*.test.ts`).
- **The caller is the run's.** `{ kind: "agent", agentId, runId, verified: true, receivedHop }`: the agent fixed when the run's tools are built, the run's id, and the run's received hop. The tools' argument schemas are strict (`send_message { recipients, body, threadId?, inReplyTo? }`, `read_messages { threadId?, afterSeq?, limit? }`): a model field naming a sender, an agent, a project, a run, a hop or `verified` is `invalid_args` and nothing is sent. The service re-parses every request with the contract's schema and runs the whole send policy (section 8), so a send's project is the agent's, and posting and reading are participant-only. File and excerpt refs are not offered (excerpts are refused by the service until their slice; taint source 3 has no producer yet).
- **Tiers.** `read_messages` is `read`. `send_message` is `write` (section 6.5 of the design: it changes Axis state): allowed without asking in an untainted run (the broker's floor is `network`), and a tainted run's send waits for the user's approval, whose card's content is `To: ...`, `Thread: ...`, the reply target and the whole body, with the taint sources. The card's head holds 2,048 escaped units (`MAX_PREVIEW_HEAD`): a send whose card would be cut there, or whose text a scan finding hides, is REFUSED before any card is shown, with its own reason `body_not_reviewable` (the `broker.decision` row is `deny` with reason `body-not-reviewable`, not a user's decline), so the user never approves a message they were shown only part of (review 1 B1). The tool's description tells the model the limit. The generic card cap is not raised. An untainted run's send is not asked and may use the full 16,384 units.
- **Received hop (design section 7.3).** One per run, in the binding, for the run's life (a run does not survive a restart, so it is never resumed with a lower hop). Every taint receipt raises it BEFORE the run is tainted: a delivered message (source 1, so a relay through delivery is now bounded by hop), each message of a read from an agent, a plugin or a CLI sender (source 2), and a test source. A hop that is not an integer from 0 to 8 raises it to 8, refusing every later send (`hop_limit`). A send's hop is `max(receivedHop, inReplyTo's hop) + 1`, refused past 8 (`hop_limit`) after the user's approval if the run is tainted.
- **Taint source 2.** Each message in a read whose sender is an agent, a plugin or a CLI sender is one receipt (`read_messages`, the sender kind, its bounded name, the hop, the message id) taken through the run's `RunTaint` before the result is returned, so a later call of the same model reply is decided tainted. A receipt that cannot be recorded leaves the run tainted, withholds the result and ends the run `FAILED`. A message from the user or from Axis is not a source.
- **What the model gets** (ADR 0007 decisions 6 and 7.6: one escaping path, every body line prefixed, a line ends only at a line feed, a body line that already starts with `| ` is prefixed again). A read is framed exactly like a delivery block (`framed` in `delivery.ts`): an opening line `[axis-read <nonce>]` with the untrusted-data label and a nonce of 16 random bytes drawn for that result, per message a header Axis writes (sender, kind, `verified`, thread, message id, seq, hop, reply target), the body as the service escaped it (`toMessageText`) with every line prefixed `| `, an end line, and a closing line. Pages follow the service's caps (32 messages, `MAX_READ_TEXT`); a cut page says more follow. A body the providers' outgoing check would refuse (the host redactor would change it: a registered secret) is replaced by a fixed note and still taints, so no read result carries a secret. A send answers with the new message's id, thread, seq, hop and recipient count. A refusal reaches the model as the service's closed reason (`queue_full`, `rate_limited`, `hop_limit`, `secret_found`, `not_found`, ...) and the broker records the call as failed.
- **Outgoing scan and quotas.** The body of a send is scanned by the service at accept with the host's scanner (`refuse`; `warn` only when every recipient is a composer agent or the user, M-6); the per-sender limits of section 8 (sends per minute and per run, a sender's queue at a recipient, reads per minute) apply to the run's agent as to any agent caller.
- **Residuals.** The secret check of a read and of a delivery now covers each body's stored raw text as well as its escaped text (section 11, closing review 1 N2). A delivered block is checked the same way, so a delivered secret no longer ends the run at the providers' check. `read_messages` does not mark messages read, so the inbox form shows the same unread messages until the user or a later ticket moves the cursor; the section 9 note on the delivery scan applies once agents mark their own threads read.

## 11. Secret check on the raw body (built)

**The gap (section 10, Residuals; PV-M4 review 1 N2).** A read's secret check (`holdsSecret`, the providers' outgoing check over the host redactor) ran on the body as `toMessageText` escaped it, and the providers' check sees that same escaped text. A registered secret that holds a control, bidi, zero-width or invisible character appears only escaped (`\u{hex}`), which neither check matches, so it could reach the model, reversibly escaped. (A backslash was never a gap: the redactor already registers each secret's JSON-escaped form, which writes a backslash as `\\` too; the tests pin that case all the same.) A delivered block (section 9) had the same gap, and more: it was not checked at all before the providers' check, which then failed the run.

**Rule.** A body is withheld (the fixed note, the message still taints and still raises the hop) when the host redactor's check matches EITHER the stored raw text OR the escaped display text. The raw text catches a secret that escaping would split; the escaped text is what actually leaves, so it is checked too. Both are bounded (raw at most 16,384 units, escaped at most 8 times that) and the check is windowed like the providers' (`providerRedactor.containsSecret`), so a secret is never split between two windows.

**Where the raw text is checked, without exposing it to participation.** The raw body never leaves the message service and the delivery pipeline, which already hold it (`MessageRecord.body`); composer participation (`messages/participation.ts`) keeps receiving escaped wire messages only.

- **Reads.** A new service method for broker callers, `readWithheld(caller, req, holdsSecret)`, does exactly what `read` does (same parse, rate limit, participant scoping, paging and audit) and, while it holds each record, evaluates `holdsSecret(raw) || holdsSecret(escaped)`; it returns the `read` reply plus `withheld`, the SET OF MESSAGE IDS whose body must not be shown. No text, length or position crosses: the participation layer replaces those bodies with the fixed note. The predicate is the agent binding's own (built from the host redactor in `bindings/agent.ts`, as `holdsSecret` is today), never a caller's. The bridge's `read` (the user) is unchanged: the user's own window shows bodies escaped, as M-11 decides.
- **Deliveries.** `delivery.ts` already reads the raw record per candidate; it gains the same predicate (`MessageDeliveryDeps.holdsSecret`, required, so a host that forgets it does not build) and withholds a matching body in the block the same way. This also closes section 10's delivery residual: a delivered secret no longer ends the run at the providers' check.
- **Not chosen.** Unescaping the display text before the check (the escaping is reversible) would work for the backslash and `\u{...}` forms but duplicates the escaper's grammar in a second place; adding a `withheld` field to the wire schema would change the served contract (`axis.messages/1`) for a broker-only concern.

**Tests to build (each failing on mutation).** Registered secrets holding a backslash, a control character (BEL), a bidi override and a zero-width joiner: through `read_messages` and through delivery, the body is withheld and the message still taints; the same secret without such a character is still withheld (both checks run); a mutant checking only the escaped text, one checking only the raw text with a secret written as a literal `\u{7}`, and one passing raw text to participation are killed (a runtime test pins that `readWithheld` returns only `messages`, `more` and `withheld`, the reply carries only escaped text and the predicate saw the raw text inside the service); a predicate that throws fails closed (a read shows nothing of the message; a delivery releases this call's leases, counts the failure and fails the run); the user's bridge `read` is unchanged. The `message.deliver` row carries `withheld` (a boolean, never text), so an operator can tell a withheld delivery from a shown one.

**Residual.** Each body is judged alone, against the registered forms: a secret split across two messages, or broken up by characters a sender inserts (an invisible character between its letters, not part of the registered form), is matched by neither check.

**Size.** One small slice in `packages/daemon-host` (service method, delivery dep, participation and binding wiring, tests); no journal or protocol change.

## 12. The CLI endpoint relay, daemon side (PV-M6 slice 1)

- **Where.** `packages/daemon-host/src/messages/endpoint.ts` (`createEndpointRelay`, built by the messaging binding as `endpoints.relay`); the relay envelope (`relayInbound`, `relayOutbound`) is on the pty control channel (`packages/pty-process/src/messages.ts`, exported through `@axis/pty-process/client`). The pty process side (the listener, framing, peer checks, the spawn's `messagesEndpoint` request) is slice 2; the `axis-messages` shim is PV-M7. Until slice 2 the relay is driven only by tests.
- **INERT UNTIL PV-G4 (named follow-up).** `mint(runId)` gives an endpoint only to a RUNNING run whose agent `agentOf` returns, that the directory knows as a CLI agent, and whose `cliMessaging` setting is on, and never on Windows (ADR 0007 validation 3). The host gives no `agentOf`, its directory knows no agent, and `updateSettings` refused `cliMessaging: true` until PV-M7 slice 1 (section 14), which now decides it; nothing is minted in production unless `messaging.enabled` and `messaging.cliEndpoint` are both on (both default false). With PV-G4, compose passes the real `agentOf` and the run start (slice 2) mints and hands the endpoint to the spawn.
- **Endpoint and token.** One per run; the id is derived from the run id (`ep_` and the SHA-256 of a fixed prefix and the run id), so the daemon maps an endpoint to its run itself; the id is not a secret (anyone who knows the run id can compute it), the token is (review s1 N1). The token is 32 random bytes (base64url), held only as its SHA-256 and compared in constant time against the SHA-256 of what the frame carries; it is never in the journal, the audit log or a log (a test dumps every journal table to check).
- **The relay is untrusted (ADR 0007 decision 7.1).** `onRelay(source, message)` ignores anything not marked with the supervised channel's symbol (the pty binding is its only holder). It refuses a frame for an endpoint id the daemon did not mint, a revoked endpoint, a run that is not RUNNING (and revokes it: `endpoint-close`), a connection that was not opened, was closed or failed its `auth`, a second `auth` on any connection, and a fifth connection; at most 4 requests of one endpoint are in flight (the fifth is `busy`). A frame is JSON text of at most 64 KiB and depth 32, parsed by a strict schema (`auth { token }`, `send { id, recipients, body, threadId?, inReplyTo? }`, `read { id, threadId?, afterSeq?, limit? }`); anything else is `invalid` and closes the connection. The first frame must be `auth`.
- **Bounded for the daemon's lifetime (review s1 SF).** A revoked endpoint is removed from the table, its token buffer wiped; what remains is a tombstone (id and run) in a ring of the last 256 revocations, so a late frame answers `revoked` and the run is not minted again; past the ring a late frame gets the answer for an unknown id (`refused`). At most 256 live endpoints.
- **The caller** is the binding's: `{ kind: "agent", agentId, runId, verified: false, receivedHop }`, never a frame's (a frame naming a sender, an agent, a run, a project, a hop or `verified` is `invalid`). Every endpoint message is therefore stored unverified and taints the composers that receive it (section 9).
- **Received hop (ADR 0007 decision 5).** Per endpoint (one per run), across all threads: each read raises it to the highest hop it returns, and nothing lowers it; a send carries it plus one and stops at 8 (`hop_limit`).
- **Answers.** Through the message service (its policy, limits and audit), escaped there (`toMessageText`); a read uses `readWithheld` (section 11), so a body whose raw or escaped text holds a registered secret is replaced by the fixed note. A reply names the sender by its bounded label (`senderLabel`), with `verified`. Reads are limited to 60 a minute per endpoint, besides the service's per-caller limit. Refusals carry the service's closed reason, `invalid`, `failed` (never an error's text), `paused` (Pause of the agent's scope, checked at every request) or `revoked`.
- **Audit.** `message.endpoint` rows: `minted`, `revoked`, and token failures as ONE aggregated row per endpoint and minute (`failures`, `firstAt`, `lastAt`), written when the next minute's first failure arrives, at revocation or at `flush()`; the reply to a failed `auth` sets `authFailed` so the pty process can back off per peer (slice 2).
- **Built in slice 2 (section 13):** revocation when the run's process exits (no longer only at the next relayed message), the transport bounds including the 2 s pre-authentication bound (review s1 N2) and `flush()` at shutdown (review s1 N3). **Built in slice 3:** revocation at a settings change and closing open connections on Pause (below). **Still not here:** a send already in flight when the run ends, or when the worker's messaging is turned off, completes and is stored (review s1 N4, review s3 SF1): it passed the checks before it awaited the secret scan, and only a pause is re-checked inside the send's transaction. The bound is one send per connection in flight (at most 4 per endpoint), each at most one scan long; its reply is dropped, the endpoint being gone; revoking when the worker is archived (its runs end, and the exit revokes); `messaging.enabled` is a composition option, fixed for the daemon's lifetime.
- **Slice 3: settings change and Pause.** `updateSettings` turning a worker's `cliMessaging` from on to off, and a `pause` that changed the state, call the settings service's `onChange` after the change committed; a hook that throws is audited (`message.endpoint`, event `hook_failed`) and never fails the user's write. The binding fans the event out to the wired relay (only with `messaging.enabled` and `messaging.cliEndpoint`). Off: `revokeWorker` revokes every live endpoint of that worker (tombstone, audit `revoked`, `endpoint-close`), and the pty process removes every connection, lingering ones included, the listener and the socket file. Backstop: every relayed open and frame re-reads the stored setting, so a write that reached no hook still revokes at the next message, and any message for a revoked endpoint is answered with `endpoint-close` again (idempotent), so a pty process that missed the first close stops listening (review s3 N1). A hook that throws and an audit sink that throws while recording it still leave the committed write a success (review s3 N2). Pause: `dropPaused(projectId)` sends `endpoint-drop` (reason `paused`) for each live endpoint with connections whose sender the committed settings now pause (the policy's `senderPaused`, so worker, group and project scopes match it exactly), audits `paused` with the count, and forgets those connections; the pty process destroys every connection of that endpoint (`relay-close` each) and every lingering one, and KEEPS the listener, so a resume needs nothing: a new connection may authenticate, and while paused its requests answer `paused` and close. `endpoint-close` now carries only `revoked`. Off by default: nothing is wired unless `messaging.enabled` and `messaging.cliEndpoint` are both on; enabling `cliMessaging` is decided by the rule of section 14.
- **Run lifecycle (fix after slice 2).** The run supervisor spawns while the run is QUEUED and moves it to RUNNING only after the spawn returns, and the endpoint is minted in the spawn: so `mint` accepts a QUEUED or RUNNING run (any other state is refused). Before RUNNING, a relayed open or frame answers `not_ready` and revokes nothing, a relay-close answers nothing and changes nothing, and a connection that was refused in that window is not open afterwards (it must be opened again once the run is RUNNING), so nothing is relayed as the worker before the run is RUNNING; the window runs from the pty process opening the listener (in the spawn, before the child starts) until the supervisor marks the run RUNNING once the spawn has returned: about one control-channel round trip, and a client that connects in it is told `not_ready` and may retry. A failed spawn and the run's exit revoke as before; a run in any other state (terminal, REVIEWING, BLOCKED) is revoked at its next message, as before. The messaging setting is checked before the launch window, so a QUEUED endpoint whose worker's messaging is off is revoked rather than answered `not_ready`. Tested through the real supervisor (`messages-endpoint-lifecycle.test.ts`).

## 13. The CLI endpoint listener (PV-M6 slice 2)

- **Where.** `packages/pty-process/src/endpoint-host.ts` (the endpoint's transport, hosted by the pty process, ADR 0007 decision 7.1; it loads no socket built-in: it listens through `endpoint-listen.ts`, the template pinned by SHA-256 in `scripts/code-oss/web-rules.mjs` that alone may load `node:net`, and handles each connection through that template's facade), wired into the service's spawn (`messagesEndpoint`), its run exit and its control channel (`relayOutbound` in, `relayInbound` out); the client port forwards relayed messages (`onRelay`) and the daemon's answers (`relay`); `packages/daemon-host/src/compose-parts.ts` (`wireCliEndpoints`, `cliEndpointPty`) connects them to the relay of section 12.
- **Off by default, two guards.** Compose wires the relay only with `ComposeOptions.messaging = { enabled: true, cliEndpoint: true }` (both default false; PV-G4 reads `enabled` for delivery and the tools) and a pty port that relays; the pty process listens only when its service is given `messagesEndpoints` (absent by default: a spawn asking for an endpoint is refused `endpoint_unavailable`). And the relay mints nothing until PV-G4 (section 12).
- **The spawn (ADR 0007 amendment item 1).** At a CLI run's spawn the daemon mints the run's endpoint and sends `messagesEndpoint { endpoint, token }`; the pty process runs its unchanged PTY-5 check, opens the endpoint, and only then adds exactly `AXIS_MESSAGES_ENDPOINT` (the socket path) and `AXIS_MESSAGES_TOKEN`. A spawn that fails revokes the endpoint; the run's exit closes it in the pty process (connections, listener, socket file) and revokes it in the daemon at once.
- **Transport (7.2, 7.4).** The socket is in the runtime directory (`$XDG_RUNTIME_DIR/axis`, else `/tmp/axis-<uid>`; `$TMPDIR/axis` on macOS), which must be a real directory owned by the user with mode 0700 (created so when absent, refused otherwise: a symlink, 0755, another owner); socket names are random (72 bits), the path at most 100 bytes, and the socket file is set to 0600 once it listens (an endpoint whose mode cannot be set is closed). A name is never reused, so opening never meets, and never removes, another run's live socket; closing removes only its own file. Sockets a crashed pty process left behind stay in the 0700 directory, unused (no sweep). At most 4 connections (the fifth closed at accept); 4-byte big-endian framing; the first frame at most 512 bytes and within 2 s; nothing after it is relayed before the daemon answered it, and a connection holds at most one frame's cap meanwhile; later frames at most 64 KiB, at most 4 unanswered; a frame over its cap or not UTF-8 closes the connection; an authenticated connection idle for 10 minutes is closed. A reader that does not read (review s2 B1): a reply counts as unanswered until the peer has taken it (the facade's `buffered()` back at 0), a connection whose unread replies pass 4 MiB is dropped (checked before relaying a frame and after every write), one whose unread replies have not drained for 60 s is dropped, and frames from a connection above half that cap do not refresh its idle timer. A reply frame is at most 1 MiB in UTF-8 bytes (the daemon's `replyFrame`; larger is `too_large`). A reply that closes the connection (review s2 recheck B1) destroys it at once while anything is unread; otherwise the connection ends and lingers at most 5 s before it is destroyed, and closing the endpoint destroys every lingering one. The 60 s slow-reader clock re-arms while the backlog falls below the largest seen since it was armed, so a reader steadily taking a long run of replies is kept; progress is seen per reply (a write leaves `buffered()` only once all of it is taken), so a single 1 MiB reply read slower than 60 s is still dropped. A hostile authenticated peer of the same user can hold one of the 4 slots indefinitely by taking one reply before each 60 s slow-reader check and sending frames to refresh its idle timer; that refresh only counts while its unread replies are at most half the cap, so past the 10-minute idle bound it holds at most about 2 MiB per connection (8 MiB for the 4 slots; 4 MiB per connection at any moment). Accepted for a same-user local peer (RR-90). A daemon reply with `close` ends the connection and tells the daemon (`relay-close`), which forgets it, so a failed one does not hold a slot.
- **Residuals.** No peer credentials: Node exposes none, the ADR ships Unix without a native helper, so the 0700 directory keeps other users out and a same-user process can still connect (endpoint design section 2; it needs the token to do anything). Per-peer backoff needs a peer id: the bound is one `auth` per connection under the 4-connection cap, so a same-user process can hold the slots (each for at most 2 s unauthenticated). Windows: no endpoint (no pipe helper; ADR 0007 validation 3). Pause still answers `paused` per request rather than closing open connections.

## 14. Enabling CLI messaging for a worker (PV-M7 slice 1)

- **Where.** `packages/daemon-host/src/messages/enable-rule.ts` (the pure rule), `enable-check.ts` (the host's facts), the `updateSettings` handler (asks first), and `cliEndpointPty`, which asks again at mint. Endpoint design section 6, M-3; ADR 0007 §6.
- **Tier (unchanged).** Enabling is `axis.messages/1.updateSettings`, a user-only tier 2 write. The rule can only refuse an enable or ask for its second step; it never approves anything, and no method's tier or side effect changes.
- **The second confirmation (M-3).** It is the shell's own dialog, resolved in the renderer as a tier 2 user action. It is NOT a native or main-drawn confirmation, and the daemon contract carries only codes, no wording.
  - The daemon cannot tell whether a dialog was shown. Only user-only access through an attested desktop connection protects the second step: the handler refuses any other caller, and the policy row is `userRule(2)`. So a worker or a plugin cannot acknowledge.
  - Re-confirming needs a second toggle. A worker whose messaging is already on cannot confirm again in place: `value: true` on an enabled worker skips the check and leaves the acknowledged files as they are. The user turns messaging off and on.
- **The facts.** The worker's `axis.cliAgents` entry as main returns it (user, application or machine scope only, the CLI start's own path), the real path of an absolute executable, the worker's home worktree, and which CLI project-configuration files exist there (`CLI_PROJECT_CONFIG` of `@axis/pty-policy`, the same list as the protected set).
  - Any gap refuses (`no_entry`): an unknown, archived or composer worker, no live home, no answer from main, or no such entry.
- **Which rows apply.** The CLIs named by the executable's base name AND by its real path, as a union. When neither names a known CLI, every CLI's rows apply, over all of its arguments.
  - **Real path that is a wrapper.** A known CLI's name whose real path is a wrapper (`env`, `sudo`, `doas`, `su`, `runuser`, `nice`, `nohup`, `timeout`, `time`, `stdbuf`, `xargs`, `npx`, `npm`, `pnpm`, `yarn`, `bunx`, `uvx`, `pipx`) or an interpreter is judged as a wrapper. A real path with an unknown name (Claude's versioned binary) still trusts the name.
  - **Unresolvable real path.** An absolute executable whose real path cannot be resolved (a broken link, no permission, gone) refuses: `real_path_unresolved`.
  - So for a wrapper, Codex's `-p/--profile` row also refuses an argument meant as another CLI's `-p` (`npx <package> -p hi`). That fails closed.
- **The rule, in order.**
  1. **User marking.** The entry's `bypassesPrompts` marking, a closed boolean set in user-scope settings: `user_marked`.
  2. **Empty argv:** `empty_argv`. A configuration home set in the arguments (`CODEX_HOME=` or `CLAUDE_CONFIG_DIR=`, as for `env`) refuses: `config_home`.
  3. **Shells and interpreters** (`wrapper_unparsed`).
     - **The names, exactly:** `sh`, `bash`, `zsh`, `dash`, `ksh`, `ash`, `fish`, `busybox`, `cmd`, `powershell`, `pwsh`, `python`, `pythonw`, `py`, `node`, `nodejs`, `deno`, `bun`, `perl`, `ruby`, `php`, `lua`, `luajit`, `awk`, `gawk`, `mawk`, `nawk`, `rscript`, `osascript`, `tclsh`. Each is matched by its base name with a trailing version dropped (`python3.12`, `ruby3.2`).
     - **As the executable,** a shell or interpreter with an inline-code argument is refused; an `awk`-family executable always is.
     - **For an executable that is not a known CLI,** an interpreter named in ANY argument (`env bash`, `nice sh`, `sudo zsh`, `xargs node`) is refused, and so is an inline-code argument in any position.
     - **Inline-code arguments, exactly:**
       - `-c`, `-e`, `-r` and short clusters ending in them (`-lc`, `-ec`, `-Ic`);
       - a value attached to `-c` or `-e` (`-cCODE`);
       - `--eval`, `--command` and `--print`, with or without `=`;
       - `-Command`, `-EncodedCommand`, `-enc` and `-ec` in any case;
       - `/c` and `/k`;
       - `-S` clusters and `--split-string`;
       - a bare `eval`.
     - **Anything outside these two lists is a residual.**
     - **Side effect (fails closed).** A wrapper that passes an inline-code-looking flag to a CLI (`npx <package> -c model=o3`, `-s read-only`, `-r`) is refused too.
  4. **Codex `-c`/`--config` overrides: an allowlist.** More keys than two switch off approvals or the sandbox (`approvals_reviewer`, custom `permissions` with `default_permissions`), so only these keys are allowed:
     - `model` and `model_reasoning_effort`, each with a plain scalar value. The first is the installed codex-cli 0.166.0's own `--help` example; the second is in its package text.
     - `approval_policy` with `on-request` only, the one non-bypass value the help lists; anything else is `codex.config.approval_policy`.
     - `sandbox_mode` with `read-only` or `workspace-write`; anything else is `codex.config.sandbox_mode`.
     - **Everything else is `config_unparsed`:** every other key, every dotted key, any value with `{`, `[`, a backslash or a non-ASCII character, a quoted key, and mismatched quotes. That is a fixed reason, so no key a caller wrote reaches the audit row.
     - **Verified (2026-11-27).** The two benign keys were checked against the installed codex-cli 0.166.0 in a scratch `CODEX_HOME`, with no login and the network routed to a dead proxy, using `codex debug prompt-input`: `model` and `model_reasoning_effort` leave the approval policy, sandbox mode and network access exactly as the baseline, while the same probe shows `approval_policy=never` and `sandbox_mode=danger-full-access` changing them.
  5. **Flag table.** A frozen table of bypass flags, each verified in the CLI's own `--help`:
     - Claude Code 2.1.330: `--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions`, `--permission-mode bypassPermissions | auto | acceptEdits`, `--settings` (any value).
     - Claude Code 2.1.330, also refused whatever their value because they change which configuration, tools or plugins load: `--mcp-config`, `--setting-sources`, `--agents`, `--plugin-dir`.
     - codex-cli 0.166.0: `--dangerously-bypass-approvals-and-sandbox`, `-a/--ask-for-approval never`, `-s/--sandbox danger-full-access`, `--approve-for-me`, `-p/--profile` (any value).
     - Rows match `--flag value`, `--flag=value` and attached short values (`-anever`).
     - Every row refuses.
     - There are no Gemini rows: it is not installed here.
  6. **Pattern rule.** A fail-closed rule over any argument (`dangerously`, `yolo`, `bypass`, `skip-permissions`, `no-confirm`, `auto-approve`, `full-auto`, `approval-mode`, `danger-full-access`, `no-sandbox`, `sandbox=false`): `bypass_pattern`.
  7. **Project-configuration files.** Each file present, for the CLIs that apply, is a structured warning `{ code: "repo_config", path, cli }`.
     - More than 8 refuses (`too_many_repo_files`); a list is never truncated, because a dropped warning would be a file never confirmed.
     - A row whose `severity` is `refuse` refuses instead (`repo_config`; none in slice 1).
- **What the caller sees.** An enable the rule cannot judge is refused under its own reason (`wrapper_unparsed`, `config_unparsed`, `too_many_repo_files`, `empty_argv`); every recognised bypass, the marking and a missing fact are `bypass_entry`. The audit row always names the rule.
- **Two steps.** With warnings, the first `updateSettings` writes nothing and answers `changed: false` with the warnings.
  - The request that names every warned file in `acknowledged` (closed, at most 8, path and CLI bound by regular expressions, compared by path AND cli) writes the setting.
  - It also writes the freshly computed warned paths, never the caller's list, to `messaging_cli_acknowledged` (schema v18): a foreign key to the worker, ids and paths only, no NUL.
  - Turning messaging off clears them.
- **At mint.** The same rule runs over the argv that actually spawns and the entry's marking read again.
  - A file present now that was not acknowledged gets no endpoint until the user confirms again: `repo_config_unacknowledged`.
  - So does an entry edited or marked since, or more than 8 files.
  - The check is bounded at 2 s (no answer: no endpoint), inside the supervisor's 10 s start bound.
- **Audit.** `message.endpoint` rows, never an argument or a path:
  - `enable_refused`, with the rule's id;
  - `enable_needs_confirmation` and `enable_allowed`, with the warning count;
  - `mint_refused`, with the rule's id and, for unacknowledged files, their count.
- **Known evasions (residuals; the user's own entry is the trust anchor, so these are ways it can still auto-approve):**
  - **Abbreviated or combined flags.** An abbreviated long flag (`--permission-m auto`) is not matched, and combined short flags (`-xa never`) are not split.
  - **Unlisted config keys.** Codex `-c` keys other than the two security keys are not checked.
  - **Interpreters off the list.** Shells, interpreters and inline-code forms not in the two exact lists above are not caught.
  - **Other working directories.** Project configuration in another directory than the worker's home (Codex `-C/--cd DIR`, Claude `--add-dir`) is never checked.
  - **Tool permissions.** Tool pre-approval by `--allowedTools`, or a `--permission-prompt-tool`, is not inspected.
  - **Programs that run programs.** Programs other than the listed wrappers and interpreters can run a CLI or run code: `mshta`, `sqlite3 .shell`, `make`, `sed s///e`, `xargs -I`, `find -exec`, `script -c`, a container runner. Their arguments are judged only by the wrapper union and the pattern rule. An interpreter or shell running a script FILE (`bash run.sh`) is not read.
  - **Environment and user-level files.** `envPassthrough` variables and the CLI's environment-driven settings are not inspected. User-level CLI configuration (`~/.claude`, `~/.codex/config.toml`) is not inspected either.
  - **File contents.** Project-configuration content is never read, only its presence (by `lstat` of the final component; a file reached through a linked parent directory counts as present). A script run by a shell as a file (`bash run.sh`, a shell as the executable) is not read.
  - **Argument files.** Arguments read from a file (an `@argfile` form, if a CLI has one) are not inspected.
  - **Marking a live endpoint.** Marking an entry, or adding a flag to it, after enabling does not revoke a run's live endpoint; the next mint refuses.
  - **Content and path races.** A project file whose content changes between enable and mint is not detected. A file that appears between the mint's `lstat` and the CLI reading it is not either.
  - **Real-path race.** The real path is taken only for an absolute `argv[0]`, by the daemon at mint, while the executable is resolved later at exec: a link swapped in between is a race. A bare name gets no real path.
  - **Closed, for comparison.** A later overriding flag never re-allows, because any listed occurrence refuses (stricter than the CLI). Between the mint check and the spawn, the spec is the same object, so the argv cannot change.
  - **Not here.** The open question of messaging while BLOCKED stays for slice 2.
