# Diff review core (`@axis/review`)

- **Status:** Design, Phase 1a (ROADMAP ticket 7, design task B7). Written before the code.
- **Covers:** the changed-files list against a base, per-file and per-hunk accept and reject, the reviewed tree and its binding to `@axis/git-ops` commit (REV-1), the "files changed outside the agent" model, protected-path flags, display escaping, symlink-safe preview and the secret-warning data for the push dialog (PSH-1, FT-1, DASH-1, WT-3, DRF-2 to DRF-4).
- **Does not cover:** the UI, the daemon handlers (`axis.git/1.commit`, `axis.worktrees/1.discard`, `.applyPatch`), the drift ledger watcher, the run-base ref writer, the protected-path list itself, writing rejected changes back to the worktree (the `discard` action).

## 1. Shape

A pure TypeScript package. It touches no file and no process directly. Everything goes through:

- the `GitRunner` and `GitOpsDeps` of `@axis/git-ops` (the same object the daemon already holds), always in the **daemon** context with the hardened prefix (`--no-pager --no-replace-objects --git-dir --work-tree -c core.fsmonitor=false -c core.hooksPath=<off> -c protocol.allow=never -c diff.submodule=short` and every `filter.*` driver neutralised). `guardedRunner` refuses a call that lacks it. This package never builds an argv for another context.
- a `TempIndexProvider` (the daemon hands out a file in its private data directory; tests use `mkdtemp`). The package has no `node:fs`.
- an optional `ProtectedPathMatcher` and the optional `SecretScanner` already in `GitOpsDeps`.

Errors are `ReviewError` with a code from the closed `@axis/protocol` set. Details are primitives only; no `cause`, no getters, nothing taken from git's stderr except a sanitised, truncated string (`sanitizeText` and `redactUrls` from `@axis/git-ops`).

## 2. The worktree is read once, into immutable objects

Reading a worktree file twice is a TOCTOU (a CLI is still writing; a file can be swapped for a symlink). So review reads the worktree **exactly once**, through git, into a tree object, and everything after works on objects:

1. Temporary index (`GIT_INDEX_FILE` set only on these calls, never in the pty environment).
2. `read-tree <against-tree>`, then `-c core.sparseCheckout=false add -A`, then `write-tree`. The result is the **worktree tree** `W`: tracked and untracked, **not ignored**. This is the same method the run-base ref uses (policies §3.1), so the two agree.
3. The temporary index is removed in a `finally`, after the last git process that uses it has ended.

`git add` uses `lstat`: a symlink is stored as a link and never followed, and a directory replaced by a symlink is a single link entry. Filters are neutralised by the prefix, so no repository-defined program runs (see the next two paragraphs for what that costs). Ignored files never enter `W`, and so cannot reach a commit made from the reviewed tree. A change to `.gitignore` is itself a reviewed change.

**Content filters (git-crypt, LFS, a clean/smudge pair).** Because no clean filter runs, the worktree's smudged bytes enter `W` as they are, and a file that `git status` calls unchanged (stored blob = clean(worktree)) looks modified: accepting it would commit the smudged bytes (decrypted text, or a full binary in place of an LFS pointer). So `check-attr -z --stdin filter` (which runs no program) is asked about every changed path, both sides of a rename included, and a path is **filtered if any read names a driver**: (1) the worktree's attribute files, (2) the real index's (`--cached`), and (3) the **base tree's**, read from a temporary index holding the `against` tree. The third read is what stops a CLI from making a stored blob look plain by staging an edit of `.gitattributes`, removing it, or editing it in the worktree only. Each read is run twice, with `core.ignorecase` true and false, because the setting changes which paths a pattern matches. Attribute sources outside the tracked tree are handled by what they can do. `$GIT_DIR/info/attributes` outranks every tracked `.gitattributes` and every read obeys it, so any attribute line there (blank and comment lines do not count) makes every changed path `kind: "filtered"` with `fileLevelReason: "attributes_untrusted"`. The user-level file (`core.attributesFile`, or when that is unset the default under `$XDG_CONFIG_HOME` or `$HOME/.config`, as git itself chooses) and the system file rank **below** every tracked file, so only a **macro definition** there can hide a filter (it replaces a macro the tree uses); a macro definition in either, quoted or not, gives the same `attributes_untrusted` result. Lines are read the way git reads them: leading white space is skipped, a `"` starts a C-style quoted pattern (so `"\133attr]x"` is the macro `[attr]x`), and a quoted pattern that cannot be decoded counts as a macro. A line that only names a filter (`*.ipynb filter=nbstripout`, or a pattern such as `src/filters/*.c`) does not block anything: the three reads see it. An attribute file that exists and cannot be read whole also gives `attributes_untrusted`. The files are read through `hash-object -w` and `cat-file`, since the package has no file system. The sources are read **before and after** the `check-attr` reads, and the review refuses (`attributes_untrusted`) unless both reads are trusted and every source has the same object id in both, so a file swapped in while the reads ran is seen. Known limits: a swap made after the first read and undone before the second is not seen, and a file watcher (inotify) can time it, so this check narrows the window and does not close it (see §14); a tracked `.gitattributes` that uses a macro defined outside the tree is checked against that macro as it is now, so a redefinition made before the review cannot be seen; deleting a filter that only the user's file sets makes the stored file look unfiltered, because a line that names a filter is not read as a blocker; the system file is found with `git var GIT_ATTR_SYSTEM`, which needs git 2.42, so on an older git it is not checked. A filtered path is listed with `kind: "filtered"` and `fileLevelReason: "filtered_path"` and **cannot be accepted** (`E_POLICY_DENIED`, `reason: "filtered_path"`), by decision or by hunk; `build` refuses it as well. The user commits it with git itself, where the filter is the user's own. Known limit: a filter literally named `unspecified`, `set` or `unset` cannot be told from none by check-attr. `core.autocrlf`, `eol`, `ident` and `working-tree-encoding` need no detection: they are built into git, `add -A` applies them, and they cause no false change.

**Threat-model note: plaintext in the object store.** `add -A` writes the smudged bytes of a filtered file (the plaintext of an encrypted file, say) as loose objects in the shared object store, and `hash-object -w` does the same for `info/attributes`. No commit or ref refers to them, but they are on disk until `git gc` prunes them, and the run-base snapshots share the method and so the property. The threat model should list it next to GIT-3 when that document is next revised (not edited here).

**Size cap.** A file larger than `maxSnapshotFileBytes` (50 MiB, the cap of policies §7, not raisable) is put back to its base state in `W` after `add -A` and reported in `session.skipped` (`reason: "too_large_to_review"`, path, size) instead of being listed or silently missing. This is meant to be the rule the run-base snapshots follow, so that a large file is the same in the run base, the run end and now and is never "changed outside the agent". **Contract for the run-base writer** (not on any branch yet): policies §7 speaks of untracked artefacts, but this code also leaves a *tracked* file that grew past the cap at its base state, so the writer must skip tracked files over the cap the same way, or such a file will show as changed outside the agent. It cannot be reviewed or accepted. Its object is still written once by `add -A`.

Known cost: a fresh temporary index has no stat cache, so every snapshot hashes every non-ignored file once. It is proportional to the worktree, not to the diff (see §12).

## 3. Changed-files list

`listChanges(against, W)` runs `diff-tree -r -z --raw --no-abbrev -M -l<n> --no-ext-diff --no-textconv` and `--numstat -z`, both parsed from NUL-separated records, never from patch headers (which are C-quoted). Each entry:

`{ path, oldPath?, status: A|M|D|R|T, oldMode, newMode, oldOid, newOid, kind: text|binary|symlink|submodule|too-large|filtered, similarity?, additions?, deletions?, displayPath, displayOldPath?, protected, warnings }`

- **Renames** (`-M`), **deletions**, **mode changes** (a mode-only `M` has no hunks), **type changes** (`T`), **binary** (numstat `-`), **submodules** (mode `160000`, the commits are shown as data, never diffed or entered) and **symlinks** (mode `120000`, the target is data) are all first-class.
- Object sizes come from one `cat-file --batch-check=%(objectsize)` call over every non-gitlink oid. Over `maxPreviewBytes` marks `too-large`.
- Paths are validated before they can be used: no NUL, not absolute (`/x`, `\x`, `C:x`), no `.`, `..` or empty segment, no `.git` component (case-insensitive, trailing dots and spaces ignored, `.git:stream`, zero-width HFS-ignorable code points, `git~1`, `gitmod~1`); a `:` elsewhere in a name is an ordinary POSIX name and is allowed. Not flagged: case-only and NFC/NFD duplicate paths, and a symlinked `.gitmodules`, length at most 4096. A bad path is listed (so the reviewer sees it) with `unsafePath` and cannot be accepted. `git update-index --index-info` itself answers "Ignoring path ../x" with exit 0, so git cannot be relied on for this.
- More than `maxFiles` entries, or runner output reported `truncated`, makes the list incomplete. A review that could not list everything must not become a commit: `startReview` refuses (`E_INVALID_ARGUMENT`, `details.reason: "too_large"`).

The `against` commit is a full object id. A review that will be committed must have `against == HEAD` (the commit's parent); the daemon passes the recorded base for the overall "what did the run change" list and `HEAD` for the commit round. See §6.

## 4. Hunks

`loadHunks(review, path)` is on demand, per file, and only for a text `M` (and a text rename with content change). Add, delete, symlink, gitlink, binary, mode-only and type change are file-level only.

It diffs the **two blobs**, not paths: `git diff --no-ext-diff --no-textconv --no-color --no-renames -U3 <oldBlob> <newBlob>`, with every config setting that changes the output pinned on the command line (`diff.suppressBlankEmpty`, `diff.noprefix`, `diff.mnemonicPrefix`, `diff.interHunkContext`, `diff.context`, `core.bigFileThreshold`), so a repository cannot switch per-hunk review off. No pathspec, no attribute lookup, no quoting, no path in the output. Caps: both blobs at most `maxHunkFileBytes` (1 MiB), the patch at most `maxPatchBytes`, hunks at most `maxHunksPerFile`; beyond any of them (or a runner `truncated`) the file is file-level only with `reason`.

The parser is strict and linear:

- header `@@ -a[,b] +c[,d] @@`, at most 9 digits per number; a missing count is 1;
- the body is read **by the counts in the header**: it must contain exactly `b` old-side and `d` new-side lines (context counts for both) before the next header. More, fewer, a line that starts with anything but space, `+`, `-` or `\`, or a blank line, is `malformed`. A hunk header that lies about its line counts therefore never reaches the apply step;
- the patch is split on `\n` only. `\r` stays in the line, so CRLF files keep their line endings; `\ No newline at end of file` clears the line terminator of the line before it (both sides for a context line);
- U+2028, U+2029 and U+0085 are not line breaks.

Apply works on the old blob text with line terminators kept. For each accepted hunk, in order: the old-side lines must equal the old blob lines at the stated position **exactly** (including terminator), ranges must not overlap and must be increasing, otherwise the file falls back to file-level. Unaccepted hunks leave the old lines in place.

**Self-check.** Before hunks are offered, all hunks are applied and the result is hashed as a git blob **in process** (SHA-1 or SHA-256 by the object id length). It must equal the new blob's id. If not, the file is file-level only (`not_reproducible`). This catches a lying diff, a text that does not survive the runner's UTF-8 decoding (the runner returns strings; invalid UTF-8 cannot be round-tripped), and any difference between my reading of the patch and git's. It is the property that makes partial accept safe: the hunks are proven to be the whole change.

## 5. Decisions and the reviewed tree

Nothing is accepted by default. `ReviewSession` holds, per file, `none | accepted | partial(hunk set)`. A hunk is named by `{ index, digest }` (SHA-256 of its text); a stale or unknown name is `E_NOT_FOUND`. `acceptFile` accepts the metadata (mode, rename, type, delete) and all hunks; `acceptHunk` accepts content only (the old mode stays; for a renamed file the old path is removed and the new one holds the edited content, since a half-moved file has no meaning) until every hunk of the file is accepted, which is then the whole file, mode and rename included. A path, an unknown file or a decision on an unsafe path is refused.

`build()` produces the **reviewed tree** `R`:

1. a new temporary index, `read-tree <against-tree>`;
2. one `update-index -z --index-info` call (NUL-terminated, so paths with newlines and quotes are safe), with the accepted entries: new `mode oid path`; a delete is mode `0` and the zero oid; a rename is a delete of the old path plus an add of the new one; before anything is written, accepting one side of a file-and-directory change at the same path (keep the delete of `x`, accept the add of `x/y`, or the reverse) is refused (`E_CONFLICT`, `reason: "path_conflict"`, both display paths named); a partial file is the blob written by `hash-object -w --stdin --no-filters` from the applied text; a gitlink carries its commit id;
3. `write-tree`;
4. **verification**: `diff-tree -r -z --raw` from the `against` tree to `R` must list exactly the paths that were accepted, with the accepted modes and ids. Because `--index-info` can ignore a path silently with exit 0, `R` is never trusted without this check;
5. the temporary index is removed.

Hunk and preview lines are cut at 4 x `maxDisplay` (2048) code points. A cut line carries `truncated: true` (no printable marker is added: a real `…` stays ordinary text); a hunk view has `truncated` if any line is cut, and `acceptHunk` on it is refused (`E_POLICY_DENIED`, `reason: "truncated_hunk"`) unless the caller passes `{ acceptTruncated: true }`, the user's explicit acknowledgement. A text preview reports `truncatedLines`.

The user's worktree is not touched. The user's real index and refs are not touched either, until the daemon calls `prepareCommit` (§6). Objects are added to the object store, like git-ops already does with tree objects.

## 6. The binding and the `@axis/git-ops` commit contract

What `executeCommit` does today (read from `packages/git-ops/src/commit.ts`): it takes `reviewedTreeHash`, runs `write-tree` on the **real index**, and refuses unless that equals the hash; refuses `HEAD` detached; refuses when HEAD's tree already equals it; commits in the pty context with `commit -F -`; afterwards checks the new commit has the reviewed tree and the parent it saw at check time (and undoes by compare-and-swap if only the tree is wrong).

That contract is **sufficient to bind the content of the commit**, with one step in front of it. It is **not sufficient** for the following, which this package therefore does and which I propose to tighten in git-ops (not changed here):

| # | Gap in git-ops | Done here | Proposed git-ops change |
|---|---|---|---|
| G1 | The real index only equals `R` if something put `R` there. A partial accept leaves the index at the old state. | `prepareCommit` does `read-tree R` into the real index, under the daemon's lock. | None. |
| G2 | The worktree is never compared with what was reviewed. A file edited after review does not stop the commit (the gate requires that it does). | The binding records `W`; `prepareCommit` re-snapshots and refuses if `W'` differs (`E_CONFLICT`, `details.reason: "stale"`). `handoff()` re-checks HEAD, the branch and the index right before the input is handed over. | Optional `assertReviewFresh(worktree, reviewedTreeHash)` in `GitOpsDeps`, called inside `check()` next to `assertNoDrift`, after the lock is held and immediately before `commit` runs. The daemon wires it to `checkFresh`. |
| G3 | `R` was built on HEAD at review time. `plan.parent` is read at commit time. If HEAD moved after `prepareCommit` (another tool ran `commit-tree` and `update-ref`, which leave the index alone), committing `R` lands on the new parent and silently reverts it. | The binding records `head` and the branch; `prepareCommit` refuses if either moved, and `handoff()` re-checks just before handing over and carries `expectedParent` and `expectedBranch` in the input (`PinnedCommitInput`). The parent is **carried, not pinned**: git-ops ignores the two fields today, so nothing is enforced after `handoff()` returns. | **Required.** `CommitInput.expectedParent: string` and `expectedBranch?: string`, checked in `check()` after `symbolic-ref`/`rev-parse HEAD` (`plan.parent !== expectedParent` or a different branch: `E_CONFLICT`), and again in `verify` (parent of the new commit). |
| G5 | `check()` does not refuse an operation in progress. `read-tree R` removes the unmerged index entries that make `write-tree` fail, so with `MERGE_HEAD` set git records a second parent, and with `CHERRY_PICK_HEAD` the commit takes the author of the picked commit, going around the identity check. | `prepareCommit` refuses (`E_CONFLICT`, `reason: "operation_in_progress"`) when the index has unmerged entries or `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `REBASE_HEAD`, `rebase-merge`, `rebase-apply`, `sequencer`, `BISECT_LOG` or `BISECT_START` exists, before and after staging, with paths from `rev-parse --git-path` (so a linked worktree's own directory is the one checked). Existence is asked through the injected `fileExists`. | Same refusal in `check()` (git-ops should not depend on its caller for it). |
| G4 | `GitOpsDeps` helpers needed to build hardened calls (`daemonGitFor`, `checkWorktree`, `OBJECT_ID`) are not exported; only `prefix`, `guardedRunner`, `filterNames`, `requireGitVersion` and `daemonGitEnv` are. | Rebuilt here from those exports (about 25 lines). | Export `daemonGitFor` with an `extraEnv` parameter (needed for `GIT_INDEX_FILE`), and `checkWorktree`. |

**The contract git-ops must implement against (stable).** `handoff()` returns `{ worktree, reviewedTreeHash, message, author?, expectedParent, expectedBranch }`, the shape of git-ops' `CommitInput` on `fix/git-ops-bound-commit`: `expectedParent` is a full commit id and `expectedBranch` is the short branch name (`axis/<slug>`, not `refs/heads/axis/<slug>`), and both are required. `prepareCommit` refuses a detached HEAD itself (`E_POLICY_DENIED`, `reason: "detached_head"`) and an unborn branch (`no_head`) before any hand-over. In `check()`, after the lock is held and immediately before `commit` runs, git-ops must: (a) refuse (`E_CONFLICT`) if `rev-parse HEAD` is not `expectedParent` or the branch is not `expectedBranch`; (b) refuse (`E_CONFLICT`, `operation_in_progress`) if the index has unmerged entries or `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `REBASE_HEAD`, `rebase-merge`, `rebase-apply`, `sequencer`, `BISECT_LOG` or `BISECT_START` exists under `rev-parse --git-path` (the expected operation state is: none); (c) call `assertReviewFresh` (G2); and in the post-commit check compare the new commit's first parent with `expectedParent`, not only with the parent it read itself. Until then the window from `handoff()` to git running is open: HEAD moving, or `MERGE_HEAD` appearing, in that window is not caught by this package.

`prepareCommit` returns `previousIndexTree` (the tree the real index held before it was replaced, when it could be written) so a refused commit can put the user's staging back.

Between `prepareCommit` and git running there is a window in which a file can change. That does not change what is committed (`R` is already an immutable tree in the index) but it makes the commit differ from the worktree the user saw, which is why G2 is best closed inside git-ops.

The **binding** is an instance of `ReviewBinding`, a class whose constructor needs a module-private token and whose instances are recorded in a module-private set, so a plain object, or one made with its prototype, cannot be passed in its place; every function that takes one checks (the same device as the journal's `UserPrincipal`). It holds `worktree`, `head` and the checked-out `branch` (or null), `headTree`, `worktreeTree` (`W`), `reviewedTree` (`R`), and a digest over all of them and the accepted file summary, for the audit event. `prepareCommit` refuses when HEAD or the branch is no longer the one reviewed. `prepareCommit` returns a `PreparedCommit` whose `handoff(message, author?)` returns a `PinnedCommitInput` (a `CommitInput` plus the required `expectedParent` and short `expectedBranch`; a type-level test keeps it assignable to git-ops' `CommitInput`) for `executeCommit`. It does not carry a path from a renderer: the daemon keeps the binding keyed by its own id.

## 6a. What the daemon wire adds (ticket P1b)

`axis.review/1.diff` is bounded-line review: the wire carries display paths, counts and flags, no hunks. It reports `truncated` for a file whose whole-file accept needs `acceptTruncated` (`hasCutLines`), and returns a `treeHash` only when no file is truncated and unacknowledged. The user acknowledges a file through the request's `acknowledged` list; the handler passes `acceptTruncated: true` for those files only, and MUST NOT pass it in any other case. See `docs/design/daemon-host.md` section 4.2.

## 7. Display (FT-1, DASH-1)

`escapeForDisplay(s, opts)` is total and never throws on any string: C0 and DEL, C1, lone surrogates, non-characters, line and paragraph separators, bidirectional controls (U+061C, U+200E/F, U+202A to U+202E, U+2066 to U+2069), zero-width and joiner characters (U+200B to U+200D, U+2060, U+FEFF) and the Unicode tag block are written as `\n`, `\r`, `\t`, `\xNN` or `\u{X}`; a backslash is written `\\` so the output is unambiguous; the result is truncated at `maxDisplay` code points with an ellipsis marker, never in the middle of a pair. Paths use it in full and are cut in the **middle** (the start and the last two thirds are kept), because the file name is at the end and is what a reviewer must not lose. Hunk text keeps a tab as a tab (open question Q2) and shows a trailing `\r` as an end-of-line marker `eol: "crlf"` instead of text. The raw string is kept for operations; only `display*` fields are for the UI.

## 8. Symlinks and preview

There is no filesystem access, so nothing can follow a link: previews come from objects. `previewBlob(review, path, side)` returns `text` (escaped, size-capped), `binary` (a placeholder with the size), `too-large`, `submodule` (commit ids) or `symlink`. For a link only the target string is shown, with `escapesWorktree` computed lexically: absolute (`/`, `\`, a drive), or a normalised `..` that climbs above the repository root from the link's own directory. A link that escapes is flagged as a warning and never dereferenced. Because a worktree directory replaced by a symlink is a link entry, `a/b` can never be reached through it.

## 9. Protected paths (WT-3)

`ProtectedPathMatcher.match(path): readonly ProtectedHit[]`, each hit `{ rule: string }`, is injected (the `@axis/git-snapshot` matcher will satisfy it structurally). It is called with the repository-relative path, and with both `oldPath` and `path` for a rename. A matcher that throws marks the file protected with rule `matcher-error` (fails closed). Rule names are bounded and escaped. No policy decision depends on it (highlight only, as WT-3 says for 1a).

## 10. Files changed outside the agent (DRF-2 to DRF-4)

`computeOutsideAgent(deps, { worktree, runBase, runEnd?, ledger, ledgerComplete })`. The set of changed paths is `diff(runBase, now)`; the watcher never decides it. Of those, a path counts as **outside the agent** when:

- `after-run`: it differs between the run-end tree and now. This needs no watcher at all, only a tree snapshot at run end (the daemon takes it at exit), so it holds even when every watcher event was dropped; or
- `ledger`: the watcher's ledger names it (a write during the run that was not the run's).

Every other changed path is `unattributed` and is still in the full changed list (nothing is hidden by a missing event). If `ledgerComplete` is false (the watcher reported overflow), the report says `attributionIncomplete: true` and the indicator reads "at least N". A ledger path that is not changed against the run base is ignored (reverted or overwritten: nothing to review). Attribution is informational (DRF-3). The ledger is bounded (`maxLedger`) and over-long input is `truncated`, never silently dropped.

## 11. Secret warnings for the push dialog (PSH-1)

`secretWarnings(deps, review)` runs the injected `SecretScanner` (the one `planPush` already uses) over the patch of `against..R` (`diff-tree -p --text --no-renames`, so binary and attribute tricks cannot hide content), with `part: "patch"`, and returns `{ findings: { rule, displayPath, line }[], binaryPaths, truncated, requiresConfirmation, digest }`. It lets the dialog warn at accept time. It never carries matched text: rule names are restricted to `[A-Za-z0-9._-]{1,64}` and paths are escaped. A truncated scan sets `requiresConfirmation`. This does not replace the scan in `planPush`, which runs on what is actually pushed.

## 12. Limits

All counters are incremented before they are checked, and a cap hit is always visible (`truncated` or a refusal), never silent. Defaults: `maxFiles` 5000, `maxPreviewBytes` 1 MiB, `maxHunkFileBytes` 1 MiB, `maxPatchBytes` 2 MiB, `maxHunksPerFile` 1000, `maxDisplay` 512 code points, `maxLedger` 100000, stale-path list 100. The runner's own output cap and timeout bound each git process; the package adds no timer, listener or retained handle.

## 13. Tests

`node:test` only; nothing assumes a git version or an OS (POSIX-only fixtures, such as an executable diff driver, skip on win32).

- unit: display escaping (every class above, idempotence, a lone surrogate, truncation), path validation, symlink escape, the hunk parser and apply with a fake runner: a header that lies about its counts, extra and missing body lines, CRLF, no newline at end of file on either side, overlapping or out-of-order hunks, a huge hunk count, a context mismatch;
- real git: every status (A, M, D, R, T, mode, binary, symlink, gitlink), a path with a newline and quotes, partial accept reproducing the exact blob, the reviewed tree verification, a file swapped for a symlink between review and accept and between accept and commit, an edit after review refusing, HEAD moving, `diff.external`, `diff.<driver>.textconv` and a clean filter that would write a marker file (none runs), a CRLF file, a giant diff, a hostile runner returning `../../x` and `.git/hooks/x` in paths, and an end-to-end `prepareCommit` then `executeCommit`;
- the outside-the-agent model with the watcher blind (empty ledger, `ledgerComplete` false).

## 14. Open questions and known limits

- **Q1.** `against` for the commit round must be HEAD (§3, G3); the daemon chooses. Should the journal expose "HEAD at last commit" so the UI does not compute it?
- **Q2.** Tabs in hunk text are not escaped (code in Makefiles and Go would be unreadable); everything else is. A strict reading of the gate would escape them too.
- **Q3.** Reject only leaves a change out of `R`; it does not revert the worktree. That is `axis.worktrees/1.discard`, with its backup ref and approval, and belongs to the worktree package.
- **Q4.** The snapshot hashes every file (no stat cache). If that is too slow on large repositories, the daemon can keep one persistent snapshot index per workspace; every `create()` must return its own file: two operations sharing one file could interleave `read-tree`, `add` and `update-index`, so the package refuses a path that is still in use. A persistent snapshot index must therefore be handed out one operation at a time.
- The runner decodes output as UTF-8. Text that is not valid UTF-8 cannot be offered per hunk (the self-check refuses it) and the scanner sees decoded text, the limitation `docs/packages.md` already records for git-ops.
- `prepareCommit` replaces the real index. Staging done outside Axis (the SCM view, a terminal) is replaced by the reviewed tree; the worktree is not touched.
- The injected `fileExists` is required: without it an in-progress rebase or bisect could not be seen. The daemon passes `fs.access`.
- A filter name read once per `reviewGitFor` can go stale: a config change between that read and `add -A` could run the new clean filter in the daemon (git-ops has the same pattern; closes with the git-ops change that reads filters inside the call).
- A sparse-checkout repository is not supported by `prepareCommit` (replacing the real index would drop its skip-worktree bits); it is refused with `E_UNAVAILABLE`.
- `git add` has a short race between its own `lstat` and `open`; a file swapped inside it can put the target's bytes into `W`. They are visible in the review and never committed unless the user accepts them.
- **Attribute sources can be swapped between the two reads (open, residual).** `$GIT_DIR/info/attributes` outranks every tracked attribute file, and every `check-attr` read obeys it. A process that writes `secret.env -filter` there after the first read and restores the file before the second makes an encrypted file look plain; with a file watcher it is reliable (a reviewer's test: 9 of 10 runs), and accepting the file then commits the plaintext. The two-read comparison catches a swap that is still in place at the second read only. **Not fixed in this package.** The fix the reviewer proposed is to run `check-attr` with a private, empty `GIT_DIR` whose `GIT_OBJECT_DIRECTORY` points at the real store (so no `info/attributes` exists to be swapped), read `info/attributes` once and refuse on any line, set `GIT_ATTR_NOSYSTEM=1` and hand git a private snapshot of the system and user attribute files as `core.attributesFile`. It was not done here because the hardened invocation (`--git-dir`, `-c` pins, the repository config such as `core.ignorecase`) belongs to `@axis/git-ops`' `prefix`, and a private git directory would drop the repository config the reads depend on; it should be built as one change to that prefix (a "private attribute read" mode), with this package passing the real index and work tree. Until then the residual is the same class as WT-2 (git-directory state changed under the daemon by a local process that already has the user's file-system rights); it belongs next to WT-2 in `docs/security/threat-model-phase1.md`, which this change does not edit.
