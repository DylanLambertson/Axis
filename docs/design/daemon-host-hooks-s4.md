# H9-hooks slice S4, part 1: push through the pty process, hooks off (implementation notes)

Status: part 1 BUILT. Design: `docs/design/daemon-host-hooks.md` §5.2 (push as a terminal-bound run), H-5, H-7, H-10, and `docs/design/daemon-host-git.md` (push, scan base per destination, P1e and P1f). Part 1 replaces the S1 guard (`push_not_available`, S1 note part 2, departure 2) with a real push. Part 2 (`pre-push`) is not built; see "Split" below.

## Split: why S4 is two parts

§5.2 runs `pre-push` with the push and checks its path "as in step 4": git's per-hook answer and the raw repository-level `core.hooksPath` stored in the GIT-SNAP-1 snapshot (layout version 3), plus the pinless scope read. That resolution is slice S2, which is not built (the snapshot is still layout version 2), and the reply's `hooks.prePush` is part of the S3 contract work. So:

- **Part 1 (this):** the push itself, with every repository hook pinned off. This is the default (`axis.git.runHooks` is off unless the user turns it on).
- **Part 2 (after S2 and S3):** with `runHooks` on, resolve and check `pre-push` (`hook_path_unseen`), let git run it in the push terminal, report `hooks.prePush`, and refuse `hook_failed` on a non-zero exit with the challenge already spent. Until then a push with `runHooks` on over the pty process is refused `E_UNAVAILABLE` before the scan and before any challenge (H-5: never pushed without the hook it should run, never run unchecked).

## Departures and decisions

1. **No terminal is granted yet.** §4.2 and §5.2 grant the push terminal to the workspace's terminal and attach before the spawn. The UI side is S5; until then nothing attaches and the service drops the output (it never reaches the daemon either way). The verdict is unchanged.
2. **The destination joins the digest (stricter than the design text).** The design said the approved plan's digest is what is pushed; the digest did not name where. It now does, only when the caller passes a destination (git-ops' other callers keep their digests).
3. **The ssh used for the push is the pty process's.** The push runs with the pty process's startup environment (`PATH`, `HOME`, `SSH_AUTH_SOCK`); the scan-base key is resolved daemon-side with the daemon's view (`daemon-host-git.md`, "Which ssh"). The entry must start both with the same environment (RR-11 residual unchanged). A message cannot set `GIT_SSH*` (`env_denied`).
4. **Repository and user settings that run a program on push are left to the drift gate** (the trust decision, stated): `remote.<r>.receivepack` (run through the shell for a local or `file://` remote), `core.sshCommand`, `ssh.variant`, `credential.helper`, `core.askPass` (still consulted with `GIT_TERMINAL_PROMPT=0`), `core.gitProxy` (`git://`), `http.proxy` and `remote.<r>.proxy`, and `push.gpgSign` with `gpg.program`. They are the user's configuration, as for a push from a terminal; a change to the repository's is a GIT-SNAP-1 drift, refused before the push (`git_drift`), and the user-level ones are read from the locations the host validated (S-2). The window between the last re-take and git's start is R-H1's push half. NOT left to the gate: `remote.<r>.vcs` and the `<t>::` URL forms with `alias.remote-<t>` or a `git-remote-<t>` (B-1, refused twice and pinned). `push.pushOption` sends push options from config without `-o`; harmless to Axis (nothing is read back), noted because the argv sends none.
5. **`MIN_GIT_VERSION` does not gate a push.** The floor exists for lazy fetches in plain execs; a push is itself a transport run. `GIT_NO_LAZY_FETCH=1` is set as on every exec.
6. **A failed push says only its exit code.** git-ops used to put git's sanitised stderr in the error text (review N-4); the pty run returns none (H-7), so the text is the exit status for every runner.
7. **Departure from review 1's first suggestion for S-2.** The reviewer offered refusing any `GIT_CONFIG*` in the startup environment or pinning `HOME`/`XDG_CONFIG_HOME`. Both would cut the push off from the user's own configuration (credentials, identity, ssh) or break users who set it deliberately; comparing the exact values git-ops validated with is stricter where it matters (any difference refuses) and keeps the user's configuration. git-ops already refuses `GIT_CONFIG*` in its pty environment (S-9), so in practice the service must start without them too.
8. **`GIT_*` by allow-list (review 2 SF-1).** The legacy `GIT_CONFIG=<file>` makes `git config` read only that file (`git push` ignores it), which blinded the service's `remote.<r>.vcs` read; PTY-5 lets it through. The push and its remote check now keep only these `GIT_*` names from the startup environment: the compared `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`, `GIT_SSH`, `GIT_SSH_COMMAND`, `GIT_SSH_VARIANT`, `GIT_PROXY_COMMAND`; the https trust roots `GIT_SSL_CAINFO` and `GIT_SSL_CAPATH`; the identity names; and what the service sets (`GIT_TERMINAL_PROMPT`, `GIT_NO_LAZY_FETCH`, `GIT_ALLOW_PROTOCOL`). Every other one is removed (`GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n`, the location names, `GIT_EXEC_PATH`, `GIT_TEMPLATE_DIR`, `GIT_ATTR_SOURCE`, `GIT_TRACE*`, `GIT_SSL_NO_VERIFY`, ...). `GIT_CONFIG` is also in the compared set, so a service started with it refuses (`env_denied`: the host never has it, git-ops refuses `^GIT_CONFIG`), and it is dropped even when the values agree.
9. **The push URLs are bound end to end (review 2 N-1).** With a destination, the plan digest also covers `pushUrlsDigest` of the URLs git-ops read (`remote get-url --push --all`), git-ops forwards that digest on the push request, and the service's own read just before the spawn must hash the same (`remote_refused` otherwise). So a user-level `pushInsteadOf` written after the approval (which GIT-SNAP-1, a repository-config snapshot, never reports) is `plan_changed` at the spend or refused by the service, not a push elsewhere.
10. **The spawn phase is bounded and watched (review 2 N-2).** Each read of the service's remote check is bounded at 3 s (two reads, under the host's 10 s spawn bound), and the runner watches the request's signal while the spawn is pending: a cancel answers at once and a terminal that still arrives is killed.
11. **25 s for the whole push (review 2 N-3, a product limit).** The bound covers the network push itself, and the push-time scan and the spawn round trip share the method's 30 s. A first push of a large branch can be `E_UNAVAILABLE` (the group killed; a retry is a no-op push once a later one lands). Raising it needs the method timeout raised with it and the mutex hold accepted; that belongs with S5, when the push terminal is attached and the user can see progress.

## Residuals

- **Check-to-spawn window (B-1).** The service's remote check and the push are two processes; a configuration written between them (a CLI run in another terminal, a surviving hook child) is not seen by Axis at all if it is user-level, and only at the next re-take if it is the repository's. The alias pins still stop the alias route in that window; a `git-remote-<t>` program on an absolute `PATH` entry outside the checkout does not (it needs a write outside the worktree, as the user). Same class as R-H1.
- **`PATH` and the daemon's view.** `PATH` is filtered but not compared with the daemon's; which `ssh` the push runs can still differ from the one `ssh -G` resolved (RR-11, unchanged).
- **Handler cancellation, end to end, is untested.** The runner (abort kills the group) and git-ops (the signal reaches the command) are tested; that the handler passes the daemon's request signal is a one-line call the rig cannot exercise (it cannot time a request out). The real hanging-ssh test covers the runner's bound.

- **Push-then-fail.** A push that reached the remote and then timed out or lost its status is `E_UNAVAILABLE`; the retry is a fresh tier 4 request and a no-op push (the idempotency decision in `daemon-host-git.md`).
- **Re-point between the last check and git.** The destination and the push URLs are re-derived and compared at the spend, under the mutex, and the service compares its own read of the URLs just before the spawn (decision 9). What remains is the gap between that read and git's own read of the configuration: a repository change there is reported by a later re-take; a user-level one (`~/.gitconfig`, the XDG file) is not reported by anything, since GIT-SNAP-1 covers repository configuration only.
- **Windows** is unverified (no hooks-off directory is wired, so the pinned push form is refused there, as the pinned commit is).
