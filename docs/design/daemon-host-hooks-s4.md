# H9-hooks slice S4, part 1: push through the pty process, hooks off (implementation notes)

Status: part 1 BUILT. Design: `docs/design/daemon-host-hooks.md` §5.2 (push as a terminal-bound run), H-5, H-7, H-10, and `docs/design/daemon-host-git.md` (push, scan base per destination, P1e and P1f). Part 1 replaces the S1 guard (`push_not_available`, S1 note part 2, departure 2) with a real push. Part 2 (`pre-push`) is not built; see "Split" below.

## Split: why S4 is two parts

§5.2 runs `pre-push` with the push and checks its path "as in step 4": git's per-hook answer and the raw repository-level `core.hooksPath` stored in the GIT-SNAP-1 snapshot (layout version 3), plus the pinless scope read. That resolution is slice S2, which is not built (the snapshot is still layout version 2), and the reply's `hooks.prePush` is part of the S3 contract work. So:

- **Part 1 (this):** the push itself, with every repository hook pinned off. This is the default (`axis.git.runHooks` is off unless the user turns it on).
- **Part 2 (after S2 and S3):** with `runHooks` on, resolve and check `pre-push` (`hook_path_unseen`), let git run it in the push terminal, report `hooks.prePush`, and refuse `hook_failed` on a non-zero exit with the challenge already spent. Until then a push with `runHooks` on over the pty process is refused `E_UNAVAILABLE` before the scan and before any challenge (H-5: never pushed without the hook it should run, never run unchecked).

## Departures and decisions

1. **No terminal is granted yet.** §4.2 and §5.2 grant the push terminal to the workspace's terminal and attach before the spawn. The UI side is S5; until then nothing attaches and the service drops the output (it never reaches the daemon either way). The verdict is unchanged.
2. **The destination joins the digest (stricter than the design text).** The design said the approved plan's digest is what is pushed; the digest did not name where. It now does, only when the caller passes a destination (git-ops' other callers keep their digests).
3. **The ssh used for the push is the pty process's.** The push runs with the pty process's startup environment (`PATH`, `HOME`, `SSH_AUTH_SOCK`); the scan-base key is resolved daemon-side with the daemon's view (`daemon-host-git.md`, "Which ssh"). The entry must start both with the same environment (RR-11 residual unchanged). A message cannot set `GIT_SSH*` (`env_denied`).
4. **Repository transport settings that run a program are left to the drift gate.** `remote.<r>.receivepack` (run through the shell for a local or `file://` remote), `core.sshCommand` and `push.gpgSign` with `gpg.program` are repository or user configuration, as for a push from a terminal; a change to the repository's is a GIT-SNAP-1 drift, refused before the push (`git_drift`). The window between the last re-take and git's start is R-H1's push half.
5. **`MIN_GIT_VERSION` does not gate a push.** The floor exists for lazy fetches in plain execs; a push is itself a transport run. `GIT_NO_LAZY_FETCH=1` is set as on every exec.
6. **A failed push says only its exit code.** git-ops used to put git's sanitised stderr in the error text (review N-4); the pty run returns none (H-7), so the text is the exit status for every runner.

## Residuals

- **Push-then-fail.** A push that reached the remote and then timed out or lost its status is `E_UNAVAILABLE`; the retry is a fresh tier 4 request and a no-op push (the idempotency decision in `daemon-host-git.md`).
- **Re-point between the last check and git.** The destination is re-derived and compared at the spend, under the mutex, after the drift re-take; a change after that and before git reads the config is the same window as R-H1 (a drift a later re-take reports).
- **Windows** is unverified (no hooks-off directory is wired, so the pinned push form is refused there, as the pinned commit is).
