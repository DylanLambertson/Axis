# Composer runtime in the daemon host (Phase 1b, daemon side)

- **Status:** Proposed. Tickets C1, C8 (approval preview) and the full S4 caps are on main. Ticket C2 (compare-and-swap writes and drift notices) is built on branch `feat/composer-cas` (section 4); everything else is a plan.
- **Date:** 2026-11-05.
- **Depends on:** `docs/ROADMAP.md` Phase 1b and its gate lines, `docs/PRODUCT.md` scenarios 1 and 6, `docs/design/tool-broker.md`, `docs/design/daemon-host.md` (sections 2 to 5, 9), `docs/design/daemon-host-compose.md`, `docs/design/axis-agent-shell.md` §6, `docs/design/axis-agent-shell-policies.md` §3.3 to §3.8, `docs/PROVIDERS.md`.
- **Goal:** the smallest vertical slice in which a composer agent runs on the MOCK provider through the daemon host: start a run in a workspace, read its activity, route tool calls through `@axis/broker` with the approval policy (DMN-3), audit every approval and side effect (DMN-5), stop at the per-run budget (PRV-6), keep broker-launched children on the PTY-2 allow-list, and recover the run state from the journal after a kill.

## 2. Gaps

1. **No composer contract.** `daemon-host.md` 4.2 names `axis.runs/1` (`start`, `cancel`, `get`, `list`) and `axis-agent-shell.md` §6 its `start` payload, but nothing exists in `@axis/protocol`. There is no server push (`daemon-host.md` 4.1, ticket E1), so the activity stream must be a polled read (`events` with a cursor).
2. **No broker approval adapter.** `ToolBroker` takes an `ApprovalHook`; nothing turns it into a challenge the user sees in `axis.approvals/1.pending` and answers with `resolve`, and nothing hands the broker the user's grant.
3. **No run loop.** Nothing drives provider turns, executes `tool_use` blocks through the broker, feeds results back, or maps a budget refusal to a recorded run reason.
4. **No binding.** Nothing builds a `ToolBroker` over the host's worktree locator (DMN-2), the audit log and the clock, or a guarded provider in the daemon.
5. **Journal fields.** `agent_runs` has no mode, provider, model, usage or budget columns, and no per-run activity table, so after a restart `get` cannot say which model a run used or how much it spent (C1 reports them as `null`, see 4.2; ticket J2).
6. **Composer recovery.** `Journal.recover` moves a RUNNING composer run to BLOCKED, but a QUEUED composer run is left QUEUED (`@axis/runs` cancels only `kind: cli`).
7. **Native confirmation for broker calls.** A `destructive` or `privileged` broker call should be a tier 4 challenge with the native dialog; the native bridge is reachable only through the RPC gate.

## 3. Contract: `axis.runs/1` (`packages/protocol/src/composer-runs.ts`)

The id is the one the design documents already use. It is not `axis.cli-runs`; the two are distinct contracts with distinct run kinds. No payload carries a path, a command, a credential or a tool definition (DMN-2, PRV-2).

| Method | Side effect | Tier | Idem | Trust | Actors | Request | Response |
|---|---|---|---|---|---|---|---|
| `start` | write | 2 | req | registry | user | `{ workspaceId, mode: ask/edit/agent, prompt (1..32768), providerId, modelId }` | `{ run, replayed }` |
| `cancel` | write | 2 | req | | user | `{ runId }` | `{ run }` |
| `get` | read | 0 | none | | user | `{ runId }` | `{ run }` |
| `list` | read | 0 | none | | user | `{ workspaceId?, limit? (1..200) }` | `{ runs }` |
| `events` | read | 0 | none | | user | `{ runId, afterSeq?, limit? (1..200) }` | `{ events, nextSeq, complete, available }` |

`run` is `{ runId, workspaceId, mode, providerId, modelId, state, reason, createdAt, startedAt, endedAt, live, awaitingApproval, usage }`; `mode`, `providerId`, `modelId` and `usage` are `null` when the daemon no longer holds them (after a restart, until J2). An event is one of `state`, `text` (model output, at most 4096 characters, control and invisible characters escaped by the daemon), `tool` (name, `ok` or `error`, a closed reason), `approval` (name, `requested`/`approved`/`denied`/`expired`/`withdrawn`, the challenge digest the UI matches with `pending`, the display paths and broker reasons it covers, and on `requested` the `preview` of what the call will do, see 4) and `usage`. `events` returns `available: false` for a run whose activity is no longer held (restart, eviction).

Attachments (`axis-agent-shell.md` §6) are additive and come with the IDE context work; `cancel` replaces the shell design's `cancel(runId)`.

## 4. Host structure (H9/H10 patterns)

```text
src/ports/composer.ts        ComposerRunsService (what handlers see), ComposerEngine (what the service sees)
src/handlers/composer-runs.ts  axis.runs/1 over the port; registerComposerRunsHandlers(registrar, deps)
src/composer/errors.ts       closed error map (fixed text, closed reasons)
src/composer/activity.ts     bounded per-run event rings
src/composer/loop.ts         the turn loop: provider turn, tool calls through the engine, results back, fan-out caps
src/composer/preview.ts      the approval preview (C8): tier, protected flag, bytes, SHA-256, scanned and escaped head
src/composer/service.ts      journal transitions, one active run per workspace, budgets, cancel, recovery
src/gate/run-approvals.ts    broker ApprovalHook over the ONE ChallengeManager of createApprovals
src/bindings/agent.ts        the only file that imports @axis/broker: ToolBroker per run, tools, registry over the locator
```

- **Registrar only.** `compose.ts` builds the binding and the service and calls `registerComposerRunsHandlers(registrar, ...)`; handler code never sees the daemon, the challenge manager or the broker. `@axis/broker` joins `HOST_BINDING_PACKAGES` in `test/packages/imports.test.mjs`: only `src/bindings/*.ts` may import it.
- **Closed errors.** Every handler error is a `DaemonError` with fixed text and a `reason` from a closed set (`composer/errors.ts`), the shape of `runs/errors.ts` and `git-errors.ts`. Nothing a provider, the broker or the journal said is forwarded. Run reasons in the journal are short upper-case codes (`BUDGET_TOKENS`, `PROVIDER_ERROR`, `USER_CANCELLED`, ...).
- **Minters.** The composer mints no capability and no principal. The grant the broker receives is built inside `ChallengeManager.consume`'s action, which runs only after the user resolved the challenge in its window and only for the run's own requester and connection (APR-1).
- **Identity of a run.** Each run acts as `agent:composer.<runId>` on the synthetic connection `run.<runId>`; the challenge is issued to the window that started the run. The model gets no way to resolve: `axis.approvals/1.resolve` is a user-only row, the handler refuses any other actor, and the manager refuses a non-user resolver (three layers, DMN-3).
- **Approval flow (C1).** Broker decides `approve` (tier at or above the floor, or a protected path) -> `run-approvals` issues a tier 3 challenge (`contract axis.runs`, `method toolCall`, `args { runId, tool, digest, tier }`, target `run:<runId>`, content digest = the broker call digest) and lists it for the window -> the activity stream shows `approval requested` with the paths and reasons -> the user calls `axis.approvals/1.resolve` -> on `approved`, `consume` spends it and returns `{ approved, approvedBy: "user", approvalId: "chl:<ref prefix>", digest, expiresAt }` to the broker, which verifies it again -> `broker.decision` records approver, approval id and expiry. Deny, expiry (challenge TTL), a burned challenge and run cancellation all decline; cancellation withdraws the challenge. A `destructive` or `privileged` call is declined until C4 (fails closed, no native dialog yet).
- **Budgets (PRV-6).** One `createRunBudget` per run, passed to the guard as `RunOptions.budget`. The guard asks it before every provider request; a refusal stops the loop before the request and the run ends FAILED with `BUDGET_<DIMENSION>`. Limits come from `ComposeOptions.composer.budget` (default 200,000 tokens and 50 requests; a cost cap is optional because the mock prices but J2 does not persist cost yet).
- **PTY-2.** The broker builds every child environment with `buildToolEnv` over the host's `ports.env`; C1 registers no command tool, so no child is started by a composer run yet. C3 adds command tools and the gate test that dumps a child's environment.
- **Approval preview (C8, review r1 S2).** The user never answers for content they were not shown. While a call is inside the broker, `bindings/agent.ts` holds its arguments as parsed by the tool's own schema (the one the broker parses with; at most 16 calls of a run at once, more are refused `too_many_calls`). When the broker asks its hook, the binding recomputes the broker's digest with the broker's own `callDigest` from the request (tool, worktree, actor, tier, the `access:path` operations and command lines) and each held call's arguments, and previews only the call whose digest equals the one the challenge is bound to. No match (for example a path the broker shows cut to 200 characters, or one with a control character: such a path can never be approved, an availability limit until the broker hands the hook its exact digest input), an unknown tool or a preview that cannot be built declines the call before any challenge exists; the broker records the decline. The preview (`approvalPreviewSchema` in the contract) carries the broker tier recorded at issue (the digest covers it), whether a protected path (WT-3) is written, and for a write the UTF-8 byte count and SHA-256 of exactly the bytes the call writes and a head of at most 2048 UTF-16 units, cut on a code point boundary, every code point activity text refuses (controls, bidi, format characters), the blank letters U+115F, U+1160, U+2800, U+3164 and U+FFA0 and every combining mark past two in a row escaped as `\u{hex}`, and a backslash written `\\`, so the escaping is reversible (review c2 N1, N2). The whole content first goes through `@axis/secret-scan` (plain text, `refuse` mode) and the host redactor: a finding is listed by rule name (`redactor-match` for the redactor), the head is then the redactor's output, and it is shown only if neither detector finds anything in it; a scan that cannot complete shows no head and lists `scan-incomplete`. **A protected write (WT-3) is put to the user only when the head is its whole, clean content** (`shownWhole`): a payload past the 2048-unit head, any finding, or an incomplete scan declines the call before a challenge exists, so a `Makefile` write padded to push `curl ... | sh` past the head is refused, not approved on size and hash (review c2 S1). Protected files are small; a larger one, or one whose content trips a detector, cannot be written by a composer run until a paged detail exists. The contract refuses a `requested` event without a preview, a later state with one, and a whole, clean, non-empty content shown as nothing. The preview is on the `approval` event of `events` (no new method): while a run waits for an answer its loop emits nothing else, so the event cannot be evicted before the answer; its head counts against the run's activity text bound. The event's `digest` is the one `axis.approvals/1.pending` lists, so the UI shows the preview next to the challenge it answers. Only `read_file` and `write_file` have a preview; any other tool is declined at approval until it has one, so C3 must add the preview of its command lines with its tools.
- **Fan-out caps (review r1 S4; C1, completed on `feat/composer-c2`).** Each cap ends the run FAILED with its reason from the closed set `TOOL_LIMIT_REASONS`; exactly the cap is allowed. Checked for a whole reply before any of its calls runs (a reply over a cap runs none): calls per reply (16, `TOOL_CALL_LIMIT`), calls per run (128, `TOOL_CALL_RUN_LIMIT`), nesting depth of one call's input (8, `{}` is 1, `TOOL_INPUT_DEPTH`; the walk is iterative and stops one past the cap), UTF-8 bytes of the JSON inputs per reply (2 MiB, `TOOL_INPUT_LIMIT`) and per run (8 MiB, `TOOL_INPUT_RUN_LIMIT`). Checked after each call (it ran and is audited, but its result is not kept): UTF-8 bytes of results per reply (1 MiB, `TOOL_RESULT_REPLY_LIMIT`) and per run (4 MiB, `TOOL_RESULT_LIMIT`). An input that cannot be measured counts as over the cap. The caps come from `ComposeOptions.composer.toolCaps` (partial, defaults `DEFAULT_TOOL_CAPS`); an override that is not a positive safe integer is refused when the service is built, so the host does not start. With at most 8 live runs this bounds what the loops hold to about 8 x 12 MiB of tool traffic as UTF-8, twice that as UTF-16 strings.
- **Compare-and-swap writes and drift notices (C2, policies §3.3 and §3.4).** `read_file` answers `digest: sha256:<hex>` on its first line, then the text; `write_file` takes `base`, the digest the model last saw for the path (`absent`, the default, for a new file), and answers with the new digest. The write runs under the workspace's write lock: the project mutex Axis commit and push take, entered with `ProjectMutex.exclusive`, because the loop runs in the async context of the `start` call that held the mutex and plain `run` would treat that stale context as holding it. Inside the lock the broker's `swapContained` (`packages/broker/src/swap.ts`) writes a temporary file next to the target (`O_CREAT|O_EXCL|O_NOFOLLOW`, verified like any open), then: for a create, `link`s it to the name, which fails if anything appeared there; for a replace, opens the current file (`O_NOFOLLOW`, verified), hashes it through the descriptor, compares with `base`, then checks again after the hash (the descriptor's identity, size and times, a second hash, the parent, the name still naming that file), keeps the old mode, and only then renames the temporary file over the name. Any mismatch refuses `E_CONFLICT` / `stale` with nothing changed at the path, and the model is told to read the file again; Axis never merges. The residual window of §3.3 item 5 (a writer outside the lock between the last check and the rename) is detected through the still-open old descriptor and reported to the model (`lostChange`). Before each model turn after the first, the binding re-checks every path the run read or wrote (at most 256, hashed only when its identity, size or times moved, at most 1 MiB each, through broker containment) and the loop adds a notice after the tool results: `changed`, `removed` or `unreadable` per path, at most 32 listed and the rest counted, each path display-escaped and JSON-quoted with `<` and `>` escaped, inside an `<axis-drift-notice ... content="untrusted">` block that says the paths are data, not instructions. The run's own writes are recorded as seen, so they are never drift; each change is reported once.
- **Shutdown (review r1 S1).** At the final anchor the composition stops every loop, waits a bounded time (`composerSettleMs`, default 1 s, its timer always cleared) for running calls to record their last rows (a cancelled approval records its withdrawal), then seals the composer and challenge audit writers (`audit_sealed`): a row that arrives later is refused (the broker fails the call `audit-failed`) and is never written after the final checkpoint. A `broker.decision` row with no `broker.result` row at the tail of the chain therefore means the call was cut off at shutdown (review r2 N5); the host logs `composer_unsettled` and still exits 0, because the chain is covered by the anchor. Only a call that takes time to end can reach the bound in C1; C3 (commands that take time to kill) adds a case where a result is recorded after more than 0 ms of waiting (review r2 N2).
- **Recovery.** Shutdown aborts every loop and the service then writes nothing (nothing may write after the final anchor); the journal still says RUNNING and the next start's `Journal.recover` makes it BLOCKED / `INTERRUPTED_BY_RESTART`. The composer service's own startup step cancels a QUEUED composer run (`CANCELLED / INTERRUPTED_BY_RESTART`). Nothing is resumed. Activity is in memory only (`available: false` after a restart) until J2.
- **Workspace guards.** A workspace with a QUEUED or RUNNING run is already refused by finalise and remove (`assertNoActiveRun` reads the journal for every kind). One active composer run per workspace is enforced by the service under the project mutex.

## 6. Open questions

1. **Contract name.** `axis.runs/1` (as in `daemon-host.md` 4.2 and `axis-agent-shell.md` §6) next to `axis.cli-runs/1` reads as if one were a subset of the other. Keep it, or rename to `axis.composer/1` before any client exists? C1 keeps the documented name.
2. **Default budget.** 200,000 tokens and 50 requests per run, no cost cap by default. Owner to set the product defaults and whether a cost cap is mandatory once a priced provider is connected.
3. **Tier of an approved write.** C1 issues tier 3 (no native dialog) for every approval the broker asks for, protected paths included; only `destructive` and `privileged` are refused until C4. Should a protected-path write (WT-3) also require the native dialog? Either way it needs the content preview of C8 first (review r1 S2), now built (section 4).
4. **Who may resolve.** The challenge goes to the window that started the run. If that window closes, the challenge stays pending until it expires and the run then fails the call; should another window of the same workspace be allowed to answer?
5. **Mock in production (review r1 N6).** A production compose serves `providerId: "mock"` while `axis.providers/1.list` returns `[]`. C5 reconciles the two lists; should a release build opt the mock in only through `ComposeOptions.composer`?
6. **Events naming (review r1 N8).** `axis.runs/1.events` next to the `axis.events/1` contract (E1) reads oddly, and E1's `runs` topic carries no run kind, so a client cannot tell `axis.cli-runs` from `axis.runs`. Decide with question 1, and add the kind to E1's run topic when it meets C1.
7. **Replay order (review r1 N5).** The service checks for an active run before the journal's idempotency replay, so a retry whose daemon-side key entry is gone while its run is still RUNNING answers `active_run` rather than `replayed`; the daemon's store answers such a retry first in practice, and after a restart the run is BLOCKED. Accepted for C1.
8. **BLOCKED runs.** After a restart a composer run is BLOCKED and nothing resumes it; C1 lets a new run start in that workspace. Should `cancel` of a BLOCKED run be required first (it is allowed and moves it to CANCELLED)?
