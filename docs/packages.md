## Protocol contracts

- **Wire names.** The contract id is what `contractIdSchema` allows (lower-case letters, digits, `-`), so the CLI run contract is `axis.cli-runs/1`, not `axis.cliRuns/1`. Method names may be camel case (`restoreFromRunBase`).
- **Errors from schemas.** A guarded schema fails with one fixed issue. The daemon's pipeline additionally forwards field paths only (`pathsOf` in `packages/daemon/src/pipeline.ts`), never messages or values.
- **Handlers return plain trees.** A handler result is checked by the response schema: a value reached twice (one frozen object reused for two providers), an accessor or a Proxy fails the reply with E_INTERNAL. Return fresh plain data, or deep-copy first.
- **Lists are bounded, and the bound is what a message can carry.** Responses are limited by the message walk (10,000 values, 1 MiB): a run is sixteen values, a challenge nine. `axis.cli-runs/1.list` takes a workspace and a `limit` of at most 500 and answers `{ runs }`, the newest runs oldest first, with no cursor, exactly as `RunSupervisor.list` does. `RunSupervisor.list` accepts a limit up to 1000, but 1000 runs are 16,000 values and cannot be sent, so its handler clamps to 500. Older runs are not reachable until follow-up R1 below. `axis.audit/1.list` pages with `afterSeq` and a `limit` of at most 200 (`AuditLog.list` takes the same). `axis.approvals/1.pending` lists up to 1024 challenges; the handler must shorten each `targetSummary` to at most 192 characters, or the listing fails as a whole. The cut keeps a head and a tail joined by an ellipsis, on code-point boundaries (never between the halves of a surrogate pair, which would also fail the listing), as `defaultSummary` in `@axis/challenge` does, so the end of a path stays visible.
- **Copies of other packages' enums** (`RUN_STATE_VALUES`, `RUN_STATUS_VALUES`, `SNAPSHOT_AFTER_VALUES`) are commented with their source in `cliRuns.ts`. `test/packages/protocol-copies.test.mjs` checks the run states against `@axis/journal` and the statuses against `RUN_STATUSES` in `@axis/runs`. The snapshot values have no runtime export in `@axis/runs` (a type only), so they are not checked. The same test fails if `@axis/protocol` gains a dependency on any `@axis/*` package.
- **Display text is held to rules the producers may not follow.** `projects.list` names are at most 80 characters with no edge whitespace or control characters; the host must normalise a repository folder name when it registers a project, or `projects.list` fails as a whole. Provider display names (at most 128) and descriptions (at most 512) have no edge whitespace and no control, bidi, zero-width or line-separator characters, and challenge `targetSummary`, `contract` and `method` in `pending` have no control, bidi, zero-width or line-separator characters. `@axis/providers` is not that strict: it accepts a display name with edge spaces or control characters, and the protocol refuses it. So the earlier statement that the protocol's bounds "match or are looser" than `@axis/providers` was wrong for display text. We keep the stricter rule (text the user reads must not reorder or hide itself); a provider registered with such a name makes `providers.list` fail, so `@axis/providers` should adopt the rule or the host must normalise names before registering.
- **Providers.** `connectionId` must match the vault's connection name pattern; `@axis/providers` still accepts any 1 to 256 characters there and should adopt the same pattern.

### Decided: the tier of `axis.cli-runs/1.start`

`start` stays tier 2 with `sideEffect: "write"`, no challenge, a trusted project, `user` actors only and an idempotency key, as the design table (`docs/design/daemon-host.md` on branch `docs/daemon-host-design`, section 4.2) says. The owner's delegate decided this. Threat model EXT-2 listed "start CLI run" among actions that go over the bridge with a challenge. Its wording is amended (see "Amendment 2026-11-04" under the EXT-2 row of the threat model) to say that a CLI run does only what the user could do themselves in a terminal, and that the launch dialog carries the disclosure (the run is governed by the CLI's own permissions, see `packages/runs/src/copy.ts`). A broker identity in 1b must not be given `start` at the contract minimum, because that would give it an unbrokered process.

## Audit anchor (requirement on the daemon)

A hash chain cannot show that its newest events were deleted. Threat model G-11 is closed only if the daemon keeps a copy of the chain head outside the database. The daemon MUST:

1. Call `AuditLog.checkpoint(previousAnchor)` after each append batch (for example at the end of each handled request that wrote events, and on clean shutdown). It verifies only the events after the previous anchor, so the cost is proportional to the batch, and returns `{ seq, hash }`; it throws `E_INTERNAL` if the chain is already broken, and a broken chain is never anchored. Run the full `checkpoint()` (no argument) at startup.
2. Persist that anchor outside the journal database, where an attacker who edits the database file does not also write (for example the OS keychain through the main process, or a store owned by a different principal). A separate file under the same OS user does not count: the attacker in DMN-5 runs as that user and can rewrite the file as easily as the database. Where it is stored is daemon work and is not decided here.
3. At every start, before accepting work, call `verify({ expectedHead: anchor })` and treat `ok: false` as an integrity failure (surface it to the user; do not silently continue). A longer chain that still contains the anchor is valid.

Persist an anchor only after the commit it covers is durable. `openDatabase` uses `synchronous=FULL` everywhere and, on macOS, also `fullfsync` and `checkpoint_fullfsync`, because plain `fsync` there does not flush the drive cache. That makes a commit survive a process kill on every platform, and power loss on Linux (`fsync`), Windows (`FlushFileBuffers`) and macOS (F_FULLFSYNC), provided the drive or virtualisation layer honours flushes; if it does not, nothing in the database can tell. A power cut that loses commits an anchor already covered shows up at the next start as `truncated`, and must be reported as "the database is behind the anchor", not silently treated as tampering or ignored.

Without the anchor, `verify()` detects edits, deletions in the middle and reordering, but not removal of the tail. The chain gives local tamper evidence only (ADR 0003 D5). The append-only triggers stop no one with write access to the file (`DROP TRIGGER` works), and the chain has no key, so everything after the last anchor can be recomputed. It does not stop an attacker who can also rewrite the anchor.

## Single instance (requirement on the daemon)

`Journal.recover(lock)` interrupts every RUNNING run, which is correct only when the previous writer is dead. The daemon MUST take the exclusive instance lock (`acquireInstanceLock(dir)` from `@axis/audit`, a pid and process-start-time lock file in the database directory) before opening the journal, and hold it until exit. `recover()` refuses to run without a held lock, and the lock must be the `InstanceLock` object `acquireInstanceLock` returned (an object literal with the same fields is refused) and must guard the directory of the journal's own database file. A second daemon on the same directory fails with `E_CONFLICT`.

## Principals

`createdBy` and every transition `actor` come from the authenticated connection (`ConnectionContext`), never from a request payload. The journal requires `createdBy` on `createRun` (there is no default) and scopes idempotency keys by it, so a caller that could choose its own principal could both forge attribution and replay another principal's keys. Completing a run in review (REVIEWING to COMPLETED) is the person's act in Phase 1a (diff review), and the journal does not take the string `"user"` for it. It needs a `UserPrincipal`, an unforgeable brand (a class with a private field and a module-private mint symbol; a literal, `Object.create` of the prototype or a `structuredClone` fails the check with `E_POLICY_DENIED`). The only way to get one is `userPrincipal()` from the subpath `@axis/journal/daemon-principal`, which is not exported from the package root, and `test/packages/imports.test.mjs` allows only the daemon's connection layer (package `daemon`) to import it. The daemon mints it from the attested connection (the `ConnectionContext` the renderer cannot influence) at the moment the person acts, and never from a request payload or a field a client supplied.

## Data directory

`openDatabase` and `acquireInstanceLock` create a missing data directory 0700. An existing directory is never chmod-ed, and is refused (`E_INVALID_ARGUMENT`, `details.reason` one of `symlink`, `not-owned`, `group-writable`, `world-writable`, `dotdot-path`, `parent-group-writable`, `parent-world-writable`, `parent-sticky-foreign-owner`) when its last component is a symlink or the real directory is not owned by the current user or is writable by group or others. The path is judged as the kernel resolves it: a `..` after a symlink leads to the symlink target's parent, and a missing directory is never created through a path that contains `..`. The database files themselves are always 0600. File system errors from these steps are mapped into the closed error set without the path: a bad path (too long, a component that is a file) is `E_INVALID_ARGUMENT`, an operating system permission refusal is `E_POLICY_DENIED`, a full disk or a busy file is `E_UNAVAILABLE`, and `details.errno` carries only the errno name.

The check is deliberately narrow:
- For a directory that already exists, only that directory is judged, not its ancestors. (For a MISSING one, the nearest existing ancestor must not be writable by group or others, unless it is sticky like `/tmp` AND owned by root or the current user (`parent-sticky-foreign-owner` otherwise, because the sticky bit does not restrict the owner), and a symlinked ancestor is judged by its target.) A parent that another user can write to (and that is not sticky) lets them rename the checked directory away and plant another, so the data directory must sit under a parent only the user controls, which the per-user application-data directory does.
- Only mode bits and the owner are read. POSIX ACLs (macOS `chmod +a`, Linux `setfacl`) can grant access that the bits do not show, and are ignored.
- Windows has no owner or mode bits to read here, so the check is skipped; the per-user profile directory is protected by its ACL.

## Journal and audit share one connection

`Journal.open(db, { audit })` rejects (`E_INTERNAL`) an `AuditLog` that was created on a different `DatabaseSync` handle. Sharing the handle is what makes a state change and its audit event commit or roll back together.

## Using `@axis/challenge`

The daemon owns one `ChallengeManager` and wires it like this. Identity (`actor`, `connectionId`, `windowId`) always comes from the transport, never from a request payload.

1. A tier 3-5 request arrives without `approval`. The daemon computes `contentDigest` (SHA-256 of what will be destroyed) and calls `issue({ contract, version, method, args, target, contentDigest, actor, connectionId, windowId })`. `args` is required: the request params without `approval`. The manager computes the request digest itself (see "Shared request digest"), so the contract, version and method are bound to it. The daemon may also pass its own `requestDigest` as a cross-check; it must equal the computed one. `target` must be a canonical daemon id such as `workspace:<id>`, never a path or alias. `targetSummary`, if given, is built by the daemon from `path` or `public` fields. It answers `E_APPROVAL_REQUIRED` with the returned challenge. For tier 4-5 it also calls `takeNativeProof(challengeId)` once and passes the proof to main over the privileged port; the proof never goes to a renderer or an agent.
2. The renderer's `axis.approvals/1.resolve` goes to `resolve({ actor, windowId }, params)`. Main's dialog result goes to `confirmNative({ windowId }, { challengeId, proof, confirmed })`.
3. The requester retries with `approval: { challengeId }`. The daemon recomputes `currentContentDigest` under the lock that protects the content and calls `consume(challengeId, { actor, connectionId }, { contract, version, method, args, target, currentContentDigest }, action)`. The daemon keeps no map from challenge id to grant: the id alone is not a credential.
4. When the request is aborted or its connection closes, the daemon calls `withdraw(challengeId, { actor, connectionId })` or `withdrawConnection(connectionId)`. The challenge is dropped (resolve and consume then refuse its id with `E_POLICY_DENIED`). A withdrawn challenge still counts against the requester's per-actor, per-window and total quotas until its original expiry, so an issue/withdraw loop gets `E_BACKPRESSURE`; `withdrawConnection` leaves the same tombstones, so reconnecting in a loop cannot get past the quota (the tombstones are bounded by the same quotas). `withdraw` returns `{ withdrawn: true }`, or `{ withdrawn: false, reason: "spent" }` when the approval was already consumed (the action ran or is running) and `reason: "ended"` when it was already denied, expired or burned. The audit write is best effort.
5. Every error is a `ChallengeError` over the protocol code set. `error.toWire(correlationId)` is for standalone use. Under `@axis/daemon`, the integration adapter does not call it: it maps `ChallengeError` to the daemon's `ApprovalError` (`E_POLICY_DENIED` and `E_CONFLICT` stay; any other code, or `executed: true`, becomes `E_INTERNAL`) and lets the daemon build the wire answer and own the correlation id. `details.executed` tells the caller whether the action ran. When the action throws a protocol-shaped error (a valid code, retryable flag and message), `consume` rethrows that code and message verbatim with `executed: true`, so a domain error's message must be safe to show the user (details, causes and stacks are dropped); any other throw becomes `E_INTERNAL`. The audit sink must be synchronous: a returned promise counts as a failed write.

The package limits open challenges per actor in one window (`maxOutstandingPerActor`, so one window cannot lock the same user out of another), per actor across windows (`maxOutstandingPerActorOverall`, the backstop), per window and overall; `method` is any name `@axis/protocol`'s `methodNameSchema` accepts, such as `restoreFromRunBase`; the per-window rate limit from ADR 0003 belongs to the daemon.

### Shared request digest

`requestDigest({ contract, version, method, payload })` binds a challenge to the exact request. It is, byte for byte:

```
sha256hex(JSON.stringify(["axis.request/1", contract, version, method, canonicalJson(payload)]))
```

- `contract` is the bare contract id exactly as `@axis/protocol` defines it (`contractIdSchema`, for example `axis.worktrees`), never the slash form `axis.worktrees/1`. `version` is the separate integer major version (`contractVersionSchema`). `issue` and `consume` validate both with those schemas and refuse anything else.
- `method` is the method name as sent.
- `canonicalJson(payload)` is a string: the payload's JSON text with object keys sorted recursively and a top-level `approval` field removed. It is embedded in the array as a string element, not as a nested object, so no delimiter can be forged.
- The digest function itself accepts any strings; only `issue` and `consume` enforce the schemas.

Fixed vectors (`sha256hex` as lowercase hex):

| contract | version | method | payload | digest |
|---|---|---|---|---|
| `axis.worktrees/1` (function-level only) | 1 | `remove` | `{id:"ws-1",deleteBranch:false}` | `ccb3a71aa0bc5bd6db5ccfe6fe9a09abef12092dce13ba4f6d99e929a30e0fd7` |
| `c` | 1 | `m` | `{b:[1,{z:null,y:true}],a:"x"}` | `de8399306f850ad7498d82c8f95ec94ca317181b2422480425c52ad8ed55e596` |
| `axis.worktrees` | 1 | `remove` | `{id:"ws-1",deleteBranch:false}` | `adb7a157e75395816cf74974fbdfa2b5bdf32831996a578ff80cdb46fe9d2735` |

`@axis/daemon` implements the identical function and pins the same vectors; the two copies must stay in step. The shared function moves into `@axis/protocol` later, and both packages will then import it.
## Using `@axis/git-ops`

### Finding git (CLI-1, CFG-1)

`createNodeRunner` never spawns a bare `git`, and git is found by `resolveExecutable` from `@axis/pty-policy` (the same resolver the pty launcher uses; `@axis/git-ops` depends on `@axis/pty-policy`, never the reverse). Empty, relative and `.` PATH entries are ignored; on Windows UNC, device, root-relative and quoted entries are refused as well (a network share would run code from elsewhere and leak credentials at launch) and only `.exe` and `.com` count. That behaviour is kept on purpose.

**Not yet one rule for the whole product.** `@axis/worktrees` has its own `resolveGitPath` (`packages/worktrees/src/git.ts`). It searches absolute PATH entries too, but it does not exclude worktree folders, does not compare real paths, accepts an absolute `explicit` as given, and on Windows looks only for `git.exe` without the UNC, device and quoted-entry refusals. So `@axis/git-ops` and the pty launcher share one rule and `@axis/worktrees` does not. Named follow-up **FU-GIT-RESOLVE**: point `@axis/worktrees` at the shared resolver (or have the host resolve once and pass `gitPath` to both), with the worktree package's tests passing. It is not done in the git-ops change because it edits another package that has its own owner.

- **The host resolves once.** At daemon start it calls `resolveGit(env, process.platform, excludeDirs)` with EVERY registered worktree and git directory in `excludeDirs` (so a git planted in a sibling worktree whose folder is on PATH is never chosen) and passes the result as `createNodeRunner({ gitPath, excludeDirs: () => allWorktreeRoots })`. The path is cached for the life of the runner. The PATH used for any later lookup is a copy of the environment taken when the runner is created (`env` overrides it), not `process.env` at request time.
- **Default.** Without `gitPath` and without `excludeDirs` the runner refuses every request with `E_UNAVAILABLE` ("host must supply gitPath or excludeDirs"): it could otherwise pick a git planted in a sibling worktree whose folder is on PATH. Tests may set `allowUnpinnedGit: true` to get the weaker lookup (only the request's own directories excluded); a daemon must not. With `excludeDirs` alone the runner resolves on the first request, excluding that request's directories and `excludeDirs()`. `excludeDirs()` must return a plain `Array` (a Proxy, a subclass, an accessor, a hole or an extra property is refused; elements are read by index inside the guard) of at most 1024 absolute, normalised path strings; a throw, a Promise, a string, `undefined`, a relative, empty or unnormalised entry, or a longer list is `E_UNAVAILABLE` with fixed text (nothing the host returned or threw is echoed). The list is copied on each lookup and duplicates (by real path) are dropped. Without a host `gitPath`, a list that covers none of the request's directories (for example `() => []`) is refused with `E_UNAVAILABLE` too, because it would re-open the sibling-git hole; `allowUnpinnedGit` (tests only) skips that check.
- **Per request.** The real path (symlinks resolved) is compared by path component with the request's cwd, `--work-tree` and `--git-dir`; a git inside any of them is `E_POLICY_DENIED` (`<worktree>/..bin/git` is inside; a symlink into the worktree is inside). The real path is what is spawned. A relative `gitPath` is refused, and so is a relative or empty cwd, `--work-tree=` or `--git-dir=` (git would read it against cwd), and any caller argv carrying `-C` or the space-separated `--git-dir <dir>` and `--work-tree <dir>` forms (git-ops builds only the `=` forms; the others are not parsed, so they are refused). `--exec-path` in any form is refused, and so is a request environment that sets `GIT_EXEC_PATH`, `GIT_CONFIG*`, `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE`, `GIT_SHALLOW_FILE` or `GIT_TEMPLATE_DIR`. Git's option area (everything before the subcommand) is a closed set: only `--no-pager`, `--no-replace-objects`, `--version`, `--literal-pathspecs`, `--no-optional-locks` (the last two are added by `@axis/broker`), `--git-dir=<abs>`, `--work-tree=<abs>` and `-c <key=value>` are accepted, and any other argument that starts with `-` there (`--shallow-file <file>`, `--config-env`, `--`) is refused, so an option git takes a separate value for cannot hide a later one. A `-c alias.*`, `include.*` or `includeIf.*` key is refused (an alias beginning with `!` runs a command, and an include can load one). The refusal text is fixed and echoes nothing from the request. Other config keys and variables that run programs (the HOME config, `GIT_SSH_COMMAND`, `core.*` program keys) are owned by `prefix()`, `guardedRunner` and GIT-ENV-1, not by the runner. A pathspec such as `-Cache` after the subcommand is data. The runner reads `argv` and `env` once and checks and spawns only those copies. Git's own children (helpers, hooks, external commands) get a PATH without empty, relative or Windows-unsafe entries and without any entry that lies in the request's directories, by spelling or through a symlink.
- **Gone.** If the cached file has vanished (a package manager replaced it) the runner looks again, through `resolveGit` only, with `excludeDirs()` applied to that lookup too, and retries once; failing that, `E_UNAVAILABLE` and nothing is spawned. **An injected `gitPath` with no `excludeDirs` is not looked up again at all:** the request fails with `E_UNAVAILABLE`, and the runner stays unavailable for good (there is no setter): the host must build a NEW runner (and new `GitOpsDeps`) with its full list. The same holds after any `E_UNAVAILABLE` for a vanished injected path.
- **Accepted limit.** A request whose directory is an ancestor of git's folder (cwd `/`, or a worktree at `$HOME` with git under `~/.local/bin`) is refused with `E_POLICY_DENIED`: git would then be "inside" the request. It fails closed and Axis worktrees live under `axis.worktrees.root`, so this is accepted.
- **Children.** The environment git runs with gets a PATH holding only plain absolute entries outside the request's directories, so git's helpers and external commands are not found through an empty, relative or worktree entry. The working directory of a request is unchanged (callers pass the work tree).
- Not covered: the pty-side runner (not in this repository yet) must resolve the same way; an absolute PATH entry inside a worktree the host did not list is trusted.

### Bound commit contract (what `@axis/review` implements against)

There is one commit path, and it is bound. `executeCommit(deps, input)` and `planCommit` take:

| Field | Type | Required | Meaning |
|---|---|---|---|
| `worktree` | `WorktreeRef` | yes | The registered worktree (never discovered). |
| `reviewedTreeHash` | `string`, full lower-case object id | yes | The tree the user reviewed. The index must write to exactly this tree. |
| `message` | `string`, 1 to 64 KiB, no NUL | yes | Cleaned like git's default `stripspace` (trailing white space, repeated blank lines, outer blank lines, one final newline); `commit.cleanup` is ignored. |
| `expectedParent` | `string`, full lower-case object id | **yes** | The commit HEAD pointed at when the diff was reviewed. |
| `expectedBranch` | `string`, the SHORT name `axis/<slug>` | **yes** | The branch checked out at review time. Same slug rules as always. Not `refs/heads/axis/<slug>`, never `null`; a review with no branch (a detached HEAD) cannot be committed: git-ops refuses it. |
| `author` | `{ name, email }` | no | Only compared with the configured identity; never passed to git. |

Who refuses what. `@axis/git-ops` refuses a missing, `null` or full-ref `expectedBranch` or `expectedParent` (`E_INVALID_ARGUMENT`, no git call), and a detached or unborn HEAD at commit time (`E_POLICY_DENIED`). `@axis/review`'s `PinnedCommitInput` must carry `expectedParent: string` and `expectedBranch: string` (the short name), and `handoff()` refuses a detached HEAD or an unborn branch itself, so the user sees a review-level reason. review-core refuses a detached HEAD and an unborn branch itself; git-ops refuses them too, as a second line. Do not rely on review to be the only check. (An earlier version of this page said review's type was "exactly this shape"; it was not: review sent `refs/heads/axis/<slug>` and `null`.)

Errors. Argument shape: `E_INVALID_ARGUMENT` for a malformed `expectedParent`, and for an `expectedBranch` that is not a string or is a full ref (`refs/...`); `E_POLICY_DENIED` for a short name that is not `axis/<slug>`, a detached HEAD, an unborn branch, a CLI run in progress, drift, and an identity that is not the expected one. `E_CONFLICT` carries `details.reason`:

| `reason` | Meaning |
|---|---|
| `head_moved` | The checked-out branch is not `expectedBranch`, HEAD is not `expectedParent`, or the compare-and-swap found the branch elsewhere. |
| `operation_in_progress` | Unmerged index entries, or `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `REBASE_HEAD`, `rebase-merge`, `rebase-apply`, `sequencer`, `BISECT_LOG` or `BISECT_START` exists (paths from `git rev-parse --git-path`, so a linked worktree's own directory is the one asked). |
| `stale` | `assertReviewFresh` refused. |
| `ref_update_failed` | The branch is still at `expectedParent` but git could not update it (a lock, for example). The message is fixed text; git's output is not carried. |

`E_CONFLICT` without a reason: the index does not write to `reviewedTreeHash`. `E_INTERNAL` with `details.updated: false`: the commit object that was built failed verification (not exactly the expected parent, or not the reviewed tree) and the branch was not touched; `updated: true, rolledBack: false`: the update succeeded but the branch no longer points at the new commit when read back, and nothing was rolled back. `E_UNAVAILABLE`: git could not run, or the repository state could not be read, so an operation in progress cannot be ruled out.

Order, with the caller holding the workspace lock:

1. `check()`: argument checks; CLI-run and drift gates; the branch must be `expectedBranch` and HEAD `expectedParent`; operation in progress; the index must write to `reviewedTreeHash`; the identity checks; the signing setting; then, as the last step before git builds anything, `assertReviewFresh`.
2. `commit-tree [-S] -p <expectedParent> -F - <reviewedTreeHash>` in the **pty context**. Signing and identity come from the user's configuration; `commit.gpgsign=true` adds `-S` (commit-tree ignores the setting by itself), and an unreadable value refuses. It creates an object and moves no ref.
3. The new object is verified with the daemon-side git: its parent list is exactly `[expectedParent]` and its tree is `reviewedTreeHash`.
4. The checked-out branch and the operation state are asked again.
5. `update-ref refs/heads/<branch> <new> <expectedParent>`, an atomic compare-and-swap (packed refs included). Of two commits racing on one parent exactly one wins; the other fails and leaves the ref untouched.
6. The ref is read back.

What this cannot close, accepted: HEAD switched to another branch between step 4 and step 5 still moves the reviewed branch (its content is what was reviewed; it is just not checked out); a `MERGE_HEAD` or `CHERRY_PICK_HEAD` written after step 4 does not affect the commit but stays for the user's next commit; a branch also checked out in a second linked worktree leaves that worktree's index stale, as with `git commit`. `planCommit` returns the `commit-tree` command; run alone it only makes a dangling object, so use `executeCommit`.

`GitOpsDeps` has two optional members:

- `assertReviewFresh(worktree, reviewedTreeHash): Promise<void>` (G2). **It refuses by throwing and must resolve `undefined`**: any returned value (`false`, a `{ fresh: false }` result) is also a refusal, so a `Freshness` object cannot be wired through by mistake. A throw becomes `E_CONFLICT` `stale`; a `GitOpsError` with another code (for example `E_UNAVAILABLE`) passes through. The daemon wires it to `checkFresh` and throws when `fresh` is false.
- `fileExists(path)`: the existence test for operation markers (default `pathExists`: a missing path is false, any other error, such as `EACCES`, refuses).

Exports for building hardened calls (G4): `daemonGitFor(worktree, deps, extraEnv?)` (`extraEnv` may hold only `GIT_INDEX_FILE`, an absolute path; any other name is `E_INVALID_ARGUMENT`), `checkWorktree`, `OBJECT_ID`, `DaemonGit`, `assertNoOperation`, `OPERATION_MARKERS`, `resolveGit`.

#### Commit hooks (decided 2026-11-04)

**The daemon never runs repository commit hooks.** The bound commit is `commit-tree` plus a compare-and-swap `update-ref`: neither runs `pre-commit`, `commit-msg`, `post-commit` or `reference-transaction`, and the daemon must not run hooks (GIT-3). So `axis.git.runHooks` does not change what `@axis/git-ops` does on commit.

**NOT BUILT YET: today no commit hook runs; building the hook step is a named follow-up (ticket H9-hooks).** Until it is built an Axis commit runs no `pre-commit` or `commit-msg` hook (the outcome rejected below), and the gate at ROADMAP line 40 stays open.

When `axis.git.runHooks` is on, **the host** will run the repository's `pre-commit` and `commit-msg` hooks in the Axis pty process context. The sequence, all UNDER the daemon's commit lock (so the hooks sit inside the CLI-run refusal and the GIT-SNAP-1 re-take that threat-model row GIT-3 and ROADMAP line 49 rely on):

1. the daemon refuses while a CLI run is active and re-takes GIT-SNAP-1, refusing on unacknowledged drift;
2. the host runs `pre-commit` and then `commit-msg` against a TEMPORARY index and scratch checkout of the reviewed tree. The hooks never see the user's worktree or real index (a partial-accept review differs from both);
3. a freshness re-check (`assertReviewFresh`), with the drift check, runs again;
4. then `commit-tree` and the compare-and-swap `update-ref`.

Decided behaviour for the points that were open:

- **A hook that modifies files** makes the commit refused with a hook-specific reason, not a bare `stale`. The changes are discarded and the user is told to run the formatter and review again. Axis commits exactly the reviewed tree.
- **A message rewritten by `commit-msg`** is shown to the user before it is committed, and the message that is committed is recorded in the audit event.
- **`post-commit`** and the other hooks are not run in 1a.

This matches policies section 6.1 (hooks run in the pty process, not the daemon). Push is unchanged: `pre-push` runs in the pty process, and `runHooks: false` still adds `--no-verify` to it. `git hook run` needs git 2.36, so with the 2.24 floor the host invokes the hook file directly.

This amends ADR 0004 section 4, decision Q-4 and threat-model control GIT-3 (an "Amendment 2026-11-04" paragraph in each, not a rewrite).

Rejected: accepting no commit hooks at all (ratify the current behaviour, make `runHooks` push-only). It is simpler, but a repository's `pre-commit` checks (formatters, secret scanners, lint) would silently stop applying to commits made from the review, and the policies document already promises them.

Rejected: running hooks in the daemon. Hooks are user-controlled code, and in 1b the daemon holds the vault (GIT-3).

`planPush` and `executePush` take a required `baseSha`: **the last commit that was actually pushed** (or the workspace's recorded base before the first push), read from the journal by the daemon. The secret scan covers `baseSha..tip`, every commit's patch and its commit message, so everything reachable from `baseSha` is assumed to be on the remote already. If a workspace's base is a local commit that was never pushed, its ancestors go out unscanned: the journal must record the sha of each successful push and supply it next time. A `baseSha` that is not in the repository or not an ancestor of the branch (history was rewritten) is refused with `E_CONFLICT`. Never derive it from a ref under `refs/remotes`: the code in the worktree can write those.

A plan that needs confirmation (warn mode findings, binary files, a scan that was too large) carries `tip` and `digest`. The caller passes `confirmed: true` and `confirmedPlan: { tip, digest }` to `executePush`, which re-scans and answers `E_CONFLICT` with `details.reason: "plan_changed"` if either differs. The runner reports `truncated` when it cut off output, and any truncated scan call fails closed.

Commit messages are scanned as bytes: the runner is asked for `raw` stdout (one character per byte) and must say it complied, or the scan fails with `E_UNAVAILABLE`. The scanner gets the UTF-8 reading and, when the commit declares an `encoding` other than UTF-8 (git decodes a message from it when showing it, and `i18n.commitEncoding` makes git write one), the message decoded from that encoding too, so legacy commits such as ISO-8859-1 are scanned and confirmed like any other. A message is refused in both scan modes (`E_POLICY_DENIED`, naming only commit ids) when it holds a NUL byte (UTF-16 and NUL padding), has bytes that are invalid in its declared encoding (UTF-8 when none), or declares an encoding the runtime does not know. Axis's own commit pins `i18n.commitEncoding=utf-8`.

This closes byte-level encodings only. Valid text that merely looks different (zero-width, bidi or fullwidth characters, or control characters inside a key) is not normalised and is not caught: the scan guards against accidental leaks, not a determined author. A commit object over 8 MiB is checked only up to that limit, and the scan reports it as too large (refused in refuse mode, confirmable in warn mode, unless the cut splits a multibyte character, which is refused in both). Only the first `encoding` header counts, as in git, and the whole object (headers included) is decoded from it with a strict decoder; a commit with two or more `encoding` headers is refused, and so is one whose decode fails (the runtime's decoder is stricter than git's, so there is no weaker fallback). For the ISO-2022-JP family the scan also reads the bytes with shift sequences and control characters removed. Labels git accepts but the runtime does not know are refused with a hint to push from a terminal, except a few common aliases (CP932, eucJP, CP936, CP949, ISO-2022-JP-2).

The node runner starts git in its own process group so a timeout kills git's children. A normal daemon exit kills the live groups; a crash of the daemon cannot, and may leave an orphaned git running until it finishes.

## Wiring the daemon

`@axis/daemon` never imports `@axis/challenge`. The product wiring supplies an `ApprovalGate` adapter, and the pipeline owns the whole approval sequence: a handler never sees a challenge id and the gate cannot answer "confirmed" without spending a live challenge.

- No `approval` in the request: the pipeline calls `gate.issue(input, content)` and answers `E_APPROVAL_REQUIRED`. The adapter calls `manager.issue({ contract: input.contract, version: input.contractVersion, method: input.method, args: input.args, requestDigest: input.digest, target: content.target, contentDigest: content.contentDigest, actor: input.actor, connectionId: input.connectionId, windowId: input.identity.windowId, tier: input.tier })`. `args` is required and `requestDigest` is only a cross-check, so both must agree. For tier 4 and 5 it also takes `takeNativeProof(challengeId)` once and passes it to main, never to a renderer.
- With `approval: { challengeId }`: the pipeline calls `gate.execute(input, approval, content, action)` inside the method's content lock. The adapter calls `manager.consume(approval.challengeId, { actor: input.actor, connectionId: input.connectionId }, { contract, version, method, args, requestDigest: input.digest, target: content.target, currentContentDigest: content.contentDigest }, action)`, translates a `ChallengeError` as described under the adapter rules and returns what `action` returns (the daemon ignores that value). The handler runs inside `action`, so it can only run with a spent approval, and it receives only `ctx.approved` (`method`, `target`, `requester` and the adapter's `capability`). The `approval` field is stripped from its payload.
- Content: a tier 3+ method registers a hook, `daemon.register(contract, version, handlers, { content: { method: (ctx, payload) => ({ target, withLock }) } })`. `withLock(fn)` takes the lock that protects the content and calls `fn(contentDigest)`. The digest is read under that lock at issue and again at execute, and the handler runs under the same lock, so "the content is unchanged right now" and the action cannot be separated. A method without a hook (including a policy-raised tier) is approved against target `request:<digest>` with the digest as content digest. Review each hook with the destructive call it guards; a handler must check `ctx.approved.target` against what it is about to act on.
- Replay: a tier 3+ replay from the originating connection returns the stored result. From any other connection it needs its own approval, and the stored result is returned inside `execute`.
- Withdrawal: a cancel or timeout before the approval was spent calls `gate.withdraw(challengeId, { actor, connectionId })` once; a closed connection calls `gate.withdrawConnection(connectionId)` once. Both are best effort.

Adapter rules:

- Pass both `args` and `requestDigest: input.digest` to `issue` and `consume`; the manager computes its own digest and a mismatch is `E_INVALID_ARGUMENT`.
- `gate.withdraw` calls `manager.withdraw(challengeId, { actor, connectionId })` and `gate.withdrawConnection` calls `manager.withdrawConnection(connectionId)`; the adapter may return their result (an object or a count) or discard it, the daemon ignores it. A withdrawn id is refused with `E_POLICY_DENIED` afterwards.
- Handler errors are mapped by the pipeline inside `action` and never pass through `consume`. A handler that fails (or returns an error) has still spent the approval; the user confirms again and the idempotency key is freed. `action` throws only for an abort or a failed decision-audit write.
- Map `ChallengeError` to `ApprovalError` for refusals: `E_POLICY_DENIED`, `E_CONFLICT`, `E_BACKPRESSURE` (issue out of capacity) and `E_INVALID_ARGUMENT` (arguments over 16 KiB canonical or not a plain object, a target that is not display-safe or over 1024 characters) keep their code; any other code is `E_INTERNAL`. An action failure (`ChallengeError` with `executed: true`; the flag is in `detail`, singular, not `details`) is re-thrown as it is, as `ApprovalError(code, true)` or the original error, and answered `E_INTERNAL` (or the abort code). Never call `error.toWire`: the daemon owns the wire answer and the correlation id.
- Mint the handler's capability inside the action, after the spend: for worktrees, call `markDiscardConfirmed` from `@axis/worktrees/daemon-confirm` there, bound to `content.target` and `content.contentDigest`, and pass it as `capability` in the `ConfirmedAction` given to `action`. The handler reads `ctx.approved.capability` (non-enumerable, never serialised or logged) and never mints one itself.
- Identity comes from the daemon only: pass `input.identity.windowId`, `input.connectionId` and `input.actor` (attested by the transport) to the manager, never a value from the request payload or the envelope.
- `manager.withdrawConnection` can throw `E_INTERNAL` (for example on a bad clock reading). The adapter should catch it; if it throws anyway the daemon's close path still completes and reports the error locally through `onInternalError`.
- Quotas are described under "Using `@axis/challenge`". Closing a connection leaves tombstones until they expire (at most one challenge TTL), so a legitimate window reload is held to its quota for up to one TTL.
- The challenge manager's audit sink must be synchronous (a returned promise counts as a failed write, so every `issue()` would fail closed). Never hand it a journal sink with an async `append`; wrap that in a synchronous buffer or queue.
- `issue()` out of capacity is `E_BACKPRESSURE` (retryable): ask-and-cancel cycles also count against the actor's challenge quota until withdrawn, so map it through, never to `E_INTERNAL`.
- Tier 3+ methods must declare `approval` as an optional field of their strict request schema: `register()` throws otherwise, and a policy-raised tier on a method without it is refused with `E_POLICY_DENIED` (audit reason `not_approvable`) before any challenge is issued.
- The daemon runs the action at most once and answers with the action's own outcome, never with `execute`'s return value; a gate that returns before the action completed gets `E_INTERNAL`, and the slot stays held until the handler settles.
- A challenge issued for a request that was aborted during an async `issue` is withdrawn on a best-effort basis; if that fails it holds its slots until the challenge TTL (60 s by default).

| Daemon field | Challenge field |
|---|---|
| `input.contract` (bare id), `input.contractVersion` | `contract`, `version` |
| `input.method`, `input.args` | `method`, `args` |
| `input.digest` | `requestDigest` (cross-check) |
| `input.actor`, `input.connectionId` | `actor`, `connectionId` |
| `input.identity.windowId` | `windowId` |
| `content.target`, `content.contentDigest` / digest under lock | `target`, `contentDigest` / `currentContentDigest` |

Destructive library entry points are protected independently of the daemon: `@axis/worktrees` requires a token that only `markDiscardConfirmed` can mint, and that function is exported only from the `@axis/worktrees/daemon-confirm` subpath. Only the integration package that implements the gate adapter may import that subpath, never a handler. This cannot be enforced inside `@axis/daemon`, so it is a review rule.

## Using `@axis/daemon-host` (scaffold)

The host is the one place that chooses and connects the daemon's services (`docs/design/daemon-host.md`). This change is ticket H1 only: the pieces every later ticket builds on. It has no handlers, no contracts and no startup sequence, and it opens no socket.

- **Boundary.** It may import every other package and nothing in `packages/*` imports it. `test/packages/imports.test.mjs` enforces that, and restricts `@axis/journal/daemon-principal` to `src/handlers/review.ts` (and still the `daemon` package), `@axis/worktrees` to `src/bindings/worktrees.ts`, `@axis/worktrees/daemon-confirm` to `src/gate/worktrees-confirm.ts`, and `@axis/runs` and `@axis/review` to `src/bindings/*.ts`.
- **`parseHostConfig(input, redactor)`** parses the supervisor's `init` payload with a strict Zod schema: `dataDir` and `worktreeRoot` (absolute), `platform`, `logLevel`, `devDiagnostics`, `devMemoryIdempotency` (needs `devDiagnostics`), `attestationKey` (base64url, canonical, 32 to 96 bytes, not low entropy), `contracts` (allow-list) and `limits`. Before any schema reads it, the input is walked for a `Proxy` at any depth and then checked with the protocol's bounded `inspectMessage` (no accessors, class instances, shared references or forbidden keys), so no trap or getter runs. An unknown key (including `__proto__`), a wrong type or any of the above is refused with `E_INVALID_ARGUMENT` whose detail lists failing paths and issue codes, never a value (exit code 78). The result is frozen and `attestationKey` is a getter returning a fresh copy on every read; the holder of a copy zeroes it. On success the key is registered with `redactor` (base64url, base64, hex, padded or not, either case, plus the forms `Redactor` derives), so a log line cannot carry it.
- **Ports** (`src/ports/`, interfaces and closed value sets): `StoragePort`, `WorktreesService` (the `axis.worktrees/1` shapes, id-based), `WorktreeLocator` (workspace id to a `WorktreeRef`, shared by git-ops, worktrees and runs), `RunsService` (the `RunSupervisor` shapes for start, stop, get, list and `hasActiveRun`, checked against the real class by `test/types/runs-port.test.ts`, with an opaque single-use `RunTrustAttestation` and its `RunTrustMinter`; the contract is `axis.cli-runs`), `PtyPort`, `ReviewService`, `GitPort` (exactly `GitOpsDeps`: one runner that routes by `req.context`, the two environments and the guards), `TrustRegistry` (for create, commit and push; a CLI run start is gated by the attestation), `Clock`, `RandomSource` and `SupervisorChannel`, gathered in `HostPorts`. Handlers see these and nothing else.
- **`Disposables`** holds every timer, listener and child, and disposes newest first, one at a time. `dispose()` is idempotent and never rejects; a disposer that calls `dispose()` on its own registry gets an empty result at once instead of waiting for itself. Each disposer is bounded (default 5 s; `0` means the default, never unbounded) and failures are closed-set summaries. Timers are `unref`ed (a test starts a process that must exit by draining). Registering after (or during) dispose runs the new disposer at once and throws. The function `add` returns rethrows the disposer's raw error; log it through `summarizeError`.
- **`createLogger`** writes one JSON line per record from a closed set of events and field names, every string through the process `Redactor` first and only then cut (256 characters on a code point boundary; over 4096 it becomes `[truncated]`, never a prefix). Values that are not scalars are dropped and counted; an `error` field is summarised, never serialised; a `Proxy` or getter is never read. The queue is bounded (`queueSize` 1 to 100000), a failing sink never throws into the caller, and it starts no timer or listener. Field values are strings, not a closed set: handlers must pass ids, never paths or text.
- **`summarizeError(e)`** returns `{ name, code?, errno? }` built from closed sets only (known class names, ADR 0003 codes, OS and runtime codes). It reads own data properties through `getOwnPropertyDescriptor`, never reads `message`, `stack` or `cause`, and never runs a getter or a `Proxy` trap. A stack under `devDiagnostics` is not provided yet.
- **`EXIT`** and `exitCodeForStartupError`: 0 clean, 1 unsettled work, 70 internal, 75 lock held (`E_CONFLICT`), 78 bad configuration or data directory, 79 degraded.
- **`axis.providers/1.list` handler** (`src/handlers/providers.ts`, ticket H11): `createProvidersHandlers({ providers })` answers from the `descriptor` of each guarded provider (`GuardedProvider`, so the mock today), copying only the contract's fields (a label, a credential or any other property of a descriptor is never copied), sorted by connection id. The daemon validates the request against the contract before the handler runs (design section 4.3), so the handler does not parse it; it checks its own answer with the protocol schema. An aborted request is `E_CANCELLED`, and a hostile descriptor, an answer that fails its schema (too many providers, a duplicate connection id, a bad origin) or a throwing source is `E_INTERNAL`. Errors are `DaemonError` from `@axis/daemon` (the only class `toWireError` passes on with its code and message; anything else reaches the client as an opaque `E_INTERNAL`), each with a fixed message that never contains request, descriptor or error text. It makes no network request.

- **Policy (ticket H6, `src/policy/`).** `rules.ts` is the served rule table, one line per `<contract>/<major>.<method>` with its tier, actors (`user` only in 1a) and trust mode (`none`, `registry`, `per-start`). `planned.ts` holds rows for methods no contract serves yet (`axis.git/1`, `axis.review/1`, `discard`, `setUserEditing`); they are denied like any unknown method. `RuleTablePolicy` implements the daemon `Policy`: no row, any actor other than `user` (agent, daemon, malformed), a malformed input or a throw is `deny`; it raises a tier, never lowers it. `registry` rows need the attested `identity.trusted` and the live `InMemoryTrustRegistry`; `per-start` (CLI run start) is gated by the single-use attestation and is also refused after an explicit revoke (TRU-2); nothing here stops a running run. Trust has a window level and a workspace level (no project level: a connection identity carries no project id, and the design's `trust.set` is `{ windowId, workspaceId?, trusted }`); a revoke at either level wins. **Documented deviation from design 6.2 ("the default for an unknown window is untrusted"):** a workspace decision holds in every window, because trust belongs to the source repository and a revoke must not be escapable by opening another window; a bare window with no decision is still untrusted and a grant is still ANDed with the attested `identity.trusted`. The registry is capped at 4096 entries and never evicts: a full table refuses a new grant, and a revoke it cannot record latches it saturated (every subject untrusted and revoked, every `set` throws) until restart. A `per-start` row ignores the attested `identity.trusted`; the per-start `trust.check` (H10) must refuse. `policySurface(config.contracts)` returns the registry, rules and planned rows filtered together; H2 must use it for both `RuleTablePolicy` and `checkCoverage` so they cannot diverge. `checkCoverage` (unit test now, host startup later) fails when a served method has no rule, a rule has no served method, a rule tier differs from the contract tier, or a planned row is already served; later tickets pass handler and audit-action sets through `also`.

## Using `@axis/review`

Everything goes through the `GitOpsDeps` the daemon already holds (daemon context only, hardened prefix) plus a `TempIndexProvider` that hands out a file in the daemon's private data directory. The package has no file system access.

1. `ReviewSession.start(deps, { worktree, against })` reads the worktree **once** into a tree object (`worktreeTree`, a temporary index and `add -A`) and lists the changes against `against`. Use the recorded base for the overall "what did the run change" list. A review that will be committed must be against HEAD; `build()` refuses (`E_CONFLICT`, `details.reason: "not_head"`) otherwise.
2. `session.hunks(path)` returns the hunks of a text file, or `fileLevelReason` when only a whole-file decision is offered (binary, symlink, submodule, add, delete, type change, mode only, unsafe path, over a size limit, or a diff that did not rebuild the new file exactly). `acceptFile`, `acceptHunk`, `rejectFile`, `rejectHunk` record decisions; nothing is accepted by default, and every hunk accepted is the whole file.
3. `session.build()` returns a `ReviewBinding` (the reviewed tree, the worktree tree it came from, HEAD and the branch it was reviewed against, a digest for the audit event). Only a session can mint one; a plain object is refused.
4. Under the daemon's worktree lock, `prepareCommit(deps, binding)` refuses (`E_CONFLICT`, `details.reason` `stale` or `head_moved`) when any file, HEAD or the branch changed since the review, then replaces the **real index** with the reviewed tree (any staging done outside Axis is replaced) and returns `previousIndexTree` and `handoff(message, author?)`, which re-checks HEAD, the branch and the index and returns the input for `executeCommit` with `expectedParent` and the short `expectedBranch` (both required; a detached HEAD is refused by `prepareCommit` with `detached_head`; git-ops must check them: design §6, G3). It refuses while a merge, cherry-pick, revert, rebase or bisect is in progress (`operation_in_progress`). `ReviewDeps.fileExists` is required. Files with a content filter (git-crypt, LFS) are listed but cannot be accepted (`filtered_path`; judged from the base tree's attributes as well as the current ones, with `core.ignorecase` both ways; every file is refused with `attributes_untrusted` when `.git/info/attributes` holds an attribute line or the user or system attributes file defines a macro, quoted or not; a line there that only names a filter does not block); accepting a file whole with `acceptFile` when its text has lines the view cuts needs `{ acceptTruncated: true }` (`hasCutLines(path)` says so; `build` refuses otherwise, for a whole file, a partial one and a symlink target the view cut); files over the 50 MiB snapshot cap are in `session.skipped`. A sparse checkout is refused (`E_UNAVAILABLE`). `checkFresh` is the same check without staging, for the UI.
5. Reject only leaves a change out of the reviewed tree. Writing it back out of the worktree is `axis.worktrees/1.discard`, with its backup ref and approval, and is not here.
6. `secretWarnings`, `computeOutsideAgent`, `previewSide` via `session.preview` and `escapeForDisplay` are the data for the push dialog, the drift indicator, the preview and every untrusted string. Show `displayPath`, never `path`.

Proposed changes to `@axis/git-ops` (not made here, see `docs/design/review-core.md` §6): an `assertReviewFresh` hook next to `assertNoDrift`, `CommitInput.expectedParent`, and exports for `daemonGitFor` (with an extra environment) and `checkWorktree`.

## Calling `@axis/worktrees` from the daemon

Use one `WorktreeManager` per daemon process, built with the pinned absolute git path and a `refuseIfActiveRun` hook. Its in-process mutex assumes a single instance, and each mutating call also takes a pid and start-time lockfile (workspace operations lock the worktree admin dir; create and sweep lock the common dir).

`finalise` and `remove` are destructive, so they are tier 3 or higher and go through the approval pipeline in "Wiring the daemon". The content hook for them is:

- `target`: `workspace:<id>`, never a path.
- `withLock(fn)`: takes the daemon's per-project mutex, calls `assertNoDrift(path)` (a `git-drift` `E_CONFLICT` means the user reviews the change and the daemon then calls `acknowledgeDrift(path)`), then `previewDiscard(path)` and calls `fn(scan.fingerprint)`. The fingerprint is passed as the `contentDigest`, read at issue and again at execute under the same lock. It is a SHA-256 over metadata, not over file content: the path, status, size and mtime of each dirty file, plus the path lists of the large, ignored and nested-repository or unsupported entries. This is the TOCTOU binding: if such an entry is added, removed, or changes status, size or mtime after the user approved, `consume` refuses and nothing runs. A rewrite that keeps a file's size and mtime (for example with `touch -r`) does not change it; no data is lost then, because the backup captures the content at execute time.
- The native confirmation text must show `skippedLarge`, `ignored` and `skippedUnsupported` from the preview, because a backup does not hold them.

Inside the `action` (after the approval is spent), call `markDiscardConfirmed({ workspaceId, op, fingerprint }, opts?)` from `@axis/worktrees/daemon-confirm` (never the package root) and pass the result as `discardConfirmation` to `finalise` or `remove`. The token is bound to that workspace, operation and fingerprint, expires after 30 s on a monotonic clock, and is spent by the first call that accepts it, even if that call then fails. It must not cross a JSON boundary or leave the callback.

If the manager still refuses, `E_CONFLICT` carries `details.reason`: `confirmation-stale`, `confirmation-spent` or `confirmation-expired` for a bad token, and `dirty` or `unbacked-data` (with the fingerprint) for a missing one. `remove` with `deleteBranch` also writes and returns `branchBackupRef` before deleting the branch. Errors are always `WorktreeError` with an ADR 0003 code.

Audit and journal: `@axis/worktrees` imports neither. The daemon writes the `@axis/audit` event for each `finalise` and `remove` in the same journal transaction as the workspace state change (`Journal.open(db, { audit })`), including `backupRef`, `branchBackupRef` and the three unbacked lists from the result. The `axis-workspace.json` record in the worktree admin dir is an interim store that the workspace itself can write. Once the daemon passes the `agent_workspaces` row from `@axis/journal`, that row is the source of truth for id, slug and branch, and the admin-dir record must not be trusted over it.
