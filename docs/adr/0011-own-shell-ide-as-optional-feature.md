## Context

### Owner direction (2026-11-26)

> "Lets make the IDE just like a feature, not like a core piece. Eventually this will branch off to other AI needs like social media management, etc. So just have it as a useful feature that can be used when needed, but don't build it around the IDE. This meaning lets make our own like thing instead of using Code OSS. I still want like a file manager, + and - for git changes, etc."

The owner also said the product will be rebranded later (new name, logo and colours).

What this changes:

1. The product is a home for AI work in general. Code is the first use case, not the frame. ADR 0004 already made Agent view primary, but kept the whole app inside a Code OSS workbench, so every surface still lived in an IDE's layout, build, DI and process model.
2. The IDE stops being "fully capable, never reduced" (`PRODUCT.md` §2, ADR 0004 decision 2). It becomes one optional module next to a file manager, a git changes view with stage and unstage (+ and -), a terminal and diff review.
3. A future non-code module (for example social media management) must plug in without touching the IDE module.

### What exists today

- **Product logic sits outside Code OSS already** [V]. 18 `@axis/*` packages under `packages/` (daemon, daemon-host, protocol, journal, audit, broker, challenge, git-ops, git-snapshot, review, worktrees, pty-process, pty-policy, providers, anthropic, vault, runs, secret-scan). Their tests run on plain Node and import only `node:*`, `zod` and `@axis/*` (ADR 0005).
- **Main's control plane is also a package** [V]. `packages/daemon-host/src/main/*` holds the connect broker, the attestation signer, the answers (anchor, native confirm, trust check, settings), the native dialog queue, project actions, the secret store, the pty launch and supervisor, and plugin view identities. They import no `electron`, but they are built on the workbench's model of a window. `connect-broker.ts` takes `windowTrusted` (the identity's `trusted` flag). `project-actions.ts` takes the folder from "the window's opened workspace" and `workspaceTrusted`, which decides `offerTrust`, the dialog's "Add and trust to run" button, the workbench wording and the refusal of Trust. `answers.ts` answers the T3 half of `trust.check` from the Workspace Trust model [V]. The Electron calls themselves (`dialog.showMessageBox`, `safeStorage`, `MessageChannelMain`, `utilityProcess.fork`) are in the overlay adapters `code/electron-main/axisMainSeam.ts`, `axisMainPorts.ts` and `axisMainPty.ts`, about 510 lines [V]. The daemon and pty entry files (`daemon/node/axisDaemonMain.ts`, `pty/node/axisPtyMain.ts`) are in the overlay too; they are small, but they must move.
- **The overlay** is 102 files and about 14.6k lines of TypeScript [V], plus 29 patches, `removals.txt` and `replace/`. Roughly half of it is pure logic with tests: the daemon client, reconnect, event frames and subscription, refresh drivers, the workspace model, approvals, project actions, the changes model and side-panel rules. The other half is DOM views built on Code OSS parts and services.
- **ADR 0002 was never accepted.** Its criteria 1 (full IDE in the custom shell), 4 (sync cost) and 6 (extension matrix) were never measured as passing. Criterion 2's budget was nearly spent: 10 of 12 shell files before React (`axis-shell-stage2-plan.md` §4). React was deferred because the Code OSS pipeline cannot build `.tsx` without about 9 more upstream build files [V, same section].
- **ADR 0003's bridge is built and tested** [V, `main-answers.md`, `renderer-daemon-client.md`]. That covers the main-brokered port, main-minted signed identity, daemon-side validation, the single policy pipeline, challenge approvals and native confirmation over the privileged port. Main-drawn dialogs for tier 4 and up, project add and trust, and the integrations device code (EL-4) are built as well. None of this needs Code OSS. What does need Code OSS is the glue: `IWindowsMainService`, `validatedIpcMain`, `FileAccess`, `IConfigurationService`, the application storage that holds the Workspace Trust model, `getResolvedShellEnv` and `acquirePort` [V].

## Decision 1: app technology

| | Option | For | Against |
|---|---|---|---|
| **A** | **Electron main + the existing daemon and pty utility processes + `axis.*` contracts; our own TypeScript/React renderer** | Keeps everything ADR 0003 proved: `utilityProcess.fork` with a fixed entry, only main can write `parentPort`, `MessageChannelMain` ports transferred with a payload, `safeStorage` for the audit anchor and the vault, modal `dialog.showMessageBox` for tier 4 and up, and sandboxed `WebContentsView` plugin views (ADR 0008). About 510 adapter lines are rewritten. Main's project actions get a new folder source and lose their Workspace Trust inputs (OS-3b). One Chromium on every OS, so CSP and Trusted Types behave the same everywhere. node-pty and Node 24 are unchanged. | A large binary (Chromium; on the order of 100 MB+ [I]) and Electron's release cadence: a major roughly every 8 weeks, with security fixes we must follow. Electron becomes our direct dependency instead of something Code OSS pins for us. |
| B | Tauri 2 (Rust core, system webview) | Small binaries; a Rust core with a capability system; low memory use [I]. | Every main-side primitive ADR 0003 relies on would be re-proved in Rust: window identity, sender-frame checks, port hand-over, secret storage per OS, native modals. The daemon and the pty process are Node, so they would run as sidecars over stdio. The "only main can write the daemon's channel" property would then rest on a different mechanism that would need fresh review. Three web engines (WKWebView, WebView2, WebKitGTK) differ in Trusted Types support, `MessagePort` behaviour and devtools exposure, which triples renderer security testing. 18 packages of tests assume Node. Estimated cost: several weeks before parity with what exists [I]. |
| C | Pure web host (a local server, the UI in the user's browser) | No desktop packaging; the same UI could later be served remotely. | Needs a listening socket, which breaks DMN-4 (no listener in Phases 1 to 3) and puts WEB-1 (token on a local port) on the critical path. It has no native dialog that a compromised page cannot draw or click, so tier 4 and up (EL-4) loses its guarantee. Browser extensions can read the page. It stays a later remote target through `web-host-entry.md` (W1); not the desktop shell. |
| D | Keep Code OSS (ADR 0002) | The full IDE for free; work already done. | Contradicts the owner's direction. Weekly upstream sync cost, the closed workbench layout, Copilot removal patches, no React, and an IDE-shaped core. |

**Decision: A.** The renderer is our own single-page app in TypeScript with React, bundled by esbuild. It has no Code OSS DI, no `vs/*` imports and no Node. React is chosen for its accessible primitive libraries, virtualised lists and wrappers for Monaco and xterm.js. There is one component system; `DEVELOPMENT.md`'s "no competing component systems" still applies. Exact versions of Electron, React, Monaco and xterm.js are pinned in the first scaffold ticket and follow the supply-chain rules in `SECURITY.md`.

What ADR 0003's validation already settles for option A: the identity, signing, single-use, rate-limit and fail-closed behaviour of the connect path, and the answers, are tested on Linux at package level. Only the Electron adapters and the Mac evidence remain. Under option A that remaining work is the same size as before. Under options B and C the package-level proofs would no longer cover the real path.

## Decision 2: process and window model

- **Processes are unchanged:** main, the daemon utility process (`@axis/daemon-host` entry), the pty utility process (`@axis/pty-process`) and one sandboxed renderer per app window. Plugin views stay as ADR 0008 decides: one sandboxed `WebContentsView` each, minted and placed by main.
- **App window:** `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`, `webviewTag: false`, no `remote`. Content is served from a privileged custom scheme registered by main, `axis-app://shell/`, never `file:`. The scheme is a **fixed internal id**, never derived from the brand (see "Stable ids" below). Navigation, `window.open` and new windows are refused (`will-navigate`, `setWindowOpenHandler`). External links go through main's EL-5 path (below). Every permission request and check is denied except `clipboard-sanitized-write`, which Monaco and xterm.js need for copy. Paste works through the native paste event, which needs no permission. `clipboard-read` (the asynchronous clipboard read) stays denied, and that limit is documented. A `webRequest` filter in the window's session refuses every scheme except the app scheme, so the renderer has no network at all; egress stays the daemon's (NET-GATE, egress client).
- **One preload, fixed and small.** It exposes one frozen object with named functions only: `connect(nonce)` (the port hand-over that replaces upstream's `acquirePort` on the `vscode:axisConnect` channel), `projectAction(nonce, action, projectId?)` (never a path: main takes folders from its own picker), `terminalPort(nonce, terminalId)` and `openExternal(url)`. It has no generic `ipcRenderer`, no channel argument and no `send`. ADR 0003 D7's "no new `contextBridge` globals" becomes "exactly this one, pinned by a source test".
- **`openExternal` is decided in main (EL-5).** The renderer is untrusted about where a link came from, so main does not take its word. Main itself allows only `http`, `https` and `mailto`. It shows every link that is not app-internal with its full URL in a main-drawn confirmation before it opens anything. Callers include links in run output and messages, Monaco hover links, xterm.js OSC 8 links and page links. The confirmation is a main dialog outside the challenge tiers (Decision 5 item 2).
- **Sender checks move to our own window registry.** Main keeps a table of the windows it created (id, `webContents`, app URL, the window's project binding), which replaces `IWindowsMainService.getWindowByWebContents`. The ordered checks of `main-answers.md` §2 are unchanged in substance: a registered app window; `senderFrame.url` exactly equal to the app URL main computed; the main frame; not destroyed; the per-window token bucket; the supervisor state. The channel is renamed `axis:connect` because there is no shipped client. Plugin views still never use it.
- **Identity keeps its shape:** a main-minted `connectionId`, `w<id>`, `actor: user`, signed with the generation key. The `trusted` field (the Workspace Trust answer at connect) stays on the wire for compatibility, as `project-registration-and-trust.md` §5.4 already decided, and main always sends `false`. Policy has not read it since S1b. So `@axis/daemon`'s identity schema and the attestation text do not change, and `connect-broker.ts` loses `windowTrusted` (OS-3b). One reader of the field remains: `agents/service.ts` `registryAdmission`, whose default `admitNewHome` ANDs `identity.trusted` and would refuse every new home once the field is always `false`. The composition root already replaces it (`compose-serving.ts`), so OS-3b deletes the default or pins it as unwired with a test.
- **The window-to-project binding is scoping, not a security boundary.** It says which project a window is showing, so main can scope the status answer and its project actions. PV-D1-0's status answer carries it to the renderer as `projectId`, and it is reused, not re-derived. Main sets it from (a) the result of its own folder picker and dialog on Add project, or (b) a project id the renderer asks to open, which main accepts only after the daemon confirms that the id is registered. It never comes from a path the renderer sends. The renderer can switch it with one Open project call, and that is fine **because the binding grants nothing**:
  - Authority for every action comes from the run-trust record of the project the action names, checked per action by the daemon: T1 (main's own record, written only after main's native click), T2 (the repository binding) and T4 (no revoke). The daemon never reads the window binding.
  - A window may therefore act on any project the user registered and trusted through main. Starting a run, committing or pushing from All agents or the project list, for a project other than the one shown, works with no rebind first.
  - A plugin view pinned to its own project (`main/plugin-views.ts`, `gate/project-trust-gate.ts`) keeps working when its host window shows another project. The view's own pinned project is what the action names.
  - Trust and Stop trusting act on the bound project id. Main's dialog shows the name and path that the **daemon** returns for that id, never text from the renderer. A test proves that a renderer-chosen id can only open main's dialog and never sets T1 by itself.
  - A binding change is recorded in main's closed-event log as `binding_changed`, with a count and no id or path. It is not an audit event, because it grants nothing.
- **Main keeps no project store.** `project-registration-and-trust.md` §4.3 holds: the registry of projects, their paths and the run-trust record live in the daemon's journal. Only control messages main sends after its own native click write the trust record, so that record stays main-owned. Main holds only the in-memory window bindings above.
- **ADR 0003 criterion 1 keeps both halves at G0.** The handshake half is unchanged: a second window's connect yields only its own `w<id>`, and it can never obtain or reuse another window's identity, attestation or port. The refusals for a plugin view, a navigated frame and a non-app frame stay as well. The scoping half is new: the status answer and project actions follow the window's own binding. It is labelled scoping, not a boundary.
- **The window registry** prunes everything per window when a window closes: rate buckets, in-flight project actions, the waiting native dialog (cancelled), the binding and the status.
- **Stable ids (rebrand safety).** These are fixed internal ids and are never derived from the brand constant: the app scheme (`axis-app`); the Electron app name, set with `app.setName` before `ready`; the `userData` path, set with `app.setPath('userData', ...)` before `ready`; the data roots (`axisDataRoots`); the `safeStorage` keychain entry, which Electron derives from the app name; the audit anchor's location and record tag; the vault's file names; the macOS bundle id (`appId`) and the code-signing identity (the Keychain item's access list is bound to them, so a re-sign under a new id prompts or denies); the Windows AppUserModelID; the Linux desktop-file name and `WM_CLASS`; and the single-instance lock name. A rebrand changes display strings, icons and colours only, so it cannot orphan the vault or the audit anchor. An acceptance test (plan OS-28) changes only the display brand and checks that the anchor and a vault entry still decrypt and that the renderer origin is unchanged.

## Decision 3: module boundary

### Core shell (always loaded)

Window frame and top bar; the navigation rail and the agent home (project home, All agents); the Space's project list with Add project and trust; agents and groups (ADR 0006); workspaces (worktree list, create, finalise, remove; git-specific, they stay in the core until the project-kinds ADR below, and then move to a code-oriented contribution); runs (CLI and composer) and their activity stream; approvals; messaging threads; tasks; pages; the audit view; settings; the plugin host (placement of ADR 0008 views); the command palette; notifications; the daemon connection and its states; theme tokens and brand.

### Feature modules (optional, each a lazily loaded chunk)

| Module id | What it is | Uses |
|---|---|---|
| `axis.files` | File manager: worktree tree, open a file in a read/edit viewer (single file), create, rename, delete | `axis.files/1` (missing, see the plan), the editor kit |
| `axis.changes` | Git changes: changed-files list, **+ / -** per file and per hunk, diff view, discard, commit, push, open a pull request | `axis.review/1`, `axis.git/1`, `axis.worktrees/1`, `axis.forge/1` |
| `axis.terminal` | Terminals bound to a workspace, split panes, attach to CLI runs | `axis.terminals/1` (missing), `axis.cli-runs/1`, the pty data channel |
| `axis.diff` | Diff review viewer shared by changes and run review | `axis.review/1` |
| `axis.code` | The code editor / IDE view: tabs, splits, find and replace, project search, go to line, outline, open at file:line | the editor kit, `axis.files/1`, `axis.search/1` (missing) |

The **editor kit** (`@axis/ui-editor`) is a shared, lazily loaded wrapper around Monaco (the standalone `monaco-editor` package, MIT; not the Code OSS workbench). It covers one buffer model per file per window and the theme bridge from tokens. Workers are bundled as files by esbuild and loaded from the app scheme, never from `blob:` or `importScripts` of another origin, and are tested under `worker-src 'self'`. The Trusted Types policy names Monaco creates at the pinned version are listed by exact name in the CSP (no `'allow-duplicates'`), and a test fails when a Monaco upgrade adds or renames one. The files viewer, the diff module and the code module use it. Disabling `axis.code` removes the IDE layout, tabs and search, not the single-file viewer.

Not in the code module, by decision: VS Code extensions and the extension host, the debugger, and the Open VSX registry. Language servers are a later item (Phase 2b). They run repository-chosen programs, so they would run in the pty process context, gated by run trust, never in the daemon. TypeScript, JavaScript, JSON, CSS and HTML diagnostics come from Monaco's built-in workers, which execute no repository code.

### The module contract

- A **manifest**: `{ id, version, title, requires: { contracts: ["axis.review/1", ...] }, contributes: { navItems, routes, workspaceTabs, projectHomeSections, commands, settings, intents } }`. `id` is a stable internal id (`axis.<name>`); titles go through the brand and localisation layer.
- `activate(ctx)` is loaded by dynamic `import()` the first time a contribution is used. `ctx` gives: a daemon client that refuses contracts outside `requires` (a convenience and lint target; **the daemon's policy stays the only authority**), the UI primitives, the router, the intent registry, scoped settings and a disposable store.
- **Intents decouple modules.** `openFile { workspaceId, path, line? }`, `openDiff`, `openTerminal`. A module registers as a handler with a priority. With `axis.code` enabled, `openFile` lands in the IDE view; without it, in the files viewer. The core never imports a module.
- **Enforced boundaries.** A lint rule (the repository's import scanner, moved from `scripts/code-oss/` to `scripts/lint/`; see Decision 4) allows a module to import only `@axis/shell-sdk`, `@axis/ui`, `@axis/ui-editor`, `@axis/protocol` types and its own files. The core may not import any module. A bundle-graph check on the production build confirms each module is its own chunk and the core chunk reaches none of them.
- **Enabling.** Modules are on by default and can be switched off per user (application scope). A project hides modules that do not apply to its kind (below).

### How a non-code module plugs in (for example social media management)

It is a first-party module (`axis.social`) with its own nav item, routes and project home section, its own daemon contract (`axis.social/1`) and integrations through ADR 0009's credential proxy. It never imports `axis.files`, `axis.changes` or `axis.code`. What it needs that does not exist yet is in the **core data model**, not the UI. Today a project is exactly one repository (O-2), and every agent has a home workspace that is a worktree (O-3, O-4). A non-code project therefore needs a later ADR introducing project kinds (`repository`, `general`) and agents without a worktree. This ADR only makes that later change local to the daemon and journal. The core shell's code paths must not assume a repository: project home sections that need one (pull requests, changes) are contributed by the code-oriented modules. Third-party extensions remain ADR 0008 plugins (sandboxed views), never modules: modules are first-party code in the trusted renderer bundle.

### + and - (stage and unstage)

| | Meaning of + / - | For | Against |
|---|---|---|---|
| **S1** | **Include in / exclude from the Axis commit**: a per-file and per-hunk selection that the daemon turns into a tree (review-core's accept and reject, REV-1), committed with `git commit-tree` and a compare-and-swap | The commit is exactly the tree the user saw. It fits `axis.git/1.commit`, which takes a daemon-registered `reviewedTreeHash`. It needs no new user-visible staging state. | Differs from `git add`: a `git status` in a terminal does not show Axis's staging. **Today's commit path writes the real index** (below). |
| S2 | Write the real git index (`git add`, `git apply --cached` per hunk) | Matches what users know from other tools | A daemon write to `.git/index` while CLIs may be writing it (lock races). Hunk application on the real index needs a fresh hardened path. The commit would no longer be bound to a tree the user saw unless re-reviewed. |

**Correction to the current code.** `prepareCommit` (`packages/review/src/binding.ts`) stages the reviewed tree into the **real** `.git/index` with `read-tree` before the commit, and restores the old index only when the commit is refused [V]. A successful Axis commit therefore replaces whatever the user had `git add`-ed, and it writes the index that a running CLI may also be writing.

**Decision: S1. Axis staging is canonical, and the only write to the real index is the narrow refresh after a commit (below).**
- New ticket DC-0 (security review): the commit path builds the commit through a **private temporary index** (`GIT_INDEX_FILE` in a daemon scratch directory, as review already does) and never stages into the real index. That changes `@axis/review` (`prepareCommit`) and `@axis/git-ops`: `commit.ts` today runs `write-tree` on the real index and compares it with `reviewedTreeHash`. It either passes the same `GIT_INDEX_FILE` (the one extra environment name git-ops allows) or compares the registered tree directly. The index put-back on refusal (`restoreIndex` in `daemon-host/src/bindings/review.ts`, `handlers/git-commit.ts`, `ports/review.ts`) goes or changes. The sparse-checkout refusal, which exists only because of `read-tree` into the real index, is revisited. The H9-hooks step, when built, runs in the scratch context too.
- **After the commit: a narrow refresh of the real index** (DECIDED 2026-11-26 under the owner's delegation; a 1a-gate requirement; judged sound in review 2 under these conditions). Without it, `git status` in a terminal would show the committed paths as staged reversions, which is not acceptable for a product with a file manager and git changes. The refresh is a real compare-and-swap under git's lock:
  - **Order.** It runs only after the ref compare-and-swap succeeds. It creates `<git-path index>.lock` with `O_CREAT|O_EXCL` (the per-worktree index from `git rev-parse --git-path index`); `EEXIST` means skip, without error. While holding the lock it checks that HEAD still points at the new commit (otherwise it skips). It reads the index into a private copy, edits the copy (`update-index --index-info` with `GIT_INDEX_FILE` set to the copy), writes the result into the lock file and renames that over the index. A separate `ls-files` read followed by `update-index` on the real index is forbidden: a `git add` landing in between would be overwritten.
  - **Exact equality.** Only paths in `diff-tree oldHEAD newHEAD` are considered. Each is compared on stage 0, mode (100755, 120000 and 160000 included) and object id against old HEAD. Absent in both counts as equal, so a path the commit added gets an entry. Absent in the index but present in old HEAD is not equal (`git rm --cached`), so it is left alone. Any entry that differs, including the user's `git add`, is never touched.
  - **Skips.** Entries with skip-worktree, assume-unchanged or intent-to-add are left untouched. The whole refresh is skipped when the split index or the sparse index is on, or when the index has any unmerged entry. A path whose new entry would collide case-insensitively with another entry (`core.ignorecase`) is skipped. Other index extensions are kept as git writes them, or dropped; they are never forged.
  - **No repository programs.** `core.hooksPath` points at an empty directory (`update-index` runs the post-index-change hook), `core.fsmonitor=false`, and no `--refresh` (so no clean filter runs). Stat data stays zero, and the user's next `git status` re-hashes those paths in the user's own process.
  - **Submodules.** Only the gitlink entry is updated, by the same rule. It never recurses into the submodule.
  - **Failure.** Any error after the lock is taken removes the lock and leaves the index as it was. The index file's mode and `core.sharedRepository` are kept. On Windows a failed rename-over is a skip. **Residual:** a daemon crash while holding the lock leaves a stale `index.lock` that blocks the user's git until it is removed. The lock is held for milliseconds, and the residual is recorded.
  - **Tests** (real temporary repositories, one mutant per rule): a user-staged path kept byte for byte; an equal path refreshed; added and deleted paths; intent-to-add; `git rm --cached`; skip-worktree and assume-unchanged; a gitlink; a symlink and an exec-bit change; a held lock; a race in which a `git add` lands between read and write (the read-before-lock mutant must fail it); HEAD moved after the compare-and-swap; a failed compare-and-swap leaving the index byte-identical; hook and fsmonitor marker files never written and a clean filter never run; split index, sparse index and sparse checkout skipped; a linked worktree changing only its own index; an unmerged index skipped; a `core.ignorecase` case collision skipped (with its mutant); a failed rename of the lock file over the index, after which the lock is removed and the index is byte-identical; and crash injection after the lock is taken.
- DC-2's `build` registers the built tree in the daemon's reviewed-tree registry, bound to workspace, head, branch and snapshot, so `axis.git/1.commit` accepts it the same way it accepts a `review.diff` tree. It carries the per-file truncation acknowledgement (REV-1) for every file it includes. The UI shows the exact "Staged for commit" set that produced the `treeHash`, so "the commit is exactly the reviewed tree" holds for hunk selections. Hunk ids are content-addressed [V], so a changed file invalidates its selection.
- + and - are shown as "Staged for commit" and "Changes", with a one-line note that Axis's staging is separate from `git add`. A one-way mirror into the real index (S2) is a later, separate decision.
- Discard per file uses `axis.worktrees/1.discard`, which is tier 2 and backed up to a ref [V]. Discard per hunk and the hunk and selection reads are missing contracts (plan DC-2, DC-4).

## Decision 5: security consequences

1. **The renderer gets less authority, not more.** ADR 0003's accepted residual was that the upstream renderer holds `localFilesystem`, `localPty`, `encryption`, `nativeHost` and the `UtilityProcessWorker` spawn (threat model R1, PTY-1). Our renderer has none of these. That also closes the residual in `secret-broker.md` §2 (through upstream's `encryption` channel, any renderer can decrypt any `safeStorage` ciphertext of the app). Files, terminals and search reach it only through daemon contracts and main-brokered pty data ports. I1 to I6 stay; I7 becomes "Axis code lives in `apps/desktop` and `packages/*`; no upstream footprint". The renderer is still never trusted: a compromised renderer is the EL-3 actor, as before. **Rule:** no generic file, process or shell channel may be added to main or the preload to save time. Each capability is a contract with a tier, policy rows and the coverage check.
2. **Tier semantics are unchanged.** Main-drawn native confirmation exists **only at tier 4 and above** (`packages/challenge/src/manager.ts:114`, `packages/daemon-host/src/gate/approvals.ts:251` [V]). Tiers 1 to 3 are resolved in the renderer's approval UI by the user principal, and no UI copy may call that native. Approval cards are core-shell components; module content, messages, pages and plugin views cannot render or imitate them. **Main-drawn dialogs outside the challenge tiers** are not approvals and carry no tier: project add and trust, the EL-4 device code, the OS-4 `axis.cliAgents` change and the EL-5 link confirmation. Copy must never cite them to call a tier 1 to 3 approval "native".
3. **CSP and Trusted Types are ours.** The app document sets: `default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; worker-src 'self'; connect-src 'none'; frame-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'; require-trusted-types-for 'script'; trusted-types axis-shell <Monaco's policy names at the pin>`. `'self'` is the app scheme. Inline styles are kept for React and Monaco, as the Code OSS workbench allowed. Lint bans `dangerouslySetInnerHTML`, `innerHTML`/`outerHTML` assignment, `eval` and `new Function` in the renderer. Zod runs `jitless` there (ADR 0003 criterion 5, now measured on our bundle). A Trusted Types smoke test under the production CSP fails on any violation.
4. **Workspace Trust is replaced by the run-trust record that already exists** (`project-registration-and-trust.md`). T3 (main's Workspace Trust half) is dropped: §4.2 of that note already records that it adds nothing an attacker cannot supply. `trust.check { windowId, workspaceId, projectId, projectPath }` (the daemon supplies the path from its journal, as today) becomes: main answers `true` only when the window (for a plugin view, its host window) is live in its registry. It does **not** compare the window's binding, which is scoping only (Decision 2). Main keeps no project store and reads no path of its own. The daemon ANDs that with T1 (the journal record that only main's dialog writes), T2 (the repository binding) and T4 (no revoke), unchanged. This changes main's code and dialogs (OS-3b). The add dialog always offers "Add and trust to run". Trust is no longer refused because the workbench does not trust the folder, since the protection was always main's native click (§4.2). The identity's `trusted` stays `false`. Defaults stay fail closed: untrusted until the user picks "Add and trust to run" or "Trust to run" in main's dialog. "Restricted Mode" becomes "Untrusted: read only". Files of an untrusted project open read only in the files and code modules: `axis.files/1` reads stay allowed and its writes are refused by the daemon. Plain terminals stay ungated (§2 of that note), and CLI and composer runs stay gated.
5. **CFG-1 becomes structural.** Settings live in main's store under the app data directory, in user, application or machine scope only. No repository file is ever read for settings, so the `.vscode/settings.json` gate line becomes "a repository settings file has no effect". `axis.cliAgents` defines programs Axis runs, so a change to it needs main's native confirmation (recommended default; plan ticket OS-4).
6. **Removed classes:** extension-originated commands (ADR 0003 criterion 4, EXT-2), extension environment collections in PTY-5, the reh-web listener, Open VSX VSIX tampering, the minifier's `#private` mangling risk, and Copilot or agent-host code in the bundle. **Kept:** PTY-5 (applied by the pty process as now), G-28 (no debugging ports in a packaged build: `--inspect*` and `--remote-debugging-port` are refused by main at start), EL-5, CLI-1 and every daemon-side control.
7. **Secure storage is a precondition, not a detail.** Without a secure `safeStorage` backend the host runs degraded (`anchor_unreachable`) and nothing can be added or trusted. That is common on WSL, Xvfb and CI with no keyring, and on macOS when the user denies the first Keychain prompt; a denial must read as degraded, never crash. The shell shows a clear "No secure storage: Axis is read only" state, and development and CI get a keyring rig (plan OS-27). The data-directory derivation (`axisDataRoots`, which `XDG_DATA_HOME` and `LOCALAPPDATA` move) is pinned by a test.
8. **New surface to review:** the custom scheme handler (path traversal in the bundle root, MIME types), the preload, the window registry and the new contracts (`axis.files/1` in particular: WT-1-style canonicalisation, no symlink following out of the worktree (FT-1), size caps, control and bidirectional characters escaped, recursive delete capped). `axis.files/1.read` is user-principal only. It is never served to plugin views, composer runs or messages; those keep their own paths and the existing secret withholding. The user's own view of a file such as `.env` is not withheld: it is the user's file, shown to the user. The threat model revision (ADR 0004 implication 7) covers these before G0.

## Decision 6: licensing and legal effect

- **No Code OSS code ships**, so the Code OSS row of `LICENSING.md` is replaced. The rebrand guardrails of ADR 0002 decision 5 (product.json identity, Microsoft strings, the extensions gallery, Copilot removal, Microsoft endpoints) are no longer needed, and the Visual Studio Marketplace and Open VSX questions go away with the extension host.
- **New third-party notices** [I, to verify per exact version in the scaffold ticket]. The top-level packages are MIT: Electron, React and React DOM, Monaco editor and xterm.js; node-pty stays.
  - Monaco is built from VS Code sources, so Microsoft's MIT notice and Monaco's third-party notices travel with it.

## Consequences

- **Positive:** the product's core is no longer an IDE; React, our own layout and our own design system without an upstream budget; no weekly upstream sync; a renderer with far less authority; one place for brand strings and colour tokens from the first commit (the rebrand is cheap: today about 38 overlay strings and main's dialog texts carry the name, and they move to the brand constants as they are ported); a module seam for non-code work.
- **Negative:** we build the IDE surface ourselves and it will be smaller than VS Code: no extensions, no debugger, language servers later. Electron security updates become our job. File manager, terminal, search and hunk staging need new daemon contracts, and they are security-reviewed work. Some overlay UI work is thrown away.
- **Product:** `PRODUCT.md`'s "never a reduced editor" and "full IDE" text is reversed and is edited with the gates (OS-23). A user who wants VS Code keeps their own editor next to Axis; a later "Open in external editor" intent can hand off a path.

## Rollback

- Before G0, the interim Code OSS shell keeps building (nothing is deleted until OS-22), and the packages are shared, so switching back costs only the renderer work done.
- If Electron proves unworkable, Tauri (option B) reuses the renderer, the packages and the contracts, and redoes main's adapters and their evidence.
